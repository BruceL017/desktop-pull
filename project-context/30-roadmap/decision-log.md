| 修改优先级必须先打开完整任务编辑器 | 为一个封闭六选一字段增加页面切换,拖慢黄金路径中的高频整理动作 | D-040 |
| 修改优先级前弹确认框 | 优先级修改可继续调整且有历史可追溯,确认步骤只会增加无必要阻力 | D-040 |
| 点击优先级标识同时打开编辑器或发起拖拽 | 一个命中动作产生多个结果会造成误操作,优先级必须是独立任务行控件 | D-040 |
| 创建任务时强制选择自定义分类 | 会阻断快速收集;收件箱已经提供合法且可稍后整理的默认归属 | D-041 |
| 允许活动任务以零分类或 `null` 分类保存 | 会与收件箱同时表达“尚未归类”,制造两个重复状态和额外迁移分支;垃圾箱任务退出活动分类不属于此方案 | D-041 / D-098 |
| 重新归类时复制任务而不是替换归属 | 会破坏单任务身份和单归属约束,并让历史与完成状态分叉 | D-041 |
| 创建后只能依靠跨分类拖拽改归属 | 分类较多或移动端目标较远时成本过高,无法保证精确且轻量地整理任务 | D-042 |
| 为“新建分类并归入”跳转到独立分类管理页 | 会打断当前任务上下文,把一次直接整理拆成多次页面往返 | D-042 |
| 在每条任务行持续显示分类标签 | 所在分类分组已明确表达归属,重复标签会挤占移动端任务标题空间 | D-042 |
| 只能从独立分类管理页新建空分类 | 用户会离开默认任务清单并失去当前整理上下文,增加无必要的页面往返 | D-043 |
| 新建分类成功后自动创建任务或打开任务输入器 | 用户提交的是分类名称而非任务意图,顺带启动另一动作会造成意外状态和入口混淆 | D-043 |
| 允许两个自定义分类使用相同名称 | 选择器和历史只能显示名称时无法可靠区分目标,容易把任务移入错误分类 | D-044 |
| 分类名称校验失败后清空输入或弹错误对话框 | 会迫使用户重新输入或额外关闭提示,与内联轻量创建目标冲突 | D-044 |
| 不经确认直接删除自定义分类 | 即使任务仍被保留,分类结构和任务归属会批量变化,误触后会打断用户已经整理好的清单 | D-045 |
| 删除分类时要求输入名称或连续确认两次 | 分类删除不会销毁任务内容且后果已明确展示,额外验证与实际风险不相称 | D-045 |
| 重命名分类时弹出确认框或跳转独立页面 | 重命名不会销毁内容且有历史可追溯,额外步骤会打断主清单内的轻量整理 | D-046 |
| 分类改名后用新名称覆盖旧历史摘要 | 会改写事件发生时的事实表达,使历史时间线失真 | D-046 |
| 分类排序必须寻找专用拖拽手柄或先进入排序模式 | 会为同一产品制造第二套拖拽心智模型,增加桌面与移动端的操作成本 | D-047 |
| 分类排序时同步重排或迁移其中任务 | 用户只表达了分类层级顺序变化,连带改写任务会产生未请求的内容变化 | D-047 |
| 修改任务标题或备注后必须再点“保存”或“完成” | 内容修改可逆且有历史,额外提交会让桌面和移动端编辑都多一个无必要步骤 | D-048 |
| 因采用自动保存而取消任务删除确认 | 自动保存只适用于可逆内容编辑,不能扩大到会把任务移出当前清单的破坏性动作 | D-048 |
| 标题或备注每输入一个字符就立即追加历史 | 会把一次自然编辑拆成大量无意义事件,使时间线失去可读性 | D-049 |
| 只有关闭编辑器时才第一次保存内容 | 长时间编辑、应用进入后台或意外离开时会扩大尚未提交内容的风险窗口 | D-049 |
| 标题为空时阻止用户离开整个编辑器 | 会让一个字段错误把用户困在页面中,违背产品持续可用和低阻力编辑目标 | D-050 |
| 标题被清空后自动删除任务或保存为“无标题任务” | 用户只产生了无效编辑,没有表达删除意图或接受新的标题语义 | D-050 |
| 因标题无效而停止保存备注、优先级或分类 | 独立字段的有效修改不应被标题校验连带阻断 | D-050 |
| 第一版为任务备注加入富文本或 Markdown 渲染 | 会增加编辑器、历史差异、数据迁移和未来移动端兼容复杂度,但不改善核心任务整理路径 | D-051 |
| 在备注中支持内嵌清单、附件或图片 | 会重新引入已经排除的子任务与附件生命周期,扩大第一版存储和恢复边界 | D-051 |
| 在主清单中展开完整任务备注 | 长备注会显著拉高任务行并削弱移动端扫描与拖拽效率 | D-052 |
| 让备注预览成为独立展开或编辑控件 | 会把任务行切成更多命中语义,与整行点击编辑和直接拖拽规则冲突 | D-052 |
| 在任务行常驻垃圾桶按钮或提供滑动删除 | 高频滚动、点击和拖拽过程中容易误触破坏性命令,也会挤占移动端任务内容空间 | D-053 |
| 按一次键盘删除键直接删除任务 | 焦点或选中状态不明确时风险过高,且可能绕过已确定的阻断式确认路径 | D-053 |
| 只能进入任务编辑器后才能发起删除 | 会给清单中的明确删除意图增加一次无必要页面切换 | D-053 |
| 发起删除时丢弃或回退尚未自动保存的有效编辑 | 用户已经完成输入,删除意图不等于撤销编辑;恢复后出现旧内容会造成数据意外丢失 | D-054 |
| 取消删除时同时撤销刚才的内容修改 | 取消只否定删除意图,不能隐式否定独立发生的编辑操作 | D-054 |
| 把待保存编辑与删除合并成一条无顺序操作 | 会让历史无法表达先编辑后删除,故障重试时也难以保证恢复到最新内容 | D-054 |
| 每次自动保存成功都弹 Toast 或成功弹窗 | 连续编辑会反复打断用户,且需要额外视觉注意或关闭动作 | D-055 |
| 在每条任务行常驻“已保存”状态 | 正常状态没有持续展示价值,会挤占标题和备注预览空间并增加清单噪声 | D-055 |
| 自动保存失败只在编辑器短暂闪烁后消失 | 用户可能误以为内容已经落盘,与待保存风险必须持续可见的规则冲突 | D-055 |
| 在主清单完整展开任意长度的任务标题 | 极长标题会无限撑高任务行,削弱移动端扫描和拖拽效率 | D-056 |
| 为适配两行展示而截断持久化任务标题 | 展示约束不应破坏任务内容,历史、恢复和备份必须保留完整值 | D-056 |
| 连续超长字符导致任务行横向滚动 | 会挤压优先级与菜单控件并破坏移动端页面布局 | D-056 |
| 应用启动先进入欢迎页、仪表盘或分类管理页 | 会阻断用户直接查看和操作任务清单,与默认入口约定冲突 | D-057 |
| 在移动底栏加入设置、备份或分类作为更多标签 | 会挤压三个高频页面并让低频能力长期占用单手导航空间 | D-057 |
| 桌面与移动端使用不同的页面关系 | 会增加响应式实现与未来原生 App 迁移成本,也让同一用户跨设备重新学习 | D-057 |
| 每次从历史或垃圾箱返回都把任务页滚动到顶部并重置折叠 | 用户会反复寻找刚才的任务和分类,打断查看历史或恢复任务的短暂往返 | D-058 |
| 返回任务页时自动重开编辑器或移动键盘 | 临时编辑界面会遮挡用户想返回的清单位置,也可能意外夺取焦点 | D-058 |
| 跨应用重启恢复旧滚动位置、编辑器或键盘 | 旧位置和输入界面属于瞬时会话状态,重开时恢复容易让用户落在失去上下文的位置 | D-059 |
| 把折叠与焦点等设备界面偏好写入完整备份 | 这些状态没有跨设备任务语义,会让导入结果受原设备屏幕和临时视图影响 | D-059 |
| 覆盖导入后按分类名称或偶然相同标识继承旧折叠状态 | 名称或标识相同不代表导入分类与当前设备旧分类具有同一界面上下文,可能错误隐藏导入内容 | D-060 |
| 在导入校验或写入成功前提前清除设备偏好 | 用户取消或导入失败后会无故丢失当前界面设置,破坏原子覆盖的可预测边界 | D-060 |
| 按删除时绝对索引恢复并回滚当前任务顺序 | 会为恢复一条任务搬动删除后整理过的其他任务,破坏“恢复只合并”的边界 | D-061 |
| 所有恢复任务一律放到分类顶部 | 会丢失可用的原位置脉络,并把低频恢复强行变成最高视觉优先级 | D-061 |
| 原分类已删除时自动重建该分类 | 用户已经明确删除分类结构,恢复任务不应撤销这项后来发生的有效操作 | D-061 |
| 垃圾箱显示分类当前名称而不保存删除时名称 | 分类改名或删除后会丢失任务被删除时的上下文,也无法保证备份往返后的展示一致 | D-062 |
| 在垃圾箱内直接编辑、改状态或拖拽任务 | 会制造一套脱离主清单的任务整理语义,并让恢复时应保留哪个状态变得含混 | D-062 |
| 为恢复任务增加确认弹窗 | 恢复不会销毁数据且可以再次删除,确认步骤只会阻碍误删后的直接修复 | D-062 |
| 把永久删除作为垃圾箱任务行常驻主按钮 | 会让不可恢复操作与高频恢复并列,增加移动端误触风险 | D-062 |
| 每次恢复成功后自动跳转任务页 | 会打断连续恢复并让用户反复往返垃圾箱,与低阻力恢复目标冲突 | D-063 |
| “查看任务”同时打开编辑器或移动键盘 | 用户只表达了定位意图,自动进入编辑会遮挡清单并产生未请求的焦点变化 | D-063 |
| 恢复尚在待保存队列时显示“已恢复” | 会把当前会话工作状态误报为已经安全落盘,掩盖关闭或重载后的丢失风险 | D-063 |
| 永久删除前要求输入任务名或确认短语 | 菜单选择加阻断确认已经明确表达意图,额外抄写只增加操作负担而不改善目标识别 | D-064 |
| 清空确认打开后动态纳入后来进入垃圾箱的任务 | 用户确认时没有看见这些新增目标,连带销毁会突破确认范围 | D-064 |
| 仅凭冻结标识永久删除已经恢复的任务 | 恢复已经取消其垃圾箱资格,继续销毁会把较新的明确操作覆盖掉 | D-064 |
| 清空垃圾箱逐条提交并允许部分成功 | 中途失败会留下难以解释的半清空状态,也无法安全判断重试范围 | D-064 |
| 用任务或分类当前名称回写全部旧历史 | 会让事件随当前状态变化,破坏时间线作为发生时事实的可信度 | D-065 |
| 点击历史记录后弹窗或跳转独立详情页 | 会为一次查看增加界面往返并丢失当前时间线位置,原地展开已经能承载完整事实 | D-065 |
| 在历史记录中直接提供撤销、回滚或恢复 | 会把只读审计页变成第二套状态修改入口,并绕过垃圾箱的单任务恢复边界 | D-065 |
| 把任务、分类和动作三组完整筛选控件常驻历史页顶部 | 会长期挤占移动端纵向空间并降低时间线首屏信息密度 | D-066 |
| 修改筛选后还必须点击“应用” | 筛选不修改数据,额外确认只增加一次无必要操作并隐藏条件是否生效 | D-066 |
| 多个已选动作之间取交集 | 单条事件只有一个动作类型,取交集会稳定产生空结果且不符合多选意图 | D-066 |
| 把历史筛选写入完整备份或跨重启恢复 | 临时回溯条件没有跨设备核心数据语义,重开后延续还可能让用户误以为历史缺失 | D-066 |
| 把每个底层事件类型都作为独立动作筛选项 | 会让移动端筛选列表随功能增长而膨胀,用户也难以预测相近动作的边界 | D-067 |
| 只保存八个动作组而丢弃精确事件类型 | 会无法区分完成与重新打开、组内排序与跨分类移动等真实操作,削弱历史审计价值 | D-067 |
| 为任务创建的初始归属或恢复落位再追加移动事件 | 同一个用户动作会出现重复历史,破坏“一次实际操作一条对应事实”的可读性 | D-067 |
| 把草稿按键、筛选、折叠或导航记录进历史 | 这些行为不改变任务或分类事实,会淹没真正需要回溯的业务变化 | D-067 |
| 在移动历史中显示内部排序键或绝对第几个 | 实现值对用户不可理解,绝对序号也会因其他任务变化而失去发生时语境 | D-068 |
| 展示旧移动事件时动态读取当前相邻对象名称 | 相邻对象后来改名、移动或软删除会改写旧事实,使同一事件在不同时间显示不同内容;永久清理则只允许 D-097 的不可用去身份化 | D-068 / D-097 |
| 让历史位置快照参与当前排序或恢复落位 | 审计上下文不应成为当前状态约束;当前顺序和垃圾箱恢复已有各自权威规则 | D-068 |
| 通过选择器改分类时把任务追加到目标状态区末尾 | 长分类中任务会立即被埋没,用户还要滚动寻找刚完成的整理结果 | D-069 |
| 按原分类绝对序号猜测目标分类位置 | 不同分类规模和内容没有可比较位置,会制造看似精确但无法预测的落位 | D-069 |
| 选择任务当前分类时顺便把它移到顶部 | 用户只重复选择现有值且没有表达重排意图,会破坏无变化操作不写状态与历史的规则 | D-069 |
| 从任务行选择器移动后自动跳到目标分类 | 会打断当前清单中的连续整理,并让用户失去刚才的滚动上下文 | D-070 |
| 从编辑器修改分类后自动关闭编辑器 | 用户只改变归属,没有表达结束编辑意图;关闭会丢失当前任务上下文 | D-070 |
| 选择器移动尚在待保存队列时显示“已移到” | 会把当前会话工作状态误报为安全落盘,掩盖关闭或重载风险 | D-070 |
| 从任务编辑器查看历史时继续叠加此前的分类或动作筛选 | 遗留条件可能把当前任务时间线截断甚至筛成空白,与用户明确查看该任务历史的意图相悖 | D-071 |
| 为任务预筛选暗中保留一套可恢复的旧筛选栈 | 同一历史页会同时存在两套不可见状态,返回结果难以预测,也增加没有用户价值的导航复杂度 | D-071 |
| 尚有最新有效编辑时直接进入历史且不先保存或排队 | 用户刚完成的修改可能不在时间线中且有丢失风险,破坏编辑状态与历史事实的一致性 | D-071 |
| 初始数据库未读取成功时显示可写空清单 | 会把未知既有数据伪装成没有数据,后续只能覆盖旧状态或引入第一版没有定义的合并 | D-072 / ADR-008 |
| 在启动读取故障时建立内存临时任务清单或改写其他存储 | 会形成第二事实源,会话结束可能丢失,原数据库恢复后仍需解决冲突合并 | D-072 / ADR-008 |
| 初始读取失败后自动删除或重建数据库 | 暂时不可读不等于数据不存在或已损坏,自动重建可能直接造成不可恢复的数据丢失 | D-072 / ADR-008 |
| 核心数据未读取完整时允许覆盖导入或导出空白完整备份 | 导入无法先保护当前库,导出则会把未知缺失伪装成完整副本 | D-072 / ADR-008 |
| 直接对当前活跃数据库执行 schema 迁移 | 事务提交后候选仍可能启动失败,旧应用又无法读取新 schema,会失去可完整使用的回退路径 | D-073 / ADR-009 |
| 候选迁移提交后立即提升而不完成完整读取与启动验证 | 只能证明结构变更提交,不能证明候选应用真的能使用全部新数据完成启动 | D-073 / ADR-009 |
| 候选验证期间接受用户任务操作 | 用户变更会落入尚未激活的临时代次,失败回退后无法安全保留 | D-073 / ADR-009 |
| 新代次开放写入后仍长期保留旧数据库或失败候选 | 后续永久删除只清理活跃代次,旧副本会继续残留本应彻底销毁的任务与历史 | D-073 / ADR-009 |

## ADR 准入三门槛(三个全中才写 ADR,否则只进 Decision Log)

1. **难逆转** — 改主意成本大。
2. **无上下文会让人困惑** — 未来读者会问"为什么这么做"。
3. **真实取舍的结果** — 有过被认真否决的替代方案。
