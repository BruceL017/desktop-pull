# ADR-007 · Schema 迁移失败自动回退 last-known-good 应用版本

## Status

Accepted

## Date

2026-07-27

## Decision Drivers

- Desktop Pull 自身更新失败不能让既有任务产品停摆。
- Schema 迁移失败时必须保留旧数据库,不得通过清库恢复可启动状态。
- 第一版没有服务端或第二数据副本可接管本地数据库。
- PWA 离线启动时也需要完成回退,不能依赖重新下载旧应用。

## Context

候选方案包括迁移失败后停在阻断错误页、让失败的新版本继续尝试读取旧 schema、要求用户手动导入备份,以及保留最近一次已验证应用版本并自动回退。阻断错误页违背持续可用目标;失败版本继续运行可能误读或改坏旧数据;手动导入会把应用升级故障转嫁为用户的数据恢复工作。

保留 last-known-good 应用版本会增加应用资源缓存、版本路由和发布测试成本,但能让活跃数据库继续由已知兼容代码使用。ADR-009 进一步规定迁移使用短期、不可写候选副本,而非直接改写活跃代次。

## Decision

- 候选版本迁移前必须保留可离线启动、兼容当前 schema 的 last-known-good 应用版本。
- Schema 迁移必须按 ADR-009 在隔离候选代次中使用失败可回滚的事务;失败候选不得执行任何核心写入。
- 迁移或候选启动失败后清理候选并自动启动 last-known-good 版本,用户继续完整读写未改写的旧活跃代次,无需选择版本或导入备份。
- 同一失败候选被隔离,不得在每次启动时重复迁移;只有不同的修复版本再次尝试。
- 候选只有在迁移提交、完整读取新 schema、成功启动、原子激活且旧代次清理后才能提升为新的 last-known-good。
- 修复版本迁移回退期间持续产生的最新数据,不得回到首次失败时的旧业务快照。

## Consequences

- 应用自身的迁移缺陷不会立即中断用户任务工作。
- 发布系统必须保留一个版本化应用资源集合,并测试联网、离线、失败隔离和后续修复升级。
- Last-known-good 回退只解决旧数据库仍可由旧版本读取的迁移失败;非迁移原因导致浏览器存储无法初始化或完整读取时遵守 ADR-008 的启动数据保护态。
- 候选迁移事务已提交但候选未成功启动时,按 ADR-009 清理候选并继续使用未改写旧代次;旧版本不会接触新 schema。
