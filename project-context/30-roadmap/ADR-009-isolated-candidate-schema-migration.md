# ADR-009 · Schema 迁移使用隔离候选数据库代次

## Status

Accepted

## Date

2026-07-28

## Decision Drivers

- 迁移事务一旦改写活跃数据库,旧应用可能再也无法打开已经升级的 schema。
- 候选应用必须在接管用户数据前证明自己能完整读取新 schema 并完成启动。
- 失败升级应自动回到升级前的最新状态,不能要求用户导入备份或接受数据回退。
- 临时迁移副本不得演变为第二个可写事实源,也不得长期残留已永久删除的数据。

## Context

ADR-007 规定迁移失败时自动回退 last-known-good 应用版本,但直接对活跃数据库执行升级仍存在一个提交后空窗:迁移事务已经成功,候选应用却在重新打开数据库或完成启动时失败。此时旧应用不兼容新 schema,无法安全回退。

候选方案包括让旧应用尝试读取新 schema、为每次变更编写反向迁移、迁移提交后停在恢复页,以及在隔离数据库副本中先完成迁移与启动验证。反向迁移与旧应用猜测新结构都可能破坏数据;阻断恢复页则让应用自身更新长期停住产品。

## Decision

- 每次 schema 升级必须从活跃数据库的一致快照创建不可写的候选数据库代次,不得直接迁移活跃代次。
- 创建快照前必须按 ADR-010 取得单活动窗口的排他迁移窗口,确保候选包含活跃代次的最新状态与历史且其他实例不持有核心数据库连接。
- schema 迁移只作用于候选代次。候选必须完成结构与数据校验、完整读取和一次无错误应用启动,且验证期间不得接受用户核心操作。
- 候选失败、空间不足或流程中断时,持久化激活标记保持指向旧代次。候选工件清理完成后自动启动 last-known-good 应用并继续使用未改写的旧代次。
- 候选全部验证成功后,通过单次原子更新激活标记选择候选代次及兼容应用版本。标记只能保存代次、schema 与应用版本选择信息,不能存放业务记录。
- 激活标记提交后、开放任何核心写入前,必须幂等删除旧数据库代次和其他候选工件。清理完成后候选才能提升为新的活跃事实源与 last-known-good 版本。
- 除了能够证明设备上不存在任何既有数据库代次或候选工件的首次安装引导外,激活标记缺失、冲突或无法读取,或者任何旧代次或候选工件无法确认已清理时,必须复用 ADR-008 的数据保护行为,不得猜测代次、开放写入或自动清库。
- 任一时刻只能有一个激活且可写的核心数据库代次。候选副本是短期、不可写、不可导出的迁移工件,不构成第二个业务事实源。

## Consequences

- 候选迁移提交后启动失败不再改坏活跃数据库;清理候选后旧应用可继续使用原数据。
- 升级期间需要临时占用接近两倍核心数据库空间。空间不足时升级不发生,旧版本保持可用。
- 启动器需要持久化、原子且可恢复的代次激活标记,并缓存标记所指向的兼容应用版本。
- 升级验证和切换期间不能接受用户修改;多个标签页或窗口必须先形成排他迁移窗口。
- 为兑现永久删除,旧代次和失败候选不能在重新开放写入后继续残留;清理不确定会触发数据保护态。
