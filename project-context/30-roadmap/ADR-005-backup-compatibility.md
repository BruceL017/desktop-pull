## Decision Drivers

- 完整备份是本地优先产品在站点数据丢失、设备迁移和未来移动 App 迁移时的主要恢复出口。
- 用户无法控制应用升级后内部 schema 如何变化,有效备份不能因此失效。
- 旧应用无法安全理解未来版本新增或改变的数据语义。
- 任何兼容转换都必须遵守现有的全量校验和原子覆盖边界。

## Context

候选方案包括只支持当前备份版本、对旧备份做尽力解析,以及为所有已发布旧备份维护显式迁移。只支持当前版本会让长期备份随应用升级失去恢复价值;尽力解析缺少确定语义,可能静默丢弃旧字段或错误解释未来字段。

对旧备份维护显式迁移会持续增加 fixture 和测试成本,但这是“完整备份”承诺成立的必要代价。相反,当前应用对未来备份没有足够上下文进行可靠降级,只能要求用户升级。

## Decision

- 每个后续正式 Desktop Pull 版本必须继续导入全部有效的已发布旧备份。
- 旧备份先在当前数据库之外迁移到当前 schema 并完整校验,通过后才进入安全备份、二次确认和原子覆盖流程。
- 当前应用必须在写入前拒绝无法理解的更高格式或 schema 版本,保持当前数据库不变并提示升级应用。
- 每个正式发布的格式和 schema 版本都必须保留完整备份 fixture,并成为后续版本的发布 Gate。
- 当前 schema 收窄某个事件详情时,显式支持的旧版本必须先按其发布时正式 schema 完整验证,再由该版本固定迁移规则确定性投影到当前最小结构。以 `category.created` 为例,旧 schema 合法的创建位置、UI 入口、任务关联、数量或默认元数据可以在验真后收窄为 FORMAT-029 `{}`;以 `category.renamed` 为例,旧 schema 合法的旧、新名称必须先验真,且旧版处理后的新名称与公共 `subject.name` 逐字一致后,才能丢弃重复新名称并投影为 FORMAT-030 `{ beforeName }`。未知、冲突、方向或版本不明及无法由旧事件自身证明的记录必须拒绝。当前格式损坏不得借旧迁移修复,迁移也不得读取当前分类、顺序、后来或相邻事件猜测。
- 对旧 `category.reordered` 收窄为 FORMAT-031 时,旧版本正式 schema 自身必须无歧义证明被移动主体、移动前后方向严格的直接 Custom 邻居或边界、发生时 ID / 名称与真实位置变化;验真后可丢弃旧绝对索引、内部排序值、UI 或完整顺序副本。旧版只有索引、缺少发生时名称或必须依赖导入时当前 `categoryOrder`、当前名称、后来事件或历史重放时必须拒绝。若某已知旧 schema 正式把 Inbox 定义为 Custom 序列首部哨兵,只能由该版本专属规则把它迁为 `start`;不得建立通用猜测。当前 v1 的错误 FORMAT-031 形状不得转走旧迁移路径。
- 对旧 `category.deleted` 收窄为 FORMAT-032 时,只有旧版本正式 schema 自身保存可靠的原始受影响任务数,或明确保证候选操作尚不存在任务主体永久清理且完整连续 `eventOrder = 1...N` 的迁移集合可无歧义证明原始 N,才可投影为 `{ affectedTaskCount }`。验真后可以丢弃旧 schema 合法的任务数组、固定目标、确认/UI 或其他冗余元数据;一旦旧版允许任务主体清理,不得从剩余事件数、最大 `eventOrder`、当前任务、当前 Inbox、当前分类或历史重放猜测。当前 v1 的错误 FORMAT-032 形状不得转走旧迁移路径。

## Consequences

- 备份不会仅因 Desktop Pull 升级而失去恢复价值。
- 备份迁移代码和历史 fixtures 会随版本增长,不能为简化维护而静默删除。
- 破坏性格式变化必须增加显式迁移路径,不能复用版本号改变既有含义。
- 显式迁移可以按目标 schema 删除旧版不再承载的元数据,但规则和正反 fixture 必须随旧版本固定;这不等于对未知字段做尽力解析或静默部分导入。
- 旧应用不能导入未来备份;用户必须先升级到能够理解该备份的版本。
