# ADR-008 · 初始数据未加载时进入数据保护态

## Status

Accepted

## Date

2026-07-28

## Decision Drivers

- Desktop Pull 不能把“尚未读到本地数据”伪装成“用户没有任务”。
- 第一版不具备把临时工作区与之后恢复的既有数据库安全合并的能力。
- `IndexedDB` 必须继续作为唯一持久化事实源,不能为启动故障引入第二套存储。
- 产品应保留明确、可操作的恢复界面,但不能用潜在数据覆盖换取表面可写。

## Context

本决策处理非 schema 迁移导致的 `IndexedDB` 初始化或读取失败,且失败发生在核心数据完整加载之前。候选方案包括显示可写空清单、在内存或另一种存储中创建临时工作区、自动重建数据库,以及进入数据保护态持续重试。

空清单或临时工作区会在原数据库恢复后产生覆盖或合并分歧;自动重建可能直接销毁仍存在但暂时不可读的数据。第一版没有同步或冲突合并系统,因此这些方案都比暂时停止核心操作更违背“不因误操作丢失工作脉络”的北极星。

## Decision

- 应用只有在成功初始化数据库并完整读取当前 schema 所需核心数据后,才能把任务、历史和垃圾箱状态呈现为可操作事实。
- 初始化或完整读取失败时进入启动数据保护态,不得渲染可写空清单、接受任何核心状态修改或运行自动清理。
- 数据保护态保留明确的应用恢复界面,说明本地数据尚未加载且未被应用改写,持续自动重试并提供手动重试。
- 完整备份导出不得生成不完整或空白文件;覆盖导入因无法先读取并保护当前数据库也必须暂停。
- 不得自动删除、重建或覆盖数据库,不得使用内存临时清单、`localStorage` 或其他第二事实源继续工作。
- 只有完整读取成功后才能离开数据保护态。首次安装只有在能够证明不存在任何既有数据库代次或候选工件时才能初始化合法空数据库,随后仍须完整读取;不得仅因激活标记缺失或读取失败推断为空。
- 数据加载成功后的正式任务、分类或历史业务事务失败继续由 ADR-006 的可写降级态处理;自动清理等维护事务不得据此进入用户待保存队列,必须遵守各自 ADR 或开放项;schema 迁移失败继续由 ADR-007 处理。
- 启动阶段数据已经完整读取、仅后续到期清理事务失败时已经存在可信基线,不属于本 ADR 的硬停止边界;该场景按 ADR-014 逻辑排除到期内容并继续提供日常功能。

## Consequences

- 核心任务操作存在一个明确硬停止边界:当前会话尚未建立可信的已持久化基线。
- 用户不会在旧数据暂时不可见时被诱导创建一套竞争状态,也不会下载到冒充完整备份的空文件。
- 恢复界面必须测试自动重试、手动重试、无写入保证和恢复后精确加载原数据。
- 若故障持续,用户暂时不能创建或修改任务;这是第一版为避免不可恢复覆盖而接受的限制。
- 任何删除、重建或覆盖不可读数据库的恢复方案都需要新的明确产品决策,不能作为实现细节自行加入。
- ADR-009 的激活标记或数据库代次角色无法唯一确认时复用本 ADR 的保护行为;这不是允许自动删除不可读数据库,只允许清理角色已经由可靠激活记录确定的迁移工件。
- 实现必须用“完整读取是否成功”而非“启动流程是否仍有失败”裁决边界,避免把 ADR-014 的维护清理失败误升级为未知数据保护态。
