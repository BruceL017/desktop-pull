# ADR-012 · 操作时间与历史稳定全序

## Status

Accepted

## Date

2026-07-29

Amended 2026-07-30 by D-093

## Decision Drivers

- 历史需要表达用户实际完成操作的时间与先后,不能被数据库故障恢复的提交时机改写。
- 多项操作可能共享同一时间值,一次分类操作也可能在同一事务中产生分类与任务两类事件。
- 时间线必须在刷新、筛选、待保存补写、应急导出和完整备份往返后保持同一顺序。
- 第一版单活动窗口提供唯一操作因果链,无需引入多写者时钟协调或分布式排序。

## Context

既有契约要求历史按事件时间倒序,待保存队列按原顺序补写,但没有裁决“事件时间”究竟是用户操作被接受的时间还是数据库最终提交时间,也没有定义相同时间值及一次操作多条事件的稳定顺序。

如果按实际提交时间记录,较早的待保存操作会在存储恢复后突然出现在时间线顶部。如果只依赖时间戳、IndexedDB 自然顺序或备份数组顺序,同时间事件会在查询、迁移或导入后跳动。分类删除及“新建分类并归入任务”还会出现分类事实与任务事实次序不确定的问题。

## Decision

- 每个正式操作在被当前工作状态接受时一次性冻结 `occurredAt` 和单调递增的 `operationSequence`。临时输入、拖拽预览和未确认意图不属于正式操作。
- 同一操作产生的全部历史事件共享该 `occurredAt` 与 `operationSequence`,每条事件另有在该操作内唯一的 `eventOrder`。
- 全局时间线按 `occurredAt` 所属自然日分组;组内依次按 `occurredAt` 倒序、`operationSequence` 倒序排列。同一操作内部按 `eventOrder` 正序排列。
- 直接表达分类操作的分类主体事件排在关联任务主体事件之前。多个关联任务事件按操作前源分类中的任务相对顺序排列。
- 健康事务、待保存队列、自动重试、应急备份物化、完整备份导出与覆盖导入都必须保留原操作时间和稳定顺序。实际提交、重试、导出或导入时间不得替换用户操作时间。
- 永久清理可以留下操作顺序空洞,但不得重编号既有事件或复用已经消耗的值。完整备份必须保存不关联任何主体的 `nextOperationSequence` 进度;覆盖导入后,下一正式操作必须使用该值,且该值严格大于文件中全部保留事件的操作顺序。
- `operationSequence` 与 `eventOrder` 仅用于稳定排序,不得作为用户可见编号。

## Consequences

- 历史事件、数据库 schema 和完整备份必须承载操作时间、操作顺序、操作内顺序及下一操作顺序进度语义。
- 操作顺序进度必须与当前状态和对应历史在同一个原子事务中持久化;写入失败时待保存操作保留已经冻结的值。
- 应急导出需要物化待保存历史,但不能使用导出时间重建事件时间。
- 备份导入必须校验稳定顺序与文件中的下一操作顺序进度并原样持久化,不能依赖文件数组排列或按剩余历史最大值回退进度。
