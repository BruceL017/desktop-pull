# 完整备份版本兼容契约

## 定义

- 已发布旧备份:由任一早于当前版本的正式 Desktop Pull 版本生成,且在该版本中符合备份契约的文件。
- 未来备份:其 `formatVersion` 或 `schemaVersion` 高于当前应用支持范围的文件。

## 强制规则

### COMPAT-001 · 已发布旧备份持续可导入

每个后续正式版本必须继续接受全部有效的已发布旧备份。不得仅因备份由旧应用或旧 schema 生成而要求用户放弃数据。

### COMPAT-002 · 写入前隔离迁移

旧备份必须先在内存或与当前数据库隔离的临时表示中迁移到当前导入 schema。迁移过程不得修改当前数据库,也不得改写用户选择的原备份文件。

### COMPAT-003 · 迁移后完整校验

迁移结果必须通过当前版本的格式、字段、关联完整性和领域约束校验,之后才能进入 `backup-import.md` 的安全备份、二次确认和原子覆盖流程。迁移或校验失败时,当前数据库必须保持不变。

### COMPAT-004 · 未来备份拒绝写入

当前应用不得猜测、降级解析或部分导入未来备份。必须在任何持久化写入前拒绝文件,明确说明备份来自更高版本并提示用户升级 Desktop Pull。

### COMPAT-005 · 发布兼容 fixtures

每次正式发布新的备份格式或数据库 schema 时,必须保存该版本的有效完整备份 fixture。后续版本的发布 Gate 必须逐个验证所有历史 fixtures 均能迁移、校验并恢复正确语义。

### COMPAT-006 · 旧备份缺少草稿时按空集合迁移

正式发布时尚未包含草稿集合的有效旧备份必须迁移为当前格式的空草稿集合,不得因此拒绝旧备份或虚构任务、草稿及历史。包含草稿的已发布备份必须先按其原版本 schema 读取,再通过该版本随发布 fixture 锁定的确定性迁移规则生成 FORMAT-015 记录;迁移必须保留原版本已有的标题与入口语义,不得按目标分类合并入口、trim 标题、静默丢弃草稿或在导入时临时猜测缺失语义。若某个正式旧 schema 没有直接保存当前 `generation` 或 UTF-16 `cursorOffset`,其兼容映射必须在支持该旧版本的迁移与 fixture 中明确规定,不能依赖设备、界面语言或导入时偶然状态。

### COMPAT-007 · 历史公共外壳迁移不得伪造

FORMAT-016 发布后,旧备份迁移必须依据旧版本的精确事件类型确定任务主体或分类主体,并生成只有 `subjectType`、`subject`、`eventType`、`occurredAt`、`operationSequence`、`eventOrder` 与 `details` 的公共外壳。任务变更迁移后必须把原任务标识与发生时标题放入严格任务 `subject`;分类创建、重命名、排序和删除迁移后必须把分类标识与发生时名称放入严格分类 `subject`,不得为满足新 schema 生成任务占位字段。迁移必须保留原 `(operationSequence, eventOrder)` 稳定逻辑键与合法缺口,不得生成独立事件 ID 或重编号。迁移结果的 `eventType` 必须按旧版本随发布规则无歧义映射为 FORMAT-017 的 14 个精确值之一;各类型 `details` 分支发布后必须按对应版本化规则生成符合 FORMAT-018 的事件专属最小严格对象,不得把旧完整记录直接倾倒成实体快照、通用新旧包、根级第二判别或开放 metadata。无法无歧义确定主体、精确类型、必填快照、稳定键或事件专属最小载荷时必须拒绝导入,不得猜测、填默认值、合并候选类型或丢弃事件。

迁移为 `task.content_changed` 时,旧 schema 必须能无歧义确定本次保存后的标题、发生时分类语义、实际变化字段及对应旧值和备注新值,再生成 FORMAT-019 的三个带 `categorySnapshot` 精确分支之一。保存后的标题只进入 `subject.title`;迁移不得添加 `afterTitle`、`changedFields`、根级 `kind`、默认空值或重复事实,也不得从当前任务归属猜测发生时分类。无法确定发生时分类、标题或备注是否实际变化、任一必需值,或只能得到含混的部分组合时,必须拒绝导入。

迁移为 `task.completed` 或 `task.reopened` 时,旧 schema 必须能无歧义确定精确事件方向和发生时分类语义,再生成 FORMAT-020 `{ categorySnapshot }`。旧版本若明确保存状态新旧值,迁移必须先按旧 schema 验证其与事件方向一致,再丢弃冗余状态字段;冲突时拒绝。不得从当前最终状态或归属反推事件前态与发生时分类,也不得把旧状态字段保留进当前详情。

旧版本事件 schema 一旦明确声明历史前后任务邻居字段,迁移结果必须分别使用 FORMAT-021 的 `PreviousTaskNeighborSnapshot` 与 `NextTaskNeighborSnapshot`:前侧只允许 `start | task | unavailable`,后侧只允许 `end | task | unavailable`,正常保留邻居的 `task` 分支必须且只能是 `{ kind, taskId, title }`。迁移必须从旧事件发生时事实无歧义得到方向、另一任务身份及当时用户原文标题;不得读取导入时当前顺序、当前分类、当前状态或当前标题来补算,目标后来移动、换分类、完成、软删除或改标题也不得改写快照。未知、悬空、自引用、方向错配或无法确定发生时标题的旧引用必须拒绝,不得生成边界、当前标题或 `unavailable` 兜底。FORMAT-021 只锁定联合本身;D-107 / FORMAT-022 已锁定 `task.created`,D-108 / FORMAT-023 已锁定且不含邻居字段的 `task.priority_changed`,D-109 / FORMAT-024 已锁定复用四个邻居槽位的 `task.reordered`,D-110 / FORMAT-025 已锁定复用来源与目标四个邻居槽位的 `task.category_changed`,D-111 / FORMAT-026 已锁定复用整批前来源与整批后最终 Inbox 四个邻居槽位的派生迁移且允许批次邻居同方向跨侧重复,D-112 / FORMAT-027 已锁定复用软删除移出前单一位置的两个邻居槽位,D-113 / FORMAT-028 已锁定复用恢复插入后单一位置的两个邻居槽位,D-114 / FORMAT-029 已锁定不含邻居字段的 `category.created`,D-115 / FORMAT-030 已锁定不含邻居字段的 `category.renamed`,D-116 / FORMAT-031 已锁定自定义分类序列邻居字段的 `category.reordered`,D-117 / FORMAT-032 已锁定不含邻居字段且只保存 `{ affectedTaskCount }` 的 `category.deleted`;14 个事件类型的精确详情分支均已锁定。

旧版本 `task.trashed` 只有在旧文件自身无歧义保存删除时分类、`open | completed` 状态、移出前同分类同状态双邻居及其发生时标题时,才能迁移为 FORMAT-027。FORMAT-014 无标题恢复锚点只能验证自身生命周期,不得用于补造历史标题或整个删除位置;当前任务、当前顺序、默认边界、相邻事件及后来恢复或再次删除状态同样不得作为迁移来源。迁移后的 FORMAT-027 是只读审计事实,不得成为恢复定位源。

旧版本 `task.restored` 只有在旧记录自身无歧义保存恢复事务完成后的实际分类语义(Custom 的 ID 与恢复时名称,或 Inbox)、`open | completed` 状态、插入后同分类同状态双邻居及其发生时标题时,才能迁移为 FORMAT-028 精确 `{ categorySnapshot, status, position }`。原 Custom 分类当时仍存在时必须证明同一 ID 与恢复时当前名称,当时已经删除时必须证明实际落点为 Inbox;不得从 FORMAT-027 删除事件、FORMAT-014 无标题恢复锚点、导入时当前状态、默认回退、相邻事件或历史重放补算任一事实。迁移后的 FORMAT-028 是恢复结果的只读审计事实,不得成为恢复定位或当前顺序来源;任一必需事实不确定时必须拒绝导入。

迁移为 `category.created` 时,必须先按备份声明的、明确受支持的旧版本 schema 验证整条旧记录。只有外层旧事件类型以及合法分类主体、发生时间和稳定顺序本身已经无歧义证明“创建该分类”时,才能把公共 `subject` 规范化为创建时分类 ID 与用户原文名称,并把当前 FORMAT-029 `details` 确定性生成为精确 `{}`。旧版本正式允许的重复身份或名称、位置、界面入口、关联、计数、默认值等创建元数据必须先按旧 schema 验证一致性与合法性,再统一投影掉;不得保留到当前详情。字段未知、值冲突、旧 schema 本就不允许、主体或类型含混时必须拒绝,不得从导入时当前分类、当前 `categoryOrder`、首次看见该分类、后来事件或配对任务事件推断创建事实。迁移后的当前 `categories` 与 `categoryOrder` 必须只由旧版本自身的当前状态事实确定,不得反向重放 `category.created` 补建分类、复活后来已删除分类、恢复旧名称或推导当前顺序。合法旧永久清理已经移除原选择器任务主体及其任务历史时,独立分类创建事件仍可单独迁移,不得要求或补建配对任务事件;反向孤立的任务归类事件不得用分类创建迁移补救。当前 v1 的缺失、`null`、数组、字符串或非空 `category.created.details` 属于当前格式损坏,不得冒充旧版本进入该迁移路径。

迁移为 `category.renamed` 时,同样必须先按备份声明的、明确受支持的旧版本 schema 验证整条旧记录。公共 `subject` 必须规范化为同一分类 ID 与改名后用户原文名称;旧版本若正式在 `details` 同时保存改名前后名称,必须先验证两端名称合法、不同,再要求旧后值与规范化后的 `subject.name` 逐字一致,之后丢弃冗余后值并把旧前值确定性投影为 FORMAT-030 精确 `{ beforeName }`。未知字段、旧 schema 不允许的字段、前后名称冲突或含混、主体或类型无法判别时必须拒绝;不得从导入时当前分类名称、当前 `categoryOrder`、后来事件、首次出现该分类或历史重放推断、校验或修复任一名称。迁移后的 `categories` 与 `categoryOrder` 仍只取旧版本自身当前状态事实,不得重放 `category.renamed` 恢复旧名称或推导当前名称与顺序。当前 v1 中 `category.renamed.details` 缺失、为 `null`、数组、字符串、空对象、含 `afterName`、未知或额外字段,或 `beforeName` 与 `subject.name` 相同,都属于当前格式损坏,不得冒充旧版本进入迁移路径。

迁移为 `category.reordered` 时,必须先按备份声明的、明确受支持的旧版本 schema 验证整条旧记录。只有旧值自身无歧义证明被移动 Custom 分类主体、移动前后两组有方向的自定义分类序列边界,以及每个存在邻居的分类 ID 与发生时用户原文名称,才能确定性投影为 FORMAT-031 精确 `{ beforePosition, afterPosition }`;每个位置只含 `previousCategory` / `nextCategory`,前侧只允许 `start | category`,后侧只允许 `end | category`。不得从迁移时当前 `categoryOrder`、后来事件、历史重放、Inbox、绝对索引/rank/排序键或 `unavailable` 推断缺失位置、边界、身份或名称。未知字段、冲突或含混方向/主体/邻居必须拒绝。迁移后的当前分类集合与顺序仍只取旧版本自身当前状态事实;当前 v1 的缺失/额外字段、错误联合、Inbox 或不可用邻居、主体自引、位置内重复邻居和相同前后位置均是当前格式损坏,不得冒充旧版本进入迁移路径。

迁移为 `category.deleted` 时,必须先按备份声明的、明确受支持的旧版本 schema 验证整条旧记录。只有旧记录自身保存删除受理时原受影响活动任务数,或旧文件能够证明同一操作的 FORMAT-026 迁移集合仍是清理前完整、无缺口且按来源总顺序排列,才能确定性生成 FORMAT-032 精确 `{ affectedTaskCount }`。`0` 只能由旧记录明确保存为零或由完整空迁移集合连同合法分类删除事实证明,不得作为缺失默认值。不得从迁移时当前任务归属、当前 Inbox、剩余迁移事件数量、最大 `eventOrder`、后来历史、任务状态拆分或历史重放推断;已经合法清理部分任务事件但没有原计数的旧记录必须拒绝。当前 v1 中缺失、`null`、非对象、非 JSON 非负安全整数、任务列表或任意额外字段都属于当前格式损坏,不得冒充旧版本进入迁移路径。

迁移为 `task.created` 时,旧 schema 必须能从旧文件自身无歧义确定提交时任务标题、初始 `CategorySnapshot`,以及任务插入完成后在该分类未完成序列中的直接前后邻居和发生时标题,再生成 FORMAT-022 精确 `{ categorySnapshot, position }`。`position` 必须严格嵌套 `{ previousTask, nextTask }`;不得从当前任务顺序、最终分类、当前标题、默认顶部或末尾边界推断缺失值,不得用 `unavailable` 掩盖无法还原的正常邻居,也不得把旧入口、草稿代次、默认状态、优先级、备注、内部排序键或通用 `before` / `after` 保留进当前详情。任一必需事实不确定时必须拒绝导入。

迁移为 `task.priority_changed` 时,旧 schema 必须能从旧文件自身无歧义确定操作发生时 `CategorySnapshot`、接受前优先级和同一操作接受后的优先级,再生成 FORMAT-023 精确 `{ categorySnapshot, beforePriority, afterPriority }`。两个值都必须映射到 `P0` 至 `P5` 且不同;不得从任务最终优先级、新建默认 `P3`、当前分类、当前顺序、当前标题或相邻事件猜测缺失值,也不得保留旧界面控件、设备形态、本地化标签、位置、排序键、状态或通用整实体快照。任一事实不确定或旧新值冲突时必须拒绝导入。

迁移为 `task.reordered` 时,旧 schema 必须能从旧文件自身无歧义证明同一分类、同一完成状态序列中的真实换位,并确定发生时 `CategorySnapshot`、`open | completed` 状态及移出前、插入后的两组直接邻居与发生时标题,再生成 FORMAT-024 精确 `{ categorySnapshot, status, beforePosition, afterPosition }`。不得从最终或当前顺序、当前分类、当前状态、当前标题、绝对索引、内部排序键或相邻事件猜测缺失事实,也不得保留旧拖拽区域、手势、阈值或设备来源。原旧文件表达正常未清理事件时,前后位置必须不同且不得用 `unavailable` 补缺;旧 schema 已无歧义证明合法清理投影时,迁移后的多个邻居可以为 `unavailable`,两个位置也可因此收敛,不得重新以相等拒绝。任一必需事实不确定时必须拒绝导入。

迁移为 `task.category_changed` 时,旧 schema 必须能从旧文件自身无歧义证明任务由用户直接改到另一分类,并确定操作发生时唯一的 `open | completed` 状态、身份不同的来源与目标 `CategorySnapshot`、主体移出前在来源同状态序列的位置、主体插入后在目标同状态序列的位置及全部正常任务邻居的发生时标题,再生成 FORMAT-025 精确 `{ status, source, target }`;`source` / `target` 各自必须严格为 `{ categorySnapshot, position }`,两个位置各自严格为 `{ previousTask, nextTask }`。正常未清理事件四个槽位中的可识别任务 ID 必须跨槽两两不同且非主体。不得从最终或当前归属、顺序、状态、标题、绝对索引、内部排序键、相邻事件或拖拽/任务行/编辑器/新建分类入口猜测任一缺失事实,也不得把分类删除派生迁移、任务创建、软删除或恢复改写成该类型。来源与目标位置结构相同是合法跨分类事实,不得以相等拒绝;旧 schema 已无歧义证明合法清理投影时,对应任务槽位可以迁移为 `unavailable`,但不得借此掩盖悬空、自引用、重复可识别任务身份、方向错误或普通缺失。任一必需事实不确定时必须拒绝导入。

迁移为 `task.moved_to_inbox_by_category_deletion` 时,旧 schema 必须能从旧文件自身无歧义证明它与同时间、同操作的 `category.deleted(eventOrder = 0)` 配对,并确定操作发生时唯一的 `open | completed` 状态、与分类主体一致的来源 Custom `CategorySnapshot`、整批开始前来源同状态位置、完整来源总顺序连续追加后最终 Inbox 同状态位置及全部正常邻居发生时标题,再生成 FORMAT-026 精确 `{ status, source, targetPosition }`。任务事件必须按来源权威总顺序而非状态分组保留原 `eventOrder`;最终位置可以引用更晚事件,同一批次邻居可以在来源与目标同方向重复,不得套用 FORMAT-025 的跨侧互异规则。不得从当前或最终归属、当前 Inbox 尾部、绝对索引、事件顺序、D-009、HIST-006 或相邻分类删除猜测缺失事实,也不得保存目标 Inbox 快照。合法旧清理投影可以保留 `unavailable`、任务事件缺口和原顺序号,但不得用它掩盖孤立迁移、来源错配、自引用、可识别 `taskId` 的位置内重复、可识别 `taskId` 跨方向重复或半侧去身份化。任一必需事实不确定时必须拒绝导入。

### COMPAT-008 · 后来的永久清理不使旧快照失效

一份备份在其导出版本中有效时,当前数据库后来永久清理过其中某项任务不得成为兼容性拒绝理由。迁移与校验不得查询当前或产品外的任务墓碑、删除黑名单或删除记录来删改备份语义;通过后继续进入 `backup-import.md` 的完整覆盖与导入时到期过滤。

### COMPAT-009 · 迁移保留系统语义与用户原文边界

历史备份迁移必须把旧版本可无歧义识别的系统分类、状态、`P0` 至 `P5` 优先级、事件类型和位置边界转换为当前稳定语义码,其中事件类型只能映射到 FORMAT-017 精确值并由该值按 HIST-004 推导动作组,同时逐字保留任务标题、备注、自定义分类名称及其历史快照。不得仅凭旧界面的中文或英文显示名称猜测 `eventType`,也不得把旧界面文案继续作为当前系统值或翻译用户原文。无法无歧义区分系统文案与用户值,或一个旧类型可能对应多个当前类型时,必须在写入前拒绝,不得猜测或部分导入。

### COMPAT-010 · 当前规范表示不得追溯判废旧备份

已发布旧备份必须先按其声明版本当时的正式 schema 验证,再在 COMPAT-002 的隔离表示中迁移。旧版本如果曾正式允许其他标识、分类引用或时间编码,迁移可以且必须在语义无歧义时转换为当前 FORMAT-011 的 UUID、`CategoryRef` 与 UTC 固定毫秒表示;当前 v1 的严格表示不得直接用于判定该旧原文件无效,也不得改写用户保存的原文件。

无法无歧义生成稳定 UUID、区分固定收件箱与自定义分类、确定原时间瞬间或保持全部引用一致时,必须在任何当前数据库写入前拒绝迁移结果,不得随机生成身份、按名称猜测归属或按当前设备时区解释。每个正式历史 fixture 必须继续按其原版本验证并覆盖成功迁移后的规范表示。

### COMPAT-011 · 旧清理引用迁移为不可用

已发布旧备份必须先按其原 schema 判断历史任务邻居与恢复锚点是否合法,并保持两套联合分离:FORMAT-014 恢复锚点的 `task` 分支只迁移身份而不增加标题,FORMAT-021 历史邻居的 `task` 分支还必须迁移发生时标题。原版本明确允许永久清理后保留一个指向已移除任务的结构化引用时,隔离迁移必须把该整个引用转换为 FORMAT-013 的精确 `UnavailableTaskRef`,并删除旧引用中的任务标识、标题或其他目标内容;该规则适用于所有由原事件 schema 声明的历史任务邻居字段,不限于移动事件。若被引用任务仍存在于有效删除前备份中,不得因当前数据库后来清理过它而提前转换;该任务与引用继续按旧快照迁移,只有 IMPORT-006 的导入时到期过滤可以随后触发同事务去身份化。

迁移不得从用户自由文本中的相同 UUID 或标题推断引用,不得生成任务墓碑、指纹或映射来维持旧身份。原 schema 不允许悬空引用或无法无歧义判定其语义时必须按 COMPAT-003 拒绝,不得以 `UnavailableTaskRef` 掩盖损坏文件。

### COMPAT-012 · 旧任务记录无歧义迁移到当前生命周期

FORMAT-014 发布后的旧备份必须先按其声明版本确定任务内容、状态、优先级、创建操作时间、最近一次实际任务业务状态变化的原始 `occurredAt`、活动归属或垃圾箱删除上下文及恢复锚点,再在隔离表示中映射为当前精确任务记录。旧版本正式把缺少备注定义为“无备注”时可以映射为 `notes: ""`;除此之外不得用空串、`null` 或默认值填补无法确定的用户内容。

迁移不得用导入、迁移或数据库提交时间伪造 `createdAt`、`updatedAt`、`deletedAt` 或 `expiresAt`,不得从当前数组排列猜测活动分类或顺序,也不得在公共字段与生命周期之间保留重复状态、内容或优先级。旧 schema 明确提供单一权威来源时必须按其规则迁移;来源冲突、时间语义不明、生命周期无法判别或锚点无法无歧义转换时必须拒绝。迁移结果必须完整通过 FORMAT-014 以及 `taskOrderByCategory` 的跨记录完整性校验。

## 验收 Gate

- 对每个已正式发布的历史 fixture 执行导入,验证任务、分类、顺序、垃圾箱、两种主体历史和已有草稿迁移后语义不变。
- 对旧备份迁移和迁移后校验分别注入失败,验证当前数据库与原备份文件均保持不变。
- 构造高于当前支持范围的 `formatVersion` 和 `schemaVersion`,验证两者都在写入前被拒绝并提示升级应用。
- 验证未来备份不会触发安全备份下载、二次确认或任何部分数据写入。
- 新增格式或 schema 版本时,验证仓库同时新增对应完整备份 fixture 和兼容测试。
- 导入不含草稿集合的有效旧 fixture,验证迁移得到空草稿集合且其他数据不变。
- 迁移包含草稿的每个已发布旧 fixture,验证使用该版本固定的确定性规则生成 FORMAT-015 记录,保留已有标题和入口语义,且不会按目标分类合并入口、trim 或丢弃草稿;旧格式未直接保存代次或光标时,验证结果只由版本化迁移规则决定而不随设备、语言或导入时刻变化。
- 对含任务变更和分类管理事件的旧 fixture 执行迁移,验证主体按精确事件类型正确判别且没有伪造任务字段;构造无法判别主体的旧事件时验证在写入前拒绝。
- 迁移 FORMAT-016 之前的历史 fixture,验证结果只有七字段公共外壳、严格主体分支并保留原 `(operationSequence, eventOrder)` 与合法缺口,没有生成事件 ID、动作组或本地化摘要;无法无歧义生成任一必填值时拒绝。
- 迁移各版本历史 fixture 时,验证每个 `details` 只按已发布版本规则形成 FORMAT-018 的事件专属最小严格对象,不会复制旧完整任务或分类记录、生成通用整实体新旧包、根级第二判别、`null` 或任意兼容字段;无法确定必填最小事实时拒绝而不补默认值。
- 将旧内容编辑事件迁移为 FORMAT-019 三个分支,验证发生时 `categorySnapshot`、精确变化字段和原文值保持,保存后标题只进入 `subject.title`,且不生成 `afterTitle`、`changedFields` 或默认值;旧事实不足以确定发生时分类、分支或新旧值时拒绝。
- 将旧完成与重新打开事件迁移为 FORMAT-020,验证详情只保留发生时 `categorySnapshot`;旧状态字段先与方向校验再丢弃,冲突或无法确定发生时分类时拒绝而不按当前任务猜测。
- 将旧创建事件迁移为 FORMAT-022,验证从旧文件事实得到初始分类与创建后未完成序列的嵌套双邻居,提交标题只进入 `subject.title`;无法确定分类、任一邻居方向或发生时标题,只能从当前顺序或默认边界猜测,或旧数据两侧指向同一任务时拒绝,不得补 `unavailable`、入口、草稿、默认值或排序元数据。
- 将旧优先级事件迁移为 FORMAT-023,验证只从旧文件事实得到发生时分类与不同的合法旧新值;只能从最终任务优先级、默认 `P3`、当前分类或相邻事件猜测任一值,以及旧值相等、非法或冲突时拒绝,不得保留控件来源、位置、排序键、本地化标签或完整任务。
- 将旧组内排序事件迁移为 FORMAT-024,验证只从旧文件事实证明同分类同状态真实换位并得到一份发生时分类、一份状态及两组严格直接邻居;只能从最终或当前顺序、当前分类/状态/标题、绝对索引、排序键或相邻事件猜测任一事实时拒绝,不得保留拖拽 UI、手势或设备来源。
- 迁移原版本中已无歧义表达合法清理投影的组内排序 fixture,验证多个邻居可变为 `unavailable` 且前后位置收敛后仍接受;普通缺失、悬空、自引用或相同前后位置不得借不可用值伪装为合法旧清理。
- 将旧跨分类事件迁移为 FORMAT-025,验证只从旧文件事实证明直接分类变化、唯一状态、不同的来源与目标分类快照、来源移出前位置、目标插入后同状态位置及全部发生时邻居标题;正常可识别任务 ID 跨四槽两两不同且非主体,不得保留或猜测拖拽、任务行、编辑器、新建分类入口、绝对索引、排序键或当前顺序。
- 迁移来源唯一任务到目标空状态序列的旧跨分类 fixture,验证来源与目标位置都为 `{ start, end }` 仍接受。只能从最终或当前归属/顺序/状态/标题、相邻事件或界面入口猜测任一必需事实,来源目标分类相同,或无法区分直接归类与分类删除派生迁移时拒绝。
- 将旧分类删除派生迁移为 FORMAT-026,验证旧文件自身证明匹配分类事件、来源 Custom 快照、不变状态、来源总顺序、整批前来源位置、整批后最终 Inbox 位置和发生时标题;混合状态事件仍按来源总顺序,同方向批次邻居跨侧重复及最终位置引用更晚事件合法。
- 只凭 D-009 追加约定、HIST-006 事件顺序、当前或最终 Inbox 尾部、绝对索引或相邻分类删除猜测 FORMAT-026 任一位置时拒绝;来源错配、孤立迁移、逐项中间位置、按状态分组、可识别 `taskId` 跨方向重复或把固定 Inbox 另存快照时同样拒绝。
- 迁移合法旧永久清理结果时,验证允许 FORMAT-026 任务事件少于原受影响数量并保留 `eventOrder` 缺口,重复邻居的全部出现槽位都为 `unavailable`;只清理一侧、补建事件或重编号时拒绝。
- 迁移原版本中已无歧义表达合法清理投影的跨分类 fixture,验证对应邻居可变为 `unavailable` 且位置即使结构相同仍保留事件;普通缺失、悬空、自引用、跨槽重复可识别任务身份或方向错误不得借不可用值通过。
- 将任一旧版本已声明的历史前后邻居字段迁移为 FORMAT-021,验证前侧只得到 `start | task | unavailable`、后侧只得到 `end | task | unavailable`,正常 `task` 分支只含另一任务 ID 与发生时标题;导入时任务已经改标题、移动、换分类、完成或软删除不改变结果。构造方向错配、未知或悬空任务、自引用、缺少发生时标题以及只能从当前顺序或标题猜测的旧引用,验证拒绝而不补值。FORMAT-014 恢复锚点不得因此增加标题。
- 将旧 `task.trashed` 迁移为 FORMAT-027,验证只从旧文件自身得到删除时分类、唯一 `open | completed` 状态、移出前同分类同状态直接邻居及其发生时标题。缺少任一标题或其他必需事实,只能从 FORMAT-014 无标题锚点、当前任务、当前顺序、默认边界或相邻事件猜测时,必须拒绝而不补值。
- 迁移并导入同一任务经历恢复、修改、移动或再次删除后的旧 FORMAT-027,验证删除历史原样保留且不与当前生命周期、当前分类、状态或顺序交叉校验;恢复定位始终只读当前 FORMAT-014 生命周期。
- 将旧 `task.restored` 迁移为 FORMAT-028,验证只从旧记录自身得到实际插入后分类语义(Custom 的 ID 与恢复时名称,或 Inbox)、唯一 `open | completed` 状态、插入后同状态直接邻居及其发生时标题;原分类仍存在与已经删除回退 Inbox 的 fixtures 都按旧记录所证明的实际结果迁移。
- 缺少 FORMAT-028 任一必需事实,只能从 FORMAT-027 删除事件、FORMAT-014 无标题锚点、当前状态、默认回退、相邻事件或历史重放猜测时,必须拒绝而不补值。迁移后任务后来移动、改状态或分类改名删除的当前差异不得交叉校验或改写该事件。
- 迁移合法旧永久清理结果且 FORMAT-028 `position` 引用已移除任务时,验证整个引用变为精确 `unavailable` 并删除目标 ID 与标题;不得用不可用值掩盖普通悬空、缺失发生时标题或其他损坏。
- 对每个明确受支持、且原 schema 正式允许 `category.created` 携带重复身份/名称、位置、界面入口、关联、计数或默认值的旧 fixture,先验证原记录合法,再迁移为公共分类主体与 FORMAT-029 精确 `{}`;结果不得保留这些旧创建元数据。
- 构造旧记录类型或分类主体含混、字段未知、重复值冲突,以及只能从当前分类、当前顺序、首次看见、后来事件或配对任务事件猜测创建语义的 fixture,验证迁移在写入前拒绝。对照当前 v1 的缺失、`null`、数组、字符串或非空 `category.created.details`,验证它们按当前格式损坏拒绝,不得套用旧版本迁移规则。
- 迁移包含分类创建后又重命名、重排或删除的旧 fixture,验证当前 `categories` / `categoryOrder` 只按旧文件的当前状态事实生成,创建历史仍保留创建时主体与 `{}` 但不得复活已删除分类、恢复旧名称或重建旧顺序。
- 迁移一个因合法永久清理已移除选择器关联任务及其主体历史、只剩分类创建事件的旧 fixture,验证独立事件迁移为原顺序 FORMAT-029 `{}` 且不补建任务事件。构造反向只剩任务归类事件的旧 fixture,验证不得借分类创建迁移规则补齐或接受。
- 对每个明确受支持、且旧 schema 正式在 `category.renamed.details` 保存改名前后名称的 fixture,先按旧 schema 验证两端名称合法且不同,再要求旧后值与规范化公共 `subject.name` 逐字一致、丢弃冗余后值并迁移为 FORMAT-030 精确 `{ beforeName }`;结果不保留 `afterName`、分类记录、位置、顺序、任务、入口或其他元数据。
- 构造旧改名记录的后值与公共主体冲突、前后值相同、字段未知、主体或类型含混,以及只能从当前分类、当前顺序、后来事件、首次出现或历史重放猜测任一名称的 fixture,验证迁移在任何写入前拒绝。对照当前 v1 的缺失、`null`、数组、字符串、空对象、`afterName`、未知或额外字段及相同 `beforeName` / `subject.name`,验证全部按当前格式损坏拒绝且不得套用旧迁移。
- 迁移包含多次改名后又排序或删除分类、并永久清理任意任务主体的旧 fixture,验证每条 FORMAT-030 的分类 ID、改名前 `beforeName`、改名后 `subject.name` 和稳定键逐字保留,独立分类事件不随任务清理消失;当前 `categories` / `categoryOrder` 仍只由旧文件当前状态事实生成,不重放历史。
- 对每个明确受支持且旧 schema 保存分类移动前后位置的 `category.reordered` fixture,验证只有记录自身完整证明移动主体、两组方向边界或 Custom 邻居 UUID 与发生时用户原文名称时才迁移为 FORMAT-031;结果精确只含 `beforePosition` / `afterPosition` 和各自 `previousCategory` / `nextCategory`,不保留索引、rank、排序键、`categoryOrder`、拖拽或设备字段。
- 构造只能从当前顺序、后来事件、历史重放、Inbox、绝对索引或 `unavailable` 猜测任一边界/邻居/名称,以及主体自引、位置内重复邻居、相同前后位置、字段未知或方向含混的旧 fixture,验证迁移在写入前拒绝。对照同类当前 v1 损坏详情,验证不得套用旧迁移规则修复。
- 迁移分类排序后又改名、再次排序或删除主体及邻居的旧 fixture,验证 FORMAT-031 公共主体、发生时邻居 ID/名称、`start` / `end` 边界和稳定键逐字保留;分类筛选与搜索只读事件自身,当前 `categories` / `categoryOrder` 仍只来自旧文件当前状态而不重放历史。
- 对明确受支持且旧 schema 自身保存分类删除原受影响任务数的 fixture,验证迁移为 FORMAT-032 精确 `{ affectedTaskCount }`;旧值为 `0` 时原样保留,不增加任务数组、状态拆分、分类身份副本、Inbox、位置、确认/草稿/UI 或原因字段。
- 对未保存原计数但完整保留清理前 FORMAT-026 集合的旧 fixture,验证只按同操作无缺口 `eventOrder = 1..N` 确定性生成计数;删除任一迁移事件、留下顺序缺口、来源分类错配,或只能读取当前任务/Inbox、剩余数量、最大顺序及历史重放时拒绝。
- 对照当前 v1 的缺失、`null`、负数、小数、超出安全整数、字符串、任务清单、状态拆分或额外字段,验证全部按当前格式损坏拒绝且不得套用旧迁移规则修复。
- 迁移覆盖旧版全部事件语义的 fixtures,验证每项只按版本化规则得到 FORMAT-017 的一个精确值并匹配主体;一个旧值可映射多个当前类型、只有本地化显示名称或无法区分直接归类与分类删除派生迁移时,验证拒绝而不猜测。
- 永久清理当前数据库中的一个 fixture 任务后重新导入仍含该任务的有效历史 fixture,验证兼容迁移不因后来清理拒绝或删除记录,结果继续进入完整覆盖流程。
- 使用含旧版本地化系统值和中英混合用户原文的历史 fixture,验证可判别系统值迁移为稳定语义码、用户原文逐字保留;构造无法判别的旧值时验证写入前拒绝而非猜测翻译。
- 使用一个按其原版本合法但不符合当前 UUID、`CategoryRef` 或时间表示的历史 fixture,验证先按原 schema 接受、再在隔离区无歧义迁移并通过当前校验;把身份映射、收件箱语义或时间瞬间改成无法确定时,验证拒绝且不改写当前数据库或原文件。
- v1 首发 fixture 必须覆盖小写 UUID v4、Inbox 与 custom 两种 `CategoryRef` 以及所有时间字段的 UTC 三位毫秒表示;反例 fixture 至少覆盖大写或非 v4 UUID、字符串或 `null` 收件箱、时区偏移、缺少毫秒、六位小数、数字时间戳和无效公历日期。
