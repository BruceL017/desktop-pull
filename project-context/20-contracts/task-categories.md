# 任务分类契约(Task Category Contract)

## 强制规则

### CATEGORY-001 · 单归属

每个活动任务必须且只能在 `taskOrderByCategory` 中恰好出现一次,由所在分组表达唯一当前分类。任务自身不得重复保存分类;移动到另一分类时必须把同一任务 ID 从原分组移入目标分组,不得复制出第二份归属。垃圾箱任务不得出现在任何活动分类分组;其当前垃圾箱展示与恢复读取的删除时分类只由 FORMAT-014 的 `categorySnapshotAtDeletion` 表达。FORMAT-027 另冻结同值的不可变删除历史分类快照,FORMAT-028 则冻结恢复插入完成后的实际目标分类;两者都只供审计,不构成当前归属或任何恢复来源。FORMAT-029 分类创建事件、FORMAT-031 分类排序位置与 FORMAT-032 分类删除计数同样只供历史审计;当前分类集合、任务归属与 `categoryOrder` 必须从当前记录读取,不得由分类历史主体、空详情、前后位置或发生时数量重建。

### CATEGORY-002 · 固定收件箱

系统必须始终提供具有稳定系统身份的固定收件箱分类,简体中文显示“收件箱”,英文显示 `Inbox`。任务归属、历史和备份必须引用该稳定身份,不得把任一语言的显示名称当作分类身份。用户新增任务且未主动选择自定义分类时,任务必须保存到该系统分类。

### CATEGORY-003 · 自定义分类

用户必须能创建自定义分类,并把任务从当前分类移动到任一现有自定义分类或收件箱。

每个自定义分类必须在创建事务中取得符合 `backup-format.md` FORMAT-011 的规范小写 UUID v4,并以该不可变标识贯穿当前状态、分类顺序、任务归属、历史和完整备份;重命名、排序、删除前快照、导出或导入不得重新映射。固定收件箱使用独立系统身份,不得占用或伪装成自定义分类 UUID。

### CATEGORY-004 · 无多分类与标签

第一版不得让一个任务同时引用多个分类,也不得用标签模拟多分类归属。

### CATEGORY-005 · 删除分类不删除任务

删除仍含任务的自定义分类时,必须先把其中全部任务作为一个连续分组追加到收件箱末尾,保持这些任务在原分类中的相对顺序,再删除该分类。不得把这些任务删除或移入垃圾箱。

“连续分组”以操作前来源分类的权威总顺序为准,即使其中混合 `open` 与 `completed` 也不得按状态拆批或重排。每个迁移任务的 FORMAT-026 `source.position` 必须在整批移动前从来源总顺序的同状态子序列计算,`targetPosition` 必须在完整批次追加后从最终收件箱总顺序的同状态子序列计算;不得记录逐项插入时的中间目标位置。

### CATEGORY-006 · 分类删除历史

成功删除自定义分类时,必须追加且只追加一条以该分类为主体、精确符合 FORMAT-032 的 `category.deleted(eventOrder = 0)`:公共主体保存分类不可变标识与事件发生时名称,`details` 必须且只能是 `{ affectedTaskCount }`,其中计数是操作被工作状态接受时该分类活动权威顺序的长度,也是本次实际迁入收件箱的任务数。未完成与已完成都计入,已经在垃圾箱、物理残留的到期任务、历史旧归属和分类入口草稿不计入;空活动分类保存 `0`。每个实际迁移任务必须另行追加一条以该任务为主体、精确符合 FORMAT-026 的 `task.moved_to_inbox_by_category_deletion`;根部只保存一次不变状态,`source` 保存与分类事件主体一致的被删 Custom 快照及整批前位置,`targetPosition` 保存整批完成后的最终 Inbox 位置,不得另存固定目标快照。正常 N 项删除时这些任务事件与分类事件共享操作,按来源权威总顺序使用 `eventOrder = 1...N`;不得退化为普通 `task.category_changed`。

FORMAT-032 不得保存任务标识、标题、内容或数组,也不得保存按状态拆分计数、分类身份副本、Inbox 快照、位置、草稿、确认或界面来源。计数在操作接受时与迁移批次一起冻结;待保存重试不得按持久化旧状态或后来状态重算。以后永久清理迁移任务可以删除其 FORMAT-026 主体事件并留下顺序缺口,但不得减少或移除分类删除事件中的原始 `affectedTaskCount`。

### CATEGORY-007 · 快速新增目标唯一

全局快速新增创建的任务必须只属于收件箱。从某一分类标题发起的快速新增必须只属于该分类,不得再弹出分类选择器或同时复制到收件箱。

### CATEGORY-008 · 自定义分类在创建时可选

任务创建流程不得要求用户选择自定义分类。用户未从某个自定义分类上下文发起创建时,任务必须立即进入收件箱;不得因未选择分类而阻止创建,也不得保存为零分类或 `null` 分类。

活动任务创建后必须能随时把唯一归属改为任一已有自定义分类或收件箱。用户也必须能先新建自定义分类,再把既有活动任务归入其中。除 CATEGORY-006 的分类删除派生迁移外,每次实际归属变化必须更新同一任务而非复制任务,并追加且只追加一条精确符合 FORMAT-025 的 `task.category_changed`;根部只保存一次不变状态,来源与目标分别冻结发生时分类及移出前、插入后位置。跨分类拖拽和各选择器入口使用同一类型且不保存界面来源。来源与目标分类身份必须不同;选择当前分类不形成归属变化。

### CATEGORY-009 · 创建后直接改分类

桌面端和移动端都必须提供两种创建后改分类的路径:按 `drag-interaction.md` 把整条任务跨分类拖到当前完成状态的精确位置,或从任务行操作菜单的“移动到…”以及任务编辑器的分类字段打开同一个单选分类选择器。两条路径都必须保持任务完成状态。选择器必须包含收件箱、全部已有自定义分类和“新建分类”操作。

选择另一已有分类后必须保持任务当前完成状态,把同一任务插入目标分类对应完成状态序列的顶部,关闭选择器并记录一次 FORMAT-025 `task.category_changed`,不得再打开页面或要求确认。其 `source.position` 必须冻结移出前同状态直接邻居,`target.position` 必须以前侧 `start` 和操作后实际首个邻居或 `end` 表达。该插入不得改变目标分类其他任务的相对顺序。选择当前分类属于无变化操作,不得借此把任务移到当前状态序列顶部,也不得推进时间、历史、操作顺序或待保存数量。任务行操作菜单、分类选择器及其输入控件必须与任务行点击和拖拽命中隔离。

选择“新建分类”后,必须在当前选择器内显示单行名称输入,不得跳转到独立分类管理页。成功提交必须在同一个原子事务中创建分类、保持任务完成状态并把当前任务归入新分类对应状态序列的顶部,再依次追加一条 `eventOrder = 0` 且 `details` 精确为 FORMAT-029 `{}` 的分类主体 `category.created` 和一条 `eventOrder = 1` 且精确符合 FORMAT-025 的任务主体 `task.category_changed`,成功后关闭选择器。任务事件的 `target.categorySnapshot` 必须与新分类事件主体的 ID 和发生时名称逐字一致,目标位置必须为 `start / end`;任务移动结果不得复制进分类空详情,两条详情都不得保存选择器或新建分类来源。任一步失败时不得留下新分类、任务归属变化或部分历史。

主清单已经通过分类分组表达任务归属,因此第一版不得在每条任务行重复显示分类标签。

### CATEGORY-010 · 主清单内联新建空分类

主任务清单必须在最后一个分类分组下方常驻一行明确标注的“新建分类”入口。触发后,该入口必须在原位置切换为单行分类名称输入并立即获得焦点;移动端必须同时打开软键盘。不得打开弹窗、编辑器或独立分类管理页面。

桌面端必须支持按一次 `Enter` 提交,移动端必须把软键盘动作键配置为“添加”或等价提交动作。提交成功后,新建空分类必须追加到现有自定义分类末尾,并在同一原子事务中追加且只追加一条 FORMAT-029 `category.created(eventOrder = 0, details = {})`;事件主体 ID / 名称必须与新分类记录逐字一致。用户仍停留在主任务清单,不得自动创建任务、改变任务归属或自动打开任务创建器。

该入口必须与全局任务快速新增入口在文案和命中区域上明确分离,不得让一次操作同时进入任务创建和分类创建状态。

### CATEGORY-011 · 分类名称不得重复

主清单内联入口和任务分类选择器内的“新建分类”必须使用同一套名称校验。提交时必须先去除名称首尾空白;处理后的名称不得为空,不得与任一已有自定义分类同名,也不得使用系统保留名称“收件箱”或 `Inbox`。`Inbox` 的保留名比较必须对 ASCII 字母大小写不敏感,因此 `inbox`、`INBOX` 和其他大小写组合都无效;该规则不随当前界面语言变化。成功创建时必须保存处理后的名称。重命名复用本规则时,现有分类自身不参与真实新名称的重复比较:处理后的值通过非空与保留名称校验后必须先与自身当前名称逐字比较,相同即无变化;只有不同时才与其他现存自定义分类比较唯一性。

校验失败时必须保留用户当前输入并在输入位置就地说明原因,不得弹出阻断式对话框。不得创建分类、追加历史或改变任何任务归属;若入口来自某个任务的分类选择器,该任务必须继续留在原分类。

### CATEGORY-012 · 删除自定义分类必须确认

删除任一自定义分类前都必须显示一次阻断式确认弹窗,无论该分类是否为空。弹窗必须明确显示分类名称;分类非空时还必须显示其中任务数量,并明确说明这些任务将移动到收件箱且不会进入垃圾箱。

打开确认时必须读取该分类标题语义入口在当前逻辑状态中的 FORMAT-015 草稿。没有草稿时,确认按钮必须明确标注“删除分类”。存在草稿时,弹窗还必须明确说明该未提交草稿将从当前数据库丢弃且不进入垃圾箱,并显示可识别的当前原文预览;纯空白草稿必须显示明确的“仅含空白”语义,不得呈现为空白区域。此时破坏性按钮必须明确标注“删除分类并丢弃草稿”。

取消、关闭弹窗或离开确认流程时,不得删除分类、移动任务、删除草稿或追加历史。分类删除不要求用户输入分类名称,不增加第二个确认弹窗,也不要求连续确认两次。破坏性按钮的同一次用户意图最多只能被接受一次;首次接受后必须阻止重复派发形成第二项分类删除操作、历史或 `operationSequence`。

执行破坏性按钮前,必须再次读取同一语义入口的当前逻辑草稿,并从这次复核到事务提交完成为该入口保持同一变更栅栏。确认时看到的草稿已经换成另一 `generation` 时,本次删除不得进入工作状态、不得占用操作顺序或写历史;确认框必须以最新草稿重新展示并要求用户重新确认。确认时草稿已经不存在时可以按无草稿结果继续,不得虚构草稿删除。若确认时没有草稿但复核时出现草稿,同样必须展示该草稿并重新确认。

删除操作被当前工作状态接受后,必须冻结分类 ID 及复核得到的草稿期望状态:无草稿,或被确认草稿的 `entry + generation`。同一个原子业务事务必须再次断言该分类入口没有出现未确认的逻辑代次,删除分类、按 CATEGORY-005 移动其中任务、按 CATEGORY-006 追加对应历史,并清除该入口已由确认授权消费的持久记录。持久记录与已确认代次相同时直接删除;数据库旧代次已被确认时的最新内存代次明确覆盖时,旧记录只是同一逻辑入口的陈旧物理影子,也必须在该事务清除。若事务内出现未经确认的新逻辑代次、无法证明为陈旧影子的不同代次,或无草稿期望下出现任何草稿,必须把它视为前置条件失败并整笔回滚,不得把条件删除零行当作分类删除成功;界面重新读取当前逻辑草稿并要求确认。确认草稿只存在于内存且数据库没有任何该入口记录时,零行本身不是失败,但入口变更栅栏仍必须保证没有新代次出现。事务成功后不得留下引用已删除分类的该入口记录。任一步失败时持久化分类、任务归属、顺序、历史和草稿必须全部保持事务前状态。已接受操作的工作状态、补写和应急备份继续遵守 `degraded-availability.md`。

分类删除成功或进入待保存工作状态时,还必须使被确认代次的内存快照、自动重试与延迟回调失效。草稿不得迁移到全局入口、收件箱分类入口或其他分类,不得自动创建任务,也不得产生独立历史事件、消耗额外 `operationSequence` 或进入垃圾箱。此前已经存在的分类删除事件和逐任务移动事件仍按 CATEGORY-006 保留。

### CATEGORY-013 · 自定义分类原地重命名

自定义分类标题的操作菜单必须提供“重命名”。触发后,分类标题必须在原位置切换为单行名称输入;一次明确提交后立即保存,不得打开独立页面或要求确认。固定收件箱不得重命名。

重命名必须沿用 CATEGORY-011 的处理顺序:先去除首尾空白并校验非空与保留名称,再与自身当前名称逐字比较;相同属于无变化操作,不得改变分类、历史、操作顺序或待保存数量。只有真实变化的候选名称才与其他现存自定义分类比较唯一性;校验失败时保留输入并就地提示,不得改变分类或历史。

成功重命名必须保持分类不可变标识、`categoryOrder`、`taskOrderByCategory`、所含任务及其归属、顺序、状态、内容、优先级、生命周期与时间不变,并在同一个原子事务中更新分类名称、推进操作顺序和追加且只追加一条 FORMAT-030 `category.renamed(eventOrder = 0)`。事件公共 `subject.categoryId` 必须等于当前分类 ID,`subject.name` 必须等于处理后新名称,`details` 必须精确为 `{ beforeName }` 且保存更新前名称;旧、新名称必须不同。不得追加任务事件,任一步失败时分类名称、历史与顺序进度必须全部保持原样。

既有历史摘要必须保留各事件发生时记录的分类名称;本次改名从 `details.beforeName` 到 `subject.name` 呈现,两个用户名称不随语言切换翻译。历史筛选必须通过公共主体的分类不可变标识同时找到改名前后的分类管理事件与按 `history-interface.md` 归入该分类的任务事件,搜索可以用本事件自身的旧名或新名命中;不得查询当前分类名称补值或重放历史重建当前名称。

### CATEGORY-014 · 自定义分类直接拖拽排序

收件箱必须固定在分类列表第一位且不得移动。用户必须能从自定义分类标题的非控件区域直接拖拽整个分类分组,调整自定义分类之间的持久顺序;不得要求专用拖拽手柄或先进入排序模式。

分类标题拖拽必须沿用 `drag-interaction.md` 的桌面约 `6px` 位移阈值、移动端约 `200ms` 长按仲裁、分类间精确插入标记、边缘自动滚动、取消路径和原生手势竞争抑制。有效落点只能位于自定义分类序列,收件箱不得出现可将其移动的插入标记。折叠控件、分类快速新增和分类操作菜单等明确控件不得发起分类拖拽。

一次成功排序只能改变被移动分类 ID 在自定义 `categoryOrder` 中的位置,不得改变分类记录或名称、`taskOrderByCategory`、任何任务归属、分类内顺序或任务字段。分类顺序、操作顺序进度和唯一一条 FORMAT-031 `category.reordered(eventOrder = 0)` 必须原子提交;公共主体保存被移动分类发生时 ID / 名称,`details` 必须精确为 `{ beforePosition, afterPosition }`,每个位置精确含 `previousCategory` / `nextCategory`。前侧只接受 Custom 分类发生时 `{ kind: "category", categoryId, name }` 或自定义序列 `start`,后侧只接受同一分类分支或 `end`;收件箱、`unavailable`、绝对位置和内部排序值都不允许。

`beforePosition` 必须取主体从操作前顺序移除前的直接邻居,`afterPosition` 必须取主体插入操作后顺序后的直接邻居。每个位置内双分类邻居 ID 不同且均非主体;跨位置允许相邻移动复用同一分类,但同一 ID 的发生时名称必须一致。放回原位、取消、无有效落点或只有一个自定义分类不得改变顺序、历史、操作顺序或待保存数量。主体或邻居以后改名、排序或删除不得回写旧事件;当前分类顺序不得从 FORMAT-031 重放。

### CATEGORY-015 · 选择器移动反馈保持当前上下文

从任务行“移动到…”发起的分类变化成功持久化后,用户必须留在当前任务清单滚动位置,源位置的任务行消失,并显示短暂、非阻断且无需关闭的“已移到「目标分类」”反馈和“查看任务”操作。应用不得自动滚动或跳到目标分类。

用户选择“查看任务”时,才按 `navigation.md` 展开目标分类及必要的“已完成”区域,滚动并短暂高亮目标任务;不得打开任务编辑器、聚焦输入或弹出移动端键盘。

从任务编辑器分类字段发起时,选择器必须关闭,但桌面右侧编辑面板或移动端全屏编辑页必须保持打开,分类字段立即显示新归属。该路径不需要重复显示任务行移动反馈。若分类变化只进入待保存队列,两条路径都不得显示“已移到”成功文案,必须继续使用 `degraded-availability.md` 的待保存状态。

### CATEGORY-016 · 分类命名只由明确提交创建

主清单与任务分类选择器中的新建分类输入必须使用同一套提交与取消状态机。只有桌面端独立的一次 `Enter`、移动端软键盘“添加”动作或输入末尾的确认图标可以提交;三种入口必须汇入同一条幂等提交路径,一次用户意图最多创建一个分类。输入法仍在组合文字时按下 `Enter` 只能确认候选字,不得提交分类;组合结束后的下一次独立 `Enter` 才可提交。

确认图标的明确提交意图必须优先于其造成的焦点离开,不得先按失焦规则取消。除此之外,输入框失焦、点击外部、按 `Esc` 或触发取消图标都必须退出创建状态并清空未提交名称,不得创建分类、追加历史、要求确认或改变任务归属。若校验失败,则不得退出:必须保留原文字、焦点和移动端键盘并就地说明原因,让用户直接修正。

主清单创建成功后必须恢复“新建分类”入口并保持用户位于主清单当前位置。分类选择器创建成功时必须按 CATEGORY-009 原子创建并移动任务,随后关闭选择器。未提交分类名称只属于当前输入状态,不得写入 `IndexedDB`、待保存队列或完整备份;刷新、重载或重开应用后不恢复。

## 验收 Gate

- 不选择分类直接新增任务,任务只出现在收件箱。
- 切换简体中文与英文后验证固定收件箱分别显示“收件箱”与 `Inbox`,同一批任务的分类归属标识不变,数据库与备份没有用任一显示名称代替系统身份。
- 新建自定义分类后,任务可以移动到该分类。
- 任务从分类 A 移动到分类 B 后,只属于分类 B,且分类 A 不再包含该任务。
- 任一活动任务都不存在零个或多个当前分类,任一垃圾箱任务都不存在活动分类位置;两者不得同时占用 `taskOrderByCategory`。
- 恢复任务后验证当前分类只由 `taskOrderByCategory` 表达,FORMAT-028 的实际目标分类只供历史筛选与呈现;随后移动、删除或再次恢复时,不得读取旧 FORMAT-028 作为当前归属或恢复输入。
- 删除含多个任务的自定义分类后,这些任务按原相对顺序连续出现在收件箱末尾,且没有任务进入垃圾箱。
- 分类删除以一条 FORMAT-032 `category.deleted` 出现,`affectedTaskCount` 等于接受时活动来源列表长度;所有实际受影响任务的归属变化分别以 FORMAT-026 `task.moved_to_inbox_by_category_deletion` 出现,两者共享操作并能在历史时间线中查到。
- 删除来源总顺序为 `A(open), B(completed), C(open)` 的分类,验证收件箱最终仍连续追加 `A, B, C`,任务事件也按 A/B/C 分配操作内顺序;FORMAT-026 的位置分别从整批前来源与整批后最终 Inbox 的同状态子序列计算,不会按状态改成 A/C/B 或保存逐项中间态。
- 让同状态批次任务在迁移前后继续互为邻居,验证同一邻居可在 FORMAT-026 的 `source.position` 与 `targetPosition` 同方向重复且每个位置内部仍不自引或双侧同 ID;来源快照必须与 `category.deleted.subject` 一致,详情不得另存 Inbox 快照或批次任务数组。
- 分别从全局入口和自定义分类标题快速新增,验证任务只进入收件箱和对应自定义分类。
- 不选择自定义分类直接创建任务,验证创建不被阻止且活动任务唯一归属为收件箱,不存在零分类或空分类值;软删除后该 ID 从全部活动分类分组移除。
- 创建任务后依次把它移入已有分类、新建分类后移入、再移回收件箱,验证始终只有一条任务和一个分类归属,每次实际变化各有一条历史。
- 分别从任务行“移动到…”和任务编辑器分类字段选择已有分类,验证两处使用同一组选项、选择后立即移动且不要求确认。
- 分别把未完成和已完成任务通过选择器移动到非空分类,验证任务位于目标分类对应状态序列顶部,状态保持且其他任务相对顺序不变;移动历史记录目标顶部边界。
- 选择任务当前分类,验证任务不会借此移动到顶部,状态、归属、顺序和历史均不变化。
- 把来源同状态序列唯一任务移入同状态区为空的另一分类,验证 FORMAT-025 的来源与目标位置都为 `start / end` 仍合法,真实性只由不同分类引用证明;相同分类引用即使快照名称不同也必须拒绝。
- 分别通过拖拽、任务行选择器和编辑器选择器移动任务,验证 FORMAT-025 的根字段都精确为 `{ status, source, target }`,每侧只含分类快照与严格位置;拖拽保留精确目标落点,选择器目标前侧固定为 `start`,任何详情都不保存入口。

- 在选择器内新建分类并归入既有任务,验证同一操作的 FORMAT-029 `category.created` 为 `eventOrder = 0`、FORMAT-025 `task.category_changed` 为 `eventOrder = 1`,目标快照 ID/名称与分类事件主体一致且目标位置为 `start / end`。
