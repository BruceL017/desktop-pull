# 状态与历史一致性契约(State and History Consistency Contract)

## 强制规则

### CONSISTENCY-001 · 当前状态是读取源

健康态下,主任务页、编辑器和垃圾箱必须从当前任务、分类和顺序记录读取产品状态。可写降级态只允许按 `degraded-availability.md` 在该持久化状态上叠加有序待保存变更。不得要求重放完整历史才能展示当前清单。

### CONSISTENCY-002 · 成功变更原子落盘

每次持久化成功的任务新增、编辑、状态切换、优先级修改、分类变化、拖拽、软删除或恢复,必须在同一个原子事务中更新当前状态并为每项实际任务变化追加且只追加一条 FORMAT-017 任务主体事件。分类创建、重命名、排序或删除必须以相同规则追加对应 FORMAT-017 分类主体事件。仅进入待保存队列不属于持久化成功。

同一正式操作产生的全部事件必须严格符合 `backup-format.md` FORMAT-016,使用 FORMAT-017 与实际变化匹配的精确 `eventType`,并按 FORMAT-018 同时冻结对应事件专属最小 `details`;`task.content_changed` 还必须冻结 FORMAT-019 的精确形状,且当前状态中保存后的标题必须与事件 `subject.title` 逐字相同;`task.completed` 与 `task.reopened` 必须分别对应真实的状态方向并冻结 FORMAT-020 精确详情;`task.created` 必须冻结 FORMAT-022 的精确 `{ categorySnapshot, position }`,其分类、创建后未完成序列位置与任务创建同时来自同一原子工作状态;`task.priority_changed` 必须冻结 FORMAT-023 的精确 `{ categorySnapshot, beforePriority, afterPriority }`,`beforePriority` 与 `afterPriority` 必须不同,当前任务新值必须等于 `afterPriority` 且顺序不变;`task.reordered` 必须冻结 FORMAT-024 的精确 `{ categorySnapshot, status, beforePosition, afterPosition }`,分类与状态保持不变,正常生产的前后位置真实不同且只改变主体顺序;`task.category_changed` 必须冻结 FORMAT-025 的精确 `{ status, source, target }`,`source` 与 `target` 都精确为 `{ categorySnapshot, position }`,两侧分类引用必须不同,根 `status` 在操作中保持不变,来源位置冻结主体移除前邻居,目标位置冻结主体插入后邻居。FORMAT-025 正常生产的四个可识别邻居 ID 必须全局两两不同且都非主体,不得生成 `unavailable`;来源仅有主体且目标对应状态区为空时,两侧位置都为 `start / end` 仍是合法跨分类变化。`task.moved_to_inbox_by_category_deletion` 必须冻结 FORMAT-026 的精确 `{ status, source, targetPosition }`,`source` 精确为 `{ categorySnapshot, position }` 且 Custom 快照与同操作分类删除主体一致,根状态保持不变,来源位置取整批前同状态邻居,目标位置取整批后最终 Inbox 同状态邻居。FORMAT-026 每个位置内双任务邻居必须不同且非主体,但同一批次邻居可在来源和目标同方向重复,不得套用 FORMAT-025 的跨侧互异规则;正常生产不得生成 `unavailable`。`task.trashed` 必须冻结 FORMAT-027 的精确 `{ categorySnapshot, status, position }`:分类和状态取主体移出活动顺序前事实,位置取该分类同状态直接邻居,正常双任务邻居不同且非主体。详情分类必须与同事务 FORMAT-014 `categorySnapshotAtDeletion` 逐字段同值,详情状态等于任务公共状态,带标题位置与无标题恢复锚点表达同一删除现场但维持两个严格 schema;`updatedAt = deletedAt = occurredAt`,到期时间恰晚 30 天。`task.restored` 必须冻结 FORMAT-028 的精确 `{ categorySnapshot, status, position }`:分类和位置取主体恢复插入完成后的实际结果,状态等于恢复后保持不变的任务公共状态;原分类存在时保存同一 ID 与恢复时当前名称,原分类已删除时保存固定 Inbox,正常双任务邻居不同且非主体。`category.created` 必须冻结 FORMAT-029 的精确 `{}`;分类不可变 ID 与创建时用户原文名称只存在于公共 `subject`,不得把分类记录、位置、入口或关联任务结果复制进详情。`category.renamed` 必须冻结 FORMAT-030 的精确 `{ beforeName }`;公共 `subject.name` 是处理后新名称且为唯一新值来源,旧名称只在 `details.beforeName`,两者必须不同。`category.reordered` 必须冻结 FORMAT-031 的精确 `{ beforePosition, afterPosition }`:两个位置都精确包含方向严格的 `previousCategory` / `nextCategory`,只接受 Custom 分类发生时 ID / 名称或自定义序列 `start` / `end`,禁止 Inbox 与 `unavailable`;每个位置内双分类邻居不同且非主体,跨位置允许同一邻居复用但名称必须一致。上述单分类分支的 `categorySnapshot` 必须从操作接受时任务归属生成,FORMAT-025 则必须同时冻结该时刻来源和提交后的目标分类事实,FORMAT-026 的固定目标收件箱由事件类型表达而不另存快照,FORMAT-027 的分类只用于删除审计且不得成为恢复来源,FORMAT-028 的分类只记录实际恢复目标且同样不得成为之后恢复或排序来源。任何事件 schema 已声明的历史任务邻居字段必须从同一操作接受时工作状态冻结 FORMAT-021:前侧无邻居使用 `start`,后侧无邻居使用 `end`,存在邻居使用精确 `{ kind, taskId, title }`,其中标题逐字保存发生时原文;正常业务生产者不得直接生成 `unavailable`。邻居后来改标题、移动、换分类、完成或软删除不得改写旧快照,之后的当前顺序和标题也不得参与补算。它们共享 `history-retention.md` 冻结的 `occurredAt` 与 `operationSequence`,并各自保存唯一 `eventOrder`。`(operationSequence, eventOrder)` 是事件唯一稳定逻辑键,不得建立独立事件 ID。当前状态、全部对应事件和已使用操作顺序的持久进度必须共享同一个事务;不得提交事件却让后续操作重用其 `operationSequence`,也不得在事务提交时从后来状态重新生成 `details`、重复生成标题新值或按后来分类改写快照。FORMAT-022 已锁定创建分支,FORMAT-023 已锁定优先级分支,FORMAT-024 已锁定组内排序分支,FORMAT-025 已锁定主动跨分类分支,FORMAT-026 已锁定分类删除派生迁移分支,FORMAT-027 已锁定软删除分支,FORMAT-028 已锁定恢复分支,FORMAT-029 已锁定分类创建分支,FORMAT-030 已锁定分类重命名分支,FORMAT-031 已锁定分类排序分支,FORMAT-032 已锁定分类删除计数分支且 FORMAT-021 只锁定可复用任务联合;14 个事件详情分支与 fixtures 已全部闭合。

`category.deleted` 还必须冻结 FORMAT-032 精确 `{ affectedTaskCount }`;计数取删除操作被工作状态接受前来源分类在 `taskOrderByCategory` 中的活动任务列表长度,包括两种完成状态但排除垃圾箱任务、到期物理残留、历史旧归属和草稿。该值与完整 FORMAT-026 批次、时间、顺序及删除后的工作状态一次冻结,不得在提交、重试或应急物化时重新读取持久化分类或后来状态。

同一事务还必须把每个直接发生业务状态变化的任务 `updatedAt` 设置为该操作同一个原始 `occurredAt`;创建时 `createdAt` 与 `updatedAt` 同值,之后 `createdAt` 不可改变。分类删除迁移的每个任务都直接变化,但单任务插入或移动导致的周围任务被动位移不属于周围任务变化。待保存补写不得用事务提交时间覆盖该值。

从主清单内联入口创建空分类时,分类记录、追加到自定义 `categoryOrder` 末尾的顺序变化、操作顺序进度和唯一一条 FORMAT-029 `category.created(eventOrder = 0, details = {})` 必须共享一个原子事务。事件主体 ID / 名称必须与新分类记录逐字一致;不得创建任务、改变任何任务归属或另写任务事件。任一步失败时不得留下分类、顺序变化、历史或已消耗顺序。

重命名自定义分类时,必须先按 CATEGORY-011 处理并验证提交值。处理后名称与当前名称逐字相同不构成正式操作。真实变化必须在一个原子事务中把分类记录名称从 `details.beforeName` 更新为公共 `subject.name`,推进操作顺序进度并追加且只追加一条 FORMAT-030 `category.renamed(eventOrder = 0)`。事件主体分类 ID 必须与当前记录相同,旧、新名称必须不同;`categoryOrder`、`taskOrderByCategory`、全部任务及其归属、顺序、状态、内容、优先级、生命周期和时间必须保持不变,不得产生任务事件。任一步失败时名称、历史和顺序进度全部保持事务前状态。

排序自定义分类时,必须从同一接受时工作状态冻结 FORMAT-031 `beforePosition`,只在有效落点形成的操作后 `categoryOrder` 冻结 `afterPosition`。真实变化必须在一个原子事务中只改变公共主体分类 ID 在 `categoryOrder` 中的位置、推进操作顺序进度并追加且只追加一条 `category.reordered(eventOrder = 0)`;分类记录和名称、`taskOrderByCategory`、全部任务及任务时间保持不变。相邻移动跨前后位置复用同一邻居合法,不得误套任务主动跨分类的四槽互异规则。原位、取消、无效落点或只有一个 Custom 不构成正式操作;任一顺序、历史或顺序进度写入失败时全部保持事务前状态。

软删除必须在一个原子事务中冻结移出前 FORMAT-027,从活动顺序移除且只移除主体,建立 FORMAT-014 垃圾箱生命周期,更新主体时间并追加且只追加一条 `task.trashed`;不得为位置后果再写移动事件。若确认前有 TRASH-004 有效内容编辑,内容变化与删除必须作为两个有序操作分别冻结和提交,删除事件主体标题取前序编辑后的有效标题。取消确认、确认失效、重复删除或主体已非活动状态都不构成正式操作,不得改变状态、时间、历史或顺序进度。恢复后旧 FORMAT-027 仍为只读事实;恢复与再次删除不得回写它,再次删除必须冻结新的现场。恢复落位只读当前 FORMAT-014 生命周期锚点,不得读取 FORMAT-027 或移动其他任务。

恢复必须在一个原子事务中只读取当前 FORMAT-014 生命周期并按 RESTORE-002 计算实际落位,把生命周期整体替换为 active,把主体恰好一次插入权威顺序,设置主体 `updatedAt = occurredAt` 并追加且只追加一条 FORMAT-028 `task.restored`;不得另写移动事件。FORMAT-028 的分类、状态与位置必须对应事务完成后的实际活动状态:原分类存在时使用同一 ID 和恢复时当前名称,原分类不存在时使用 Inbox,位置取插入完成后的同状态直接邻居。任务公共内容、优先级、状态、`createdAt`、现有任务相对顺序及其时间保持不变。FORMAT-027 删除现场与 FORMAT-028 恢复结果互不复制、互不改写,两种历史都不得成为恢复或当前顺序读取源。

分类删除必须在一个原子事务中删除分类、把接受前来源权威活动总顺序作为连续批次追加到收件箱、追加一条 FORMAT-032 `category.deleted(eventOrder = 0, details = { affectedTaskCount: N })`,并为这 N 个实际迁移任务各追加一条精确符合 FORMAT-026 的 `task.moved_to_inbox_by_category_deletion(eventOrder = 1...N)`;两类事件共享操作,任务事件按操作前来源权威总顺序跟随且目标固定为收件箱。每条来源位置从整批前状态冻结,目标位置从整批完成后的最终状态冻结,不得按状态拆批或保存逐项中间态;最终位置可以引用更大 `eventOrder` 的批次任务。N 为 `0` 时仍写分类事件但不写任务事件。分类及其顺序分组、任务归属和权威顺序、每个迁移主体 `updatedAt`、全部事件和操作顺序进度要么一起提交,要么全部保持原样。若 CATEGORY-012 的同一次确认还明确接受丢弃分类标题入口草稿,该事务还必须条件删除与确认快照 `entry`、`generation` 都匹配的草稿,但草稿不进入 N。主体类型与字段必须遵守 `history-retention.md`,不得让分类事件伪造任务主体、让任务迁移只存在于分类汇总事件中、把派生迁移退化为普通 `task.category_changed`,或为草稿丢弃生成独立事件与操作顺序。

选择器内新建分类并归入当前任务时,分类创建、主体分类与顺序变化、主体 `updatedAt`、操作顺序进度及两条历史必须共享一个原子事务和同一 `occurredAt` / `operationSequence`:`category.created` 固定为 `eventOrder = 0` 且 `details` 精确符合 FORMAT-029 `{}`,`task.category_changed` 固定为 `eventOrder = 1` 并精确符合 FORMAT-025,其 `target.categorySnapshot` 的自定义分类 ID / 名称必须与分类事件主体逐字一致。任务移动结果只存在于任务事件;任一步失败时不得留下空分类、已移动任务、单边历史或已消耗顺序。

### CONSISTENCY-003 · 失败不留半成品

当前状态更新或历史追加任一失败时,整个持久化事务必须失败。数据库不得出现状态已改变但缺少历史,或历史已追加但状态未改变的情况;当前会话可按 `degraded-availability.md` 保留明确标记的待保存变更。

### CONSISTENCY-004 · 无变化不写历史

未产生实际状态变化的操作不得修改当前状态、推进任何任务的 `updatedAt` 或追加历史事件。

### CONSISTENCY-005 · 永久清理原子删除

永久清理任务时,任务内容及以该任务为主体的全部历史必须在同一个原子事务中删除,保留事件中所有 schema 已声明且语义上指向目标的 FORMAT-021 `task` 分支必须整体替换为精确 `{ "kind": "unavailable" }`,同时按 FORMAT-014 独立去身份化对应恢复锚点。历史替换必须同时移除目标 `taskId` 与发生时 `title`,不得只扫描移动事件、改变无关边界或把 FORMAT-021 带标题分支写入恢复锚点。清空垃圾箱时,冻结目标集合中执行时仍在垃圾箱的全部任务、其任务主体历史和全部必要的保留引用替换必须共享一个原子事务。该维护事务不得推进任何保留任务的 `updatedAt`。任一删除、扫描、替换或提交失败时不得留下部分任务、部分任务内容、部分任务主体历史或半更新引用;独立分类主体事件与无关历史不得加入删除集合。

### CONSISTENCY-006 · 不采用事件重放

第一版不得把历史事件作为重建当前任务清单所必需的唯一数据源,也不得在启动时通过重放全部历史生成当前状态。

### CONSISTENCY-007 · 待保存历史不是已提交历史

待保存变更的历史意图可以显示为待保存,但在对应原子事务成功前不得混入已持久化历史或失去待保存标识。补写成功后必须只产生其原本定义的正式事件,并原样保留最初冻结的 `eventType`、FORMAT-018 `details`、`occurredAt`、`operationSequence` 与 `eventOrder`;创建还必须原样保留 FORMAT-022 的初始分类和嵌套位置,内容变化还必须原样保留保存后的 `subject.title` 和 FORMAT-019 分支,完成与重新打开还必须原样保留 FORMAT-020 分支,优先级变化还必须原样保留 FORMAT-023 的发生时分类与旧新值,组内排序还必须原样保留 FORMAT-024 的发生时分类、状态与移动前后位置,主动跨分类变化还必须原样保留 FORMAT-025 的根状态、来源与目标分类及两侧位置,分类删除派生迁移还必须原样保留 FORMAT-026 的根状态、来源整批前与最终 Inbox 位置及完整操作内顺序,软删除还必须原样保留 FORMAT-027 的删除时分类、状态、移出前位置、最新有效主体标题及与 FORMAT-014 生命周期同值关系,恢复还必须原样保留 FORMAT-028 的实际分类、状态与插入后位置,分类创建还必须原样保留 FORMAT-029 `{}` 及公共分类主体,分类重命名还必须原样保留 FORMAT-030 `{ beforeName }`、公共主体中的新名称和同一分类 ID,分类排序还必须原样保留 FORMAT-031 移动前后位置、公共主体及排序后的工作状态 `categoryOrder`,所有已声明历史任务邻居字段还必须原样保留 FORMAT-021 分支与发生时标题。不得按补写时间或后来当前状态重新分配、补字段或生成快照,也不得按后来分类、顺序、标题或当前收件箱尾部重算 `categorySnapshot` 或历史邻居;FORMAT-031 也不得按后来当前名称或 `categoryOrder` 重算。

待保存分类删除还必须原样保留 FORMAT-032 `affectedTaskCount`、公共分类主体、完整接受时来源批次和删除后的工作状态。前序待保存创建或移动已经进入工作状态时应计入 N;重试不得从仍未更新的持久化来源分类、后来 Inbox、剩余事件或最大 `eventOrder` 重算。

### CONSISTENCY-008 · 提交草稿原子消费

持久草稿成功提交为任务时,必须在同一个事务中创建任务、追加且只追加一条精确符合 FORMAT-022 的 `task.created` 并条件删除语义入口与 FORMAT-015 `generation` 都和提交快照匹配的草稿。创建详情从同一事务接受时的初始分类与插入完成后未完成序列位置生成,不得保存草稿入口、代次或提交幂等键。任一步失败时三者都不得提交。普通草稿编辑和明确清空不是任务变更,不得追加历史。

### CONSISTENCY-009 · 草稿消费必须匹配代次

草稿提交事务只能消费语义入口和 `generation` 都与其捕获快照匹配的草稿。若同一入口当前草稿已经进入更新代次,较早提交事务必须保留新草稿,同时仍原子创建较早任务及其历史。不得仅凭入口标识或仅凭代次无条件删除草稿。

### CONSISTENCY-010 · 核心写入必须来自活动窗口

每次核心状态与历史事务、草稿事务和永久清理事务都必须遵守 `single-active-window.md`:只有当前活动窗口可以发起,并且提交前仍须持有有效排他所有权。已释放或失去所有权窗口的自动保存、后台重试和延迟回调不得改变状态、草稿或历史。

### CONSISTENCY-011 · 分类删除按代次消费草稿

删除自定义分类的确认执行前必须重新读取该分类标题入口的逻辑草稿,并从最终复核到事务提交完成串行化该入口的代次变化。若 `generation` 已变化,或确认时无草稿而复核时出现草稿,本次删除尚未被接受,不得改变状态、占用 `operationSequence` 或写历史;确认框必须改为展示最新草稿并要求重新确认。若草稿已经消失,按无草稿的分类删除继续。

接受操作时必须冻结分类 ID 与复核得到的草稿期望状态:无草稿,或确认时的 `entry`、`generation`。健康态下,分类删除、任务迁移、既定分类与任务事件、操作顺序进度、草稿期望状态断言以及该逻辑入口持久记录的清除是一个原子业务事务。若确认的最新内存代次已经明确覆盖同入口旧持久代次,旧记录是陈旧物理影子并随事务清除;事务内出现未经确认的新逻辑代次或无法证明陈旧的不同代次时必须整笔回滚并重新确认,不得把条件删除零行当作成功。确认草稿只存在于内存且数据库没有该入口记录是允许的零行结果,前提是入口变更栅栏确认没有新代次。成功后该入口不得悬空存在。失败时全部保持原样。接受后还必须立即失效同一草稿代次的内存快照、自动重试和延迟回调,使其在事务成功或按 `degraded-availability.md` 进入待保存工作状态后都不能重新写回。草稿丢弃不迁移、不创建任务、不进垃圾箱,也不生成独立历史或额外操作顺序。同一次确认的重复派发必须幂等,最多接受一项正式操作。
