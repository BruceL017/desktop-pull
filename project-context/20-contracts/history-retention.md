# 历史、垃圾箱与清除契约

本契约中的“任务变更”均指用户已经提交的操作,不包含输入过程中的临时状态。

## 定义

- `deletedAt`:软删除操作被当前工作状态接受时冻结的 `occurredAt`,同时也是该任务新的 `updatedAt`;之后持久化补写不得改用提交成功时间。该值使用 `backup-format.md` FORMAT-011 的 UTC 固定毫秒精度表示。
- `expiresAt`:任务达到永久清理条件的时间,即 `deletedAt` 后 30 天,使用同一 UTC 固定毫秒精度表示。
- `categorySnapshotAtDeletion`:软删除操作被当前工作状态接受时所属分类的语义快照,使用 `backup-format.md` FORMAT-012 的 `CategorySnapshot`;自定义分类保存不可变标识与用户原文名称,固定收件箱保存稳定系统身份且不保存本地化名称。待保存补写不得按提交时分类重新生成。
- 可恢复任务:当前工作状态仍为软删除、当前时间尚未达到 `expiresAt`,且尚未接受恢复操作的任务。
- 待保存恢复:在 `expiresAt` 前已被工作状态接受、已经把任务移出垃圾箱,但对应原子事务尚未成功持久化的恢复操作。
- `subjectType`:历史事件主体判别,只能是 `task` 或 `category`。
- `subject`:由 `subjectType` 唯一判别的严格主体快照;任务分支只含 `taskId` 与发生时 `title`,分类分支只含 `categoryId` 与发生时 `name`。
- `eventType`:FORMAT-017 闭合枚举中的稳定、语言无关精确事件类型。
- `details`:FORMAT-018 定义的必填、非 `null` 事件专属最小严格对象;外层 `eventType` 是唯一事件判别,其中 `task.content_changed` 的精确分支由 FORMAT-019 锁定,`task.completed` 与 `task.reopened` 的精确分支由 FORMAT-020 锁定,任何事件专属字段需要保存前后任务邻居时复用 FORMAT-021,`task.created` 的精确分支由 FORMAT-022 锁定,`task.priority_changed` 的精确分支由 FORMAT-023 锁定,`task.reordered` 的精确分支由 FORMAT-024 锁定,`task.category_changed` 的精确分支由 FORMAT-025 锁定,`task.moved_to_inbox_by_category_deletion` 的精确分支由 FORMAT-026 锁定,`task.trashed` 的精确分支由 FORMAT-027 锁定,`task.restored` 的精确分支由 FORMAT-028 锁定,`category.created` 的精确空分支由 FORMAT-029 锁定,`category.renamed` 的精确分支由 FORMAT-030 锁定,`category.reordered` 的精确分支由 FORMAT-031 锁定,`category.deleted` 的精确计数分支由 FORMAT-032 锁定;14 个事件分支已全部闭合。
- `occurredAt`:一次正式操作被当前工作状态接受时冻结的用户操作时间,也是该操作产生事件的展示时间,使用 FORMAT-011 的 UTC 固定毫秒精度表示。
- `operationSequence`:按正式操作被接受的先后单调增加的稳定顺序号;同一操作产生的全部事件共享一个值。
- `eventOrder`:JSON 非负安全整数;同一操作从 `0` 开始分配且在该 `operationSequence` 内唯一,永久清理留下缺口后不得重编号。
- `lifecycle`:任务当前生命周期判别;活动任务精确为 `{ "kind": "active" }`,垃圾箱任务使用 `backup-format.md` FORMAT-014 的 `trashed` 结构。
- `previousTaskAnchor`:删除时同状态序列的前锚点,必须且只能是 FORMAT-014 的 `{ "kind": "task", "taskId": <任务 UUID> }`、`{ "kind": "start" }` 或 `{ "kind": "unavailable" }`。
- `nextTaskAnchor`:删除时同状态序列的后锚点,必须且只能是 FORMAT-014 的 `{ "kind": "task", "taskId": <任务 UUID> }`、`{ "kind": "end" }` 或 `{ "kind": "unavailable" }`。
- `PreviousTaskNeighborSnapshot`:历史位置的前任务邻居快照,使用 FORMAT-021,只能是精确开头边界、含发生时 `taskId` 与 `title` 的任务分支或 `UnavailableTaskRef`。
- `NextTaskNeighborSnapshot`:历史位置的后任务邻居快照,使用 FORMAT-021,只能是精确末尾边界、含发生时 `taskId` 与 `title` 的任务分支或 `UnavailableTaskRef`。
- `PreviousCategoryNeighborSnapshot`:FORMAT-031 分类排序位置的前分类邻居快照,只能是精确自定义序列 `start` 或含发生时自定义分类 `categoryId` 与用户原文 `name` 的严格 `category` 分支。
- `NextCategoryNeighborSnapshot`:FORMAT-031 分类排序位置的后分类邻居快照,只能是精确自定义序列 `end` 或同一严格 `category` 分支;两个分类联合都禁止 Inbox、任务与 `unavailable`。
- 任务主体事件:以一个规范小写 UUID v4 任务不可变标识为主体的任务事实。
- 分类主体事件:以一个规范小写 UUID v4 自定义分类不可变标识为主体的分类管理事实,不依附于任何任务;固定收件箱不属于分类主体。
- `UnavailableTaskRef`:永久清理后用于替代仍保留记录中目标任务结构化邻居或恢复锚点的语言无关值,必须精确为 `{ "kind": "unavailable" }`;它不包含任务标识、标题、指纹、时间或映射,也不是任务墓碑。

## 强制规则

### HIST-001 · 历史只追加

每次已提交的任务新增、修改、移动、删除和恢复都必须追加任务主体事件;每次已提交的自定义分类创建、重命名、排序和删除都必须追加分类主体事件。恢复或后续操作不得改写或截断已有历史。任务永久清理是唯一按 ERASE-001 删除目标任务主体事件并按 ERASE-003 去身份化其他保留记录中结构化任务引用的例外。

### HIST-002 · 按主体保留完整历史

只要任务尚未永久清理,以该任务为主体的历史记录就不得因时间、记录数量或存储压缩策略被自动删除或截断。分类主体事件即使在分类已经删除后也必须继续保留,不得因时间、记录数量、分类删除或任一任务的永久清理被自动删除或截断。产品不得提供单独删除某一条历史记录的操作。

### HIST-003 · 历史事件保存发生时快照

每条历史事件必须严格符合 `backup-format.md` FORMAT-016,且只能具有 `subjectType`、`subject`、`eventType`、`occurredAt`、`operationSequence`、`eventOrder` 与 `details` 七个顶层字段。缺失、未知、额外或 `null` 顶层值均无效。`details` 必须遵守 FORMAT-018,由外层 `eventType` 选择事件专属严格分支,只保存呈现、筛选和校验该操作所需的精确事实;其中 `task.content_changed` 还必须遵守 FORMAT-019,并以保存后 `subject.title` 作为标题新值的唯一来源;`task.completed` 与 `task.reopened` 必须遵守 FORMAT-020,且状态方向只由事件类型表达;任何已经锁定的事件字段只要保存前后任务邻居,都必须精确复用 FORMAT-021;`task.created` 必须遵守 FORMAT-022,只保存初始分类与创建后嵌套位置;`task.priority_changed` 必须遵守 FORMAT-023,只保存发生时分类及不同的旧、新优先级;`task.reordered` 必须遵守 FORMAT-024,只保存一份发生时分类、一份状态和移动前后位置;`task.category_changed` 必须遵守 FORMAT-025,只保存一份状态及来源、目标两个发生时分类位置对象;`task.moved_to_inbox_by_category_deletion` 必须遵守 FORMAT-026,只保存一份状态、来源 Custom 分类与整批前位置、以及整批后最终 Inbox 位置;`task.trashed` 必须遵守 FORMAT-027,只保存删除时分类、状态与移出前位置;`task.restored` 必须遵守 FORMAT-028,只保存恢复插入完成后的实际分类、不变状态与插入后位置;`category.created` 必须遵守 FORMAT-029,详情精确为 `{}` 且 ID / 名称只由公共分类主体表达;`category.renamed` 必须遵守 FORMAT-030,公共主体名称是改名后唯一新值,详情精确只保存 `{ beforeName }` 且新旧名称不同;`category.reordered` 必须遵守 FORMAT-031,详情只保存移动前后方向严格的 Custom 分类直接邻居或自定义序列边界。上述已锁定任务事件都必须保存自身语义所需的发生时 `CategorySnapshot`,不得从后来当前归属补值;FORMAT-026 的固定目标由事件类型表达,不得重复保存 Inbox 快照;FORMAT-027 的分类、状态与位置只供删除历史审计,不得成为当前垃圾箱状态或恢复来源;FORMAT-028 的实际结果只供恢复历史审计、呈现与筛选,不得成为当前归属、当前顺序或任何恢复来源。FORMAT-031 位置同样只供审计,不接受 Inbox 或 `unavailable`,也不得驱动或重建当前 `categoryOrder`。不得另存根级 `kind`、公共外壳或主体副本、完整任务或分类记录以及通用整实体 `before` / `after` 快照包。创建、删除或恢复等不存在一侧值的事件必须由对应事件字段形状表达该侧不存在,不得使用 `null`、空占位、通用不可用对象或伪造默认值。

`category.deleted` 必须遵守 FORMAT-032,公共主体保存被删分类,详情只保存接受时活动来源列表长度 `affectedTaskCount`;该计数不复制任务集合,不参与当前状态或 FORMAT-026 重建,并在任务永久清理后保持不变。

任务主体事件的 `subject` 必须且只能是 `{ taskId, title }`,保存任务规范小写 UUID v4 不可变标识和事件发生时任务标题。分类主体事件只用于自定义分类,其 `subject` 必须且只能是 `{ categoryId, name }`,保存分类规范小写 UUID v4 不可变标识和发生时用户原文名称,且不得保存虚构的任务标识、任务标题或任务主体字段。事件实际需要的分类等上下文按其专属字段进入 `details`:自定义分类必须使用发生时用户原文名称快照;固定收件箱必须保存稳定系统身份且不得保存某一种语言的显示名称。`category.renamed` 的公共 `subject.name` 精确保存改名后处理并保存的新名称,FORMAT-030 `details.beforeName` 精确保存改名前记录中的旧名称;二者必须不同,详情不得再保存 `afterName`、分类身份、完整分类、位置、顺序、任务或界面来源。`category.reordered` 的公共主体精确保存被移动分类,FORMAT-031 邻居分支只保存其他 Custom 分类发生时 ID / 名称,不得重复主体或保存 Inbox。

`(operationSequence, eventOrder)` 是历史事件唯一且稳定的逻辑键。历史记录不得建立独立 `id`、`eventId` 或事件 UUID,也不得保存动作组、本地化摘要、预渲染历史句子或其他未知顶层字段;动作组和呈现文案只能从 `eventType` 及事件数据推导。

任务历史及垃圾箱上下文中任何可能为收件箱或自定义分类的发生时分类语义都必须使用 FORMAT-012 的 `CategorySnapshot`。Custom 快照引用允许在分类后来改名或删除后悬空,发生时名称不得回写;Inbox 快照不得保存显示名称。当前任务归属不得使用该快照代替当前分类引用。

任务状态、`P0` 至 `P5` 任务优先级、精确事件类型、固定系统分类和位置边界必须保存语言无关语义码;动作组必须按 HIST-004 从精确事件类型唯一推导,不得保存本地化动作组文案。用户输入的任务标题、备注、自定义分类名称及其历史快照必须保存原文;切换界面语言不得回写上述事件事实。

历史事件必须能够脱离当前任务和分类的可变显示字段独立呈现。后续标题编辑、分类改名、移动、状态切换、软删除或恢复不得回写既有事件的主体显示、分类名称或事件专属字段事实;永久清理按 ERASE-001 删除目标任务的任务主体事件,并且只可按 ERASE-003 把其他保留事件中语义上指向目标任务的结构化相邻任务引用去身份化。

### HIST-004 · 精确事件类型映射到八个动作组

每条历史事件必须精确使用 FORMAT-017 的 14 值闭集之一,并唯一映射到以下一个用户可见动作组。以下组名是简体中文资源,英文界面必须从同一语义映射显示对应英文,不得把任一显示名称作为持久化枚举值:

| 动作组 | 精确 `eventType` |
|---|---|
| `创建` | `task.created` |
| `内容编辑` | `task.content_changed` |
| `完成状态` | `task.completed`,`task.reopened` |
| `优先级` | `task.priority_changed` |
| `移动与归类` | `task.reordered`,`task.category_changed`,`task.moved_to_inbox_by_category_deletion` |
| `删除` | `task.trashed` |
| `恢复` | `task.restored` |
| `分类管理` | `category.created`,`category.renamed`,`category.reordered`,`category.deleted` |

`category.created` 属于“分类管理”,不得因其显示动词是创建而进入任务“创建”组。其创建时分类名称与身份只读公共 `subject`,FORMAT-029 `details` 精确为 `{}` 且没有额外详情事实;不得从当前分类记录、顺序或创建入口补充摘要。`category.renamed` 同样只属于“分类管理”,必须从 FORMAT-030 `beforeName` 到公共 `subject.name` 呈现旧名到新名;动作和方向词按当前语言本地化,两个用户名称逐字保留。`category.reordered` 也只属于“分类管理”,紧凑摘要必须从 FORMAT-031 `afterPosition` 显示移到自定义序列顶部、末尾或发生时前邻居之后,展开显示完整前后位置;边界与动作本地化而主体和邻居名称保留原文。处理后新名称与旧名称相同不得生成改名事件,分类前后位置相同不得生成排序事件。`task.content_changed` 同时覆盖只改标题、只改备注和同一次正式保存同时修改两者;具体变化字段与精确双语动作必须从 FORMAT-019 除共有 `categorySnapshot` 外的 `{ beforeTitle }`、`{ beforeNotes, afterNotes }` 或 `{ beforeTitle, beforeNotes, afterNotes }` 推导。标题新值只取保存后的 `subject.title`,不得按字段组合新增事件类型、重复事件或重复保存 `afterTitle`。没有实际内容变化时不得生成该事件。

`category.deleted` 同样只属于“分类管理”。紧凑摘要和展开必须从 FORMAT-032 公共主体、`affectedTaskCount` 与固定 Inbox 语义生成;空活动分类的 `0` 仍是明确发生时事实,不得隐藏为未知数量,也不得读取当前任务或剩余 FORMAT-026 补值。

`task.completed` 与 `task.reopened` 的精确动作和状态方向必须只从两个不同的 `eventType` 推导,两者详情都按 FORMAT-020 只保存发生时 `categorySnapshot`。不得保存 `beforeStatus`、`afterStatus`、`status`、布尔值或本地化状态文案;把任务设置为当前状态不得生成任一事件。

`task.priority_changed` 必须只在 `P0` 至 `P5` 之间发生实际变化时生成,详情精确符合 FORMAT-023。精确动作方向由不同的 `beforePriority` 与 `afterPriority` 表达,发生时分类由 `categorySnapshot` 表达;不得保存界面来源、位置、排序键或本地化优先级文案。优先级变化不得改变任务顺序;把任务设置为当前优先级不得生成事件、推进时间或占用操作顺序。

分类不变且只改变同一完成状态序列位置时使用 `task.reordered`,详情精确符合 FORMAT-024:分类与状态各保存一次,移动前后位置分别保存同状态直接邻居。正常生产时两个位置必须真实不同且不得含 `unavailable`;原位、取消或无效放下不生成事件。用户主动改变分类时使用 `task.category_changed`,详情精确符合 FORMAT-025:状态只保存一次,来源与目标分别保存发生时分类及移出前、插入后位置,两个分类身份必须不同;跨分类拖拽、任务行选择器、编辑器选择器以及选择器内新建分类后归入都使用同一分支,不得持久化界面入口或手势来源。选择当前分类不生成事件。分类删除导致的迁移只能使用 `task.moved_to_inbox_by_category_deletion`,详情精确符合 FORMAT-026:状态只保存一次,来源保存被删 Custom 快照与整批前位置,固定目标 Inbox 只保存整批完成后的最终位置。它必须与对应 `category.deleted` 共享一次操作,并按 HIST-006 排在分类事件之后;用户直接移入收件箱不得冒用该派生类型。

任务创建时的初始分类和顺序包含在同一条 `task.created` 中,详情精确符合 FORMAT-022:`categorySnapshot` 冻结入口确定的初始分类,`position` 冻结插入完成后同分类未完成序列的直接前后 FORMAT-021 邻居。连续创建的新事件不得回写先前创建位置,不得额外生成移动或归类事件。软删除详情必须精确符合 FORMAT-027:`categorySnapshot`、`status` 与 `position` 分别冻结移出前分类、状态和同状态直接邻居。恢复详情必须精确符合 FORMAT-028:同名三字段分别冻结恢复插入完成后的实际分类、不变状态和同状态直接邻居;原分类改名时保存恢复时当前名称,原分类已删除时保存固定 Inbox。软删除和恢复造成的可见位置变化分别属于 `task.trashed` 和 `task.restored`,不得重复生成移动事件。分类创建、重命名、排序和删除必须分别形成对应 `category.*` 分类主体事件;其中 `category.created` 必须精确符合 FORMAT-029,公共主体保存新分类 ID 与创建时名称而 `details` 必须为 `{}`;`category.renamed` 必须精确符合 FORMAT-030,公共主体保存同一 ID 与新名称而 `details` 只保存 `{ beforeName }`;`category.reordered` 必须精确符合 FORMAT-031,公共主体保存被移动分类而详情只保存移动前后直接 Custom 邻居或序列边界。改名不得改变分类/任务顺序,排序只改变 `categoryOrder`,二者都不得产生任务事件。

分类删除事件必须精确符合 FORMAT-032,公共主体保存被删分类而详情只保存 `{ affectedTaskCount }`;正常生产时它与 FORMAT-026 迁移集合及当前分类删除、任务连续迁移共同原子提交,但以后任务主体永久清理只删除任务事件而不回写分类事件。

`category.deleted` 必须精确符合 FORMAT-032:公共主体保存被删分类不可变标识与事件发生时名称,`details` 必须且只能为 `{ affectedTaskCount }`。计数是操作被工作状态接受时该分类活动权威顺序的长度,必须是 JSON 非负安全整数;未完成和已完成都计入,垃圾箱任务、到期物理残留、历史旧归属与分类入口草稿不计入,空活动分类保存 `0`。正常 N 项生产时每个实际迁入收件箱的任务必须另行记录一条 FORMAT-026 `task.moved_to_inbox_by_category_deletion(eventOrder = 1...N)` 任务主体事件;永久清理可以后来删除其中部分或全部任务主体事件并留下操作内缺口,不得因此改写分类事件的发生时计数。

FORMAT-032 不得列入任务标识、标题、内容或数组,也不得保存按状态拆分计数、分类身份副本、Inbox 快照、位置/顺序、草稿、确认、原因或界面来源。历史摘要和展开只能从公共分类主体、原始计数与固定 Inbox 语义生成;分类筛选只按公共 `subject.categoryId`,不得让计数或缺失的任务事件形成任务筛选。计数只供发生时审计,不得重建当前分类、任务、顺序或 FORMAT-026。

草稿输入、清空或按 CATEGORY-012 随分类删除确认丢弃草稿,以及自动保存计时与状态反馈、历史展开或筛选、分类与已完成折叠、滚动与导航、备份导出等不得为草稿或界面行为生成历史事件。草稿丢弃不改变分类删除本身的既定事实:同一操作仍必须生成一条 `category.deleted`,并为每个实际迁入收件箱的任务生成一条 `task.moved_to_inbox_by_category_deletion`。完整备份导入按既定覆盖语义保留备份历史,不得为导入动作追加新事件。

### HIST-005 · 移动事件保存相邻位置快照

每条任务移动、移出或恢复插入事件必须保存足以解释发生时归属、语言无关完成状态与相对位置的快照,并复用 FORMAT-021:前任务邻居精确使用 `PreviousTaskNeighborSnapshot`,后任务邻居精确使用 `NextTaskNeighborSnapshot`,没有邻居时分别使用开头或末尾边界,存在邻居时任务分支必须且只能包含 `kind`、另一任务 `taskId` 与发生时 `title`;正常事件生产者不得生成 `unavailable`。其中同分类组内排序必须精确使用 FORMAT-024,只保存一份发生时 `CategorySnapshot`、一份 `open | completed` 状态及两个严格位置;每个位置内双任务邻居必须不同且非主体,跨移动前后位置允许同一邻居重复。用户主动跨分类归类必须精确使用 FORMAT-025,只保存一份状态及 `source` / `target` 两个严格分类位置对象;来源位置对应移出前来源分类,目标位置对应插入后目标分类,正常可识别邻居 ID 跨两侧全部互异。两侧位置可以同为 `start / end`,真实变化由不同分类身份证明。分类删除派生迁移必须精确使用 FORMAT-026,只保存一份状态、来源 Custom 快照与整批前位置、以及整批后最终 Inbox 位置;每个位置内部双任务邻居不同且非主体,但同一批次邻居可以在来源与目标同方向重复,不得套用 FORMAT-025 的跨侧互异规则。软删除必须精确使用 FORMAT-027,只保存一份发生时分类、一份不变状态及移出前单一位置;恢复必须精确使用 FORMAT-028,只保存一份实际目标分类、一份不变状态及插入后单一位置;两者正常双任务邻居都必须不同且非主体。自定义分类快照必须保存对应事件发生时用户原文名称;固定收件箱只保存稳定系统身份。不得方向互换、保存本地化边界或状态文案、使用裸任务 ID、缺失标题或用缺失数据冒充未知位置。

每条自定义分类排序事件必须是分类主体事件并精确符合 FORMAT-031。`details.beforePosition` 与 `afterPosition` 都只能包含 `previousCategory` / `nextCategory`:前侧为自定义序列 `start` 或严格 `{ kind: "category", categoryId, name }`,后侧为 `end` 或同一分类分支。每个位置内双分类邻居不同且均非主体;跨位置允许相邻移动复用同一 ID,重复时名称逐字一致。收件箱固定第一的事实不得被记录为邻居,也不得接受 `unavailable`、绝对序号或内部排序键。

位置快照只用于解释事件发生时上下文,不得成为当前排序读取源、FORMAT-014 恢复锚点或约束后续拖拽。相邻任务或分类后来改名、移动、换分类、切换状态、软删除或删除时,既有事件快照不得回写;相邻任务永久清理时,只把语义上指向该任务的整个 FORMAT-021 任务分支按 ERASE-003 原子替换为精确 `UnavailableTaskRef`。多个区分邻居被合法去身份化后,FORMAT-024 的前后位置、FORMAT-025 的多个邻居槽位、FORMAT-026 的来源与最终位置、FORMAT-027 的删除前位置或 FORMAT-028 的恢复后位置可以结构收敛;这种合法保留结果不得被误判为原位拖拽、损坏归类、无效删除或无效恢复。FORMAT-031 没有任务引用或分类永久清理投影,因此不存在 `unavailable` 或合法位置收敛例外,相同前后位置始终无效。FORMAT-026 同一邻居跨侧重复时必须把所有对应分支一起去身份化,不得留下可识别的一侧。历史界面和备份不得暴露内部排序键,也不得把数据库索引或绝对序号作为用户可见位置事实。历史任务邻居的任务分支保留发生时标题;恢复锚点的任务分支按 FORMAT-014 禁止标题,两种联合不得互换。FORMAT-027 删除位置和 FORMAT-028 恢复位置即使仍完整也不得参与任何恢复。

### HIST-006 · 操作时间与稳定全序

正式操作必须在被当前工作状态接受时一次性冻结 `occurredAt` 和下一个 `operationSequence`;输入按键、拖拽预览、未确认删除或其他尚未形成正式操作的临时状态不得提前占用历史顺序。每个后来被接受的正式操作必须取得更大的 `operationSequence`;永久清理造成的序号空洞不得填补或触发既有事件重编号。

健康写入、待保存重试和应急备份物化都必须保留原 `occurredAt` 与 `operationSequence`。实际 `IndexedDB` 提交、自动重试或导入发生的时间不得覆盖它们,也不得作为用户时间线的替代排序时间。

任何实际改变任务业务状态的操作都必须用同一个冻结 `occurredAt` 更新直接受影响任务的 `updatedAt`;创建操作还必须用它同时建立不可变 `createdAt`。重试、应急导出与延迟提交不得重新计时;无变化操作及备份、自动清理等维护动作不得推进该字段。

一次操作产生多条事件时,所有事件必须共享该操作的 `occurredAt` 与 `operationSequence`,并用 `eventOrder` 稳定排序。直接表达用户分类操作的分类主体事件必须为 `eventOrder = 0`;由该操作引起的任务主体事件随后按操作前源分类中的权威任务总顺序递增,不得按 `open` / `completed` 分组。分类删除的 FORMAT-026 `targetPosition` 仍取完整批次追加后的最终 Inbox 同状态邻居,可以引用更大 `eventOrder` 的批次任务;不得把事件顺序解释成逐条插入步骤。通过选择器新建分类并移动一个任务时,FORMAT-029 空详情分类创建事件同样固定在 FORMAT-025 任务移动事件之前;任务结果不得复制进分类详情。

同一 `operationSequence` 内不得出现重复 `eventOrder`,`(operationSequence, eventOrder)` 在全部保留历史中必须唯一。永久清理可以删除某些任务主体事件并留下操作内顺序缺口,包括让分类删除操作保留的迁移事件少于 FORMAT-032 `affectedTaskCount`、甚至只剩分类事件;后续持久化、迁移、备份导出或导入都不得压缩缺口、重编号既有事件、补建被删事件或要求现存数量仍相等。保留的配对 FORMAT-026 必须使用 `1...affectedTaskCount` 内原有顺序且数量不得超过计数;计数为 `0` 时不得存在配对迁移事件。

### HIST-007 · 分类筛选按目标归属

分类主体事件必须按其主体分类不可变标识匹配分类筛选。FORMAT-031 中只作为排序邻居出现的其他分类不得形成筛选命中;名称搜索可以读取事件自身公共主体及四个 `category` 邻居分支的发生时用户原文,但不得查询当前名称补值。任务主体事件只涉及一个分类时必须按事件保存的发生时 `CategorySnapshot` 匹配该分类;同时保存来源与目标分类的事件必须只按目标分类不可变标识匹配,不得因保留来源快照而同时匹配来源分类。`task.created`、`task.content_changed`、`task.completed`、`task.reopened`、`task.priority_changed`、`task.reordered`、`task.trashed` 与 `task.restored` 必须分别使用 FORMAT-022 / FORMAT-019 / FORMAT-020 / FORMAT-023 / FORMAT-024 / FORMAT-027 / FORMAT-028 的 `categorySnapshot`,不得查询当前任务归属;恢复事件因此按实际恢复目标匹配,不得按删除时分类、锚点分类或任务后来归属重算。`task.category_changed` 必须只使用 FORMAT-025 的 `target.categorySnapshot.ref` 匹配,`source` 不形成来源筛选命中;FORMAT-026 派生迁移必须只匹配固定收件箱,其 `source.categorySnapshot` 同样不形成来源命中。发生时自定义分类后来改名或删除不改变既有事件的匹配。

因此,跨分类任务移动只归入目标分类;分类删除产生的逐任务迁移事件只归入目标收件箱,而同一操作中的分类删除主体事件只归入被删除分类。目标归属只定义筛选结果,不得删除、弱化或回写 HIST-003 与 HIST-005 要求的来源分类和位置快照。

### TRASH-001 · 删除进入垃圾箱

删除任务必须把 `lifecycle` 从精确 `{ "kind": "active" }` 整体替换为 FORMAT-014 的 `trashed` 结构,从 `taskOrderByCategory` 移除该任务,并将 `deletedAt` 与任务新的 `updatedAt` 都设置为删除操作冻结的 `occurredAt`;`expiresAt` 为其后 30 天。任务公共标题、备注、状态与优先级继续保留,不得立即销毁或在生命周期中建立副本。

### TRASH-002 · 软删除前阻断确认

任务进入垃圾箱前必须显示阻断式确认弹窗,明确标识目标任务并说明它将移入垃圾箱且可在 30 天内恢复。取消或关闭弹窗不得执行软删除、改变任务顺序或追加删除历史;按 TRASH-004 在确认前独立发生的有效内容编辑不因此撤销。只有用户明确确认后才能执行软删除并追加且只追加一条 FORMAT-027 `task.trashed`;其 `subject.title` 使用删除接受时最新有效标题,`details` 精确冻结删除时分类、未改变状态与移出前位置。移出活动顺序属于该事件,不得另写移动。

### TRASH-003 · 删除入口共享确认

普通任务删除只能从任务行操作菜单底部或任务编辑器底部的“删除任务”命令发起。两者必须复用 TRASH-002,不得在任一入口中提前软删除或采用不同确认语义。第一版不得通过滑动、常驻垃圾桶或单次键盘删除键绕过这些入口。

### TRASH-004 · 删除排在待保存编辑之后

任务存在尚未自动保存的有效内容时,发起删除必须先保存或排队该编辑。用户确认删除后,编辑与软删除必须作为两个有序操作依次提交并各自形成历史,不得合并、倒序或让旧内容覆盖新内容;垃圾箱记录必须包含编辑后的最新有效内容。取消删除不得取消前序编辑。

### TRASH-005 · 删除时保存恢复定位快照

软删除事务必须同时记录 `categorySnapshotAtDeletion`,并按删除时同一分类、同一 `status` 序列保存 FORMAT-014 的 `previousTaskAnchor` 与 `nextTaskAnchor`。前方没有任务时 previous 必须为 `{ "kind": "start" }`,后方没有任务时 next 必须为 `{ "kind": "end" }`;任务分支必须是只含 `kind: "task"` 与另一任务 `taskId` 的对象,不得使用裸 ID 或保存标题。删除时完成状态继续保存在任务公共 `status` 字段,生命周期不得另存 `statusAtDeletion`;FORMAT-027 历史详情仍必须保存一份同值的发生时 `status`,用于恢复后仍可独立审计,不构成生命周期或当前状态来源。删除事件的 `details.categorySnapshot` 必须与 `categorySnapshotAtDeletion` 逐字段同值,其带标题 `position` 与两侧无标题锚点必须表达同一删除现场但保持严格分离。恢复定位、垃圾箱展示快照与删除历史必须与 `deletedAt`、`expiresAt`、`updatedAt`、任务生命周期及活动顺序移除在同一个原子事务中提交,并进入完整备份。锚点或历史邻居任务后来被永久清理时,对应结构化引用必须分别按 FORMAT-014 与 FORMAT-021 / ERASE-003 变为 `UnavailableTaskRef`,不得继续保存其任务标识或标题。

只有 FORMAT-014 生命周期中的恢复定位快照可用于恢复时寻找最接近原位置的锚点;FORMAT-027 删除历史位置与任一 FORMAT-028 恢复结果都只供审计,不得成为后备锚点。三者都不得在任务删除后锁定或覆盖其他任务的新增、移动、编辑、状态变化或删除。

### TRASH-006 · 最近删除优先展示

垃圾箱只能展示尚未达到 `expiresAt` 的可恢复任务,并按 `deletedAt` 从新到旧排列。每行必须显示删除时标题、优先级、`categorySnapshotAtDeletion` 对应的删除时分类、删除时间和剩余保留天数。自定义分类显示删除时用户原文名称;固定收件箱按当前界面语言显示。剩余天数必须由当前时间与 `expiresAt` 实时计算并向上取整;任务仍可恢复时最小显示 1 天,达到 `expiresAt` 后不得继续显示为 0 天可恢复。

### TRASH-007 · 垃圾箱只负责恢复与清理

每个垃圾箱任务行必须直接提供“恢复”操作。恢复不要求确认,触发后立即执行既定单任务合并恢复;成功或进入待保存队列后,该任务必须离开可恢复列表。

单任务“永久删除”只能位于该垃圾箱任务的操作菜单中。选择该命令只能打开 PURGE-002 的不可恢复确认,明确确认前不得销毁任何内容或历史。

垃圾箱内不得编辑标题或备注、切换完成状态、修改优先级、改变分类、拖拽或重排任务。任务行非控件区域不得打开任务编辑器或发起拖拽;用户必须先恢复任务,再回到主清单修改。

### RESTORE-001 · 单任务合并恢复

恢复必须只影响目标任务,把完整 `trashed` 生命周期整体替换为精确 `{ "kind": "active" }`,移除 `deletedAt`、`expiresAt`、删除时分类快照和两侧锚点,并把同一任务 ID 恰好一次加入权威活动顺序。恢复保留 `createdAt`,把 `updatedAt` 设置为恢复操作冻结的原始 `occurredAt`,并追加且只追加一条精确符合 FORMAT-028 的 `task.restored`;`details` 冻结恢复插入完成后的实际分类、任务公共状态和同状态直接位置,不得另写移动。恢复不得创建副本或覆盖恢复之后新增或修改的其他任务。

### RESTORE-002 · 恢复到最接近原位置

恢复必须保留任务公共 `title`、`notes`、`priority`、`status` 和原始 `createdAt`。删除时分类的不可变标识仍存在时,任务恢复到该分类;分类后来改名不改变此判断,FORMAT-028 必须以同一 ID 保存恢复时当前用户原文名称而不是删除时旧名称。原分类已经删除时,任务恢复到收件箱对应完成状态序列的末尾且 FORMAT-028 使用固定 Inbox 快照,不得重新创建已删除分类。分类选择和下述落位只读取目标任务当前 FORMAT-014 生命周期,不得读取或重放其 FORMAT-027 删除历史或任何 FORMAT-028 恢复结果。

在目标分类中必须按以下优先级只插入被恢复任务;`UnavailableTaskRef` 与不存在、已移动到其他分类或完成状态不符的任务锚点一样视为无效锚点:

1. 前后锚点都仍属于目标分类和删除时完成状态,且前锚点当前仍位于后锚点之前时,恢复到二者之间。
2. 否则前锚点仍属于目标分类和删除时完成状态时,恢复到前锚点之后。
3. 否则后锚点仍属于目标分类和删除时完成状态时,恢复到后锚点之前。
4. 否则恢复到目标分类对应完成状态序列的末尾。

恢复不得移动任何现有任务。恢复事务必须更新原任务而非创建副本,并且只追加一条 FORMAT-028 `task.restored`;其 `position` 取插入完成后的实际同状态直接邻居,只供历史审计而不成为当前顺序第二来源。后来新增或修改的任务必须与被恢复任务共存。

### RESTORE-003 · 恢复成功反馈不强制跳页

恢复事务成功持久化后,用户必须仍停留在垃圾箱,目标任务行立即消失,并出现短暂、非阻断且无需关闭的“已恢复到「实际分类名称」”反馈。实际分类名称必须使用恢复完成后的当前归属:原分类仍存在时使用其当前名称,原分类已删除时显示“收件箱”。反馈必须提供“查看任务”操作,但不得自动切换页面。

用户选择“查看任务”时,应用才按 `navigation.md` 进入任务页并定位目标任务。若恢复操作只进入待保存队列而尚未持久化,不得显示“已恢复”成功文案,必须继续使用 `degraded-availability.md` 的待保存状态。

### RESTORE-004 · 恢复资格在操作被接受时冻结

恢复操作被当前工作状态接受时必须使用同一时刻冻结的 `occurredAt` 检查资格。只有任务在工作状态中仍为软删除且 `occurredAt < expiresAt` 时,才能形成正式恢复操作、把任务移出垃圾箱并追加或排队恢复历史。资格检查与工作状态接受必须属于同一个不可分割动作。

符合资格的恢复即使因写入失败进入待保存队列,也不得在后来跨过 `expiresAt` 时被撤销、隐藏或改为永久清理目标。存储恢复后必须先按队列顺序提交该恢复及其前序操作,再清理工作状态中仍为软删除的到期任务。应急完整备份必须把该任务及恢复历史物化为已恢复状态。

若恢复操作被接受时 `occurredAt >= expiresAt`,或任务在工作状态中已经不再处于垃圾箱,则不得形成恢复操作、改变状态、进入待保存队列或追加历史。到期前已接受但尚未补写或导出的恢复若随活动会话关闭、崩溃或重载而丢失,仍遵守 `degraded-availability.md` 的既定内存队列风险;不得从较旧持久化状态猜测恢复已经发生。

### PURGE-001 · 30 天自动幂等清理

- 当前时间达到或超过 `expiresAt` 时,工作状态中仍为软删除且没有到期前已接受恢复的任务进入永久清理范围。
- 应用运行期间必须自动清理到期任务;`degraded-availability.md` 定义的可写降级态除外。
- 应用启动或回到前台时,必须在展示或恢复任务、垃圾箱和历史交互之前尝试清理已到期任务。核心数据库已经完整读取但启动或回到前台清理事务失败时,可以且只能在先按 PURGE-005 建立逻辑排除后继续;运行期自动清理失败时同样立即逻辑排除并继续日常操作。
- 同一清理过程重复执行任意次数,结果必须与执行一次相同,且不得产生重复记录或错误。

### PURGE-002 · 手动永久清理

用户可以永久删除单个垃圾箱任务或清空垃圾箱。单任务命令只能从对应垃圾箱任务的操作菜单发起;确认框必须显示任务标题,并明确说明任务内容及以该任务为主体的全部历史将永久删除且无法恢复。确认按钮必须使用破坏性视觉并明确标为“永久删除”。

“清空垃圾箱”只能位于垃圾箱页面操作菜单。确认框必须显示打开时垃圾箱内可恢复任务的准确数量,并明确说明这些任务的内容及以这些任务为主体的全部历史将永久删除且无法恢复。确认按钮必须使用破坏性视觉并明确标为“永久删除 N 个任务”,其中 `N` 是本次冻结目标集合的任务数。

两种确认都必须把“无法恢复”限定为当前 Desktop Pull 数据库及之后新生成的备份,并明确提示:用户此前导出的删除前备份可能仍包含这些内容,主动覆盖导入后可能重新出现。不得声称任务已经从用户保存的所有副本中消失。

两种操作都必须经过命令选择后的独立阻断确认,但不得要求输入任务名、确认短语或重复弹出第二个确认框。取消、关闭或离开确认流程不得删除任何任务或历史。

### PURGE-003 · 降级期间暂停永久清理

存在待保存变更时,自动永久清理、单任务永久清理和清空垃圾箱均不得执行。没有到期前已接受恢复的垃圾箱任务达到 `expiresAt` 后立即失去发起新恢复的资格并从逻辑工作状态排除,其任务内容和任务主体历史不得继续进入视图或新备份;所有保留记录中指向该目标的结构化任务邻居与恢复锚点必须立即逻辑投影为 `UnavailableTaskRef`,但物理删除与去身份化写入延后。到期前已接受的待保存恢复继续作为工作状态中的已恢复任务。待保存队列全部按顺序提交后,必须在同一个幂等原子事务中清理仍为软删除的到期任务、其主体历史及对应保留引用,再恢复健康态和手动永久清理入口。

### PURGE-004 · 确认目标冻结且整批原子清理

打开单任务永久删除或清空垃圾箱确认框时,必须按任务不可变标识冻结本次目标集合。确认框打开后才进入垃圾箱的任务不得加入本次集合;集合中的任务若在确认前已经恢复,执行时不得销毁。

用户确认后,应用必须在同一个原子事务内重新筛选目标集合中仍处于垃圾箱的任务,删除这些任务的全部内容及以这些任务为主体的全部历史,并按 ERASE-003 去身份化所有保留记录中指向这些目标的结构化任务引用。批量清理时,本身也会被删除的目标记录无须先去身份化;只有不属于实际清理目标的保留记录需要替换引用。整批任一删除、引用扫描、替换或提交失败时,全部目标任务、目标任务主体历史和所有保留记录都必须保持操作前状态。使用同一目标集合重复执行必须幂等,不得误删已恢复任务、后来新增任务、任何集合外任务、无关历史或独立分类主体事件。

### PURGE-005 · 自动清理失败时逻辑隔离

核心数据库已经完整读取但启动、回到前台或运行期自动到期清理事务失败时,应用不得进入空白工作区或阻断全部日常任务操作。启动时必须在首次展示产品数据前、回到前台时必须在恢复交互前、运行期必须在任务达到 `expiresAt` 时,从逻辑工作状态排除全部仍为软删除且触发时刻达到或超过 `expiresAt` 的任务、其内容及其全部任务主体历史,并把所有保留记录中指向这些目标的结构化任务引用逻辑投影为 `UnavailableTaskRef`。到期前已按 RESTORE-004 接受的恢复不属于排除目标;独立分类主体事件不得被连带排除。

逻辑排除必须使目标任务无法从垃圾箱、历史、搜索、筛选、计数、直接标识访问、操作命令或新备份中出现,并使新备份与所有逻辑视图都不能从保留记录的结构化邻居或恢复锚点读出目标任务标识或标题。物理残留不延长恢复资格,也不得重新成为产品事实。界面与重试、受限操作及状态退出必须遵守 `degraded-availability.md` 的 AVAIL-016。

每次自动或手动重试必须重新计算当前全部到期目标并执行幂等原子清理。清理待完成期间新达到 `expiresAt` 的软删除任务必须立即加入逻辑排除范围。清理失败本身不得形成历史、占用操作顺序或进入用户待保存队列。

### ERASE-001 · 不留历史痕迹

无论自动还是手动永久清理,都必须删除任务内容以及以该任务不可变标识为主体的全部历史记录,并按 ERASE-003 去身份化保留记录中的结构化任务引用。分类主体事件不得携带任务标识或任务标题,也不得因保存了事件发生时受影响任务数量而被某个任务的永久清理连带删除。清理完成后,当前数据库内不得通过垃圾箱、历史或其他任务功能恢复该任务、筛选出其任务事实链或从结构化邻居与恢复锚点识别该任务;ERASE-002 的用户主动完整备份覆盖不属于当前数据库内恢复。

### ERASE-002 · 不可恢复范围止于当前数据库与新备份

永久清理成功后,当前活跃数据库及之后新生成的完整备份都不得包含目标任务、任务内容、以该任务标识为任务身份的字段、其任务主体历史,或保留记录中可识别目标任务的结构化引用。这是按字段语义而非 JSON 原始字符串判断:其他任务的相同标题、用户自由文本中的相同字符,或另一主体类型偶然相同的 UUID 都不是目标任务身份,必须保持不变。Desktop Pull 不得扫描、修改、销毁或声称已经销毁用户此前保存到产品外的删除前备份。

用户主动覆盖导入有效删除前备份时,其中后来被当前数据库永久清理的任务及当时历史可以按完整快照重新进入当前数据库;导入时已经到期的垃圾箱任务仍按 `backup-import.md` 过滤。产品不得保留跨覆盖导入的任务墓碑、删除黑名单或其他用于阻止该恢复的第二事实源。

### ERASE-003 · 跨记录任务引用去身份化

永久清理事务必须只扫描 schema 明确定义为任务邻居或恢复锚点、且语义上指向实际清理目标的结构化引用。保留中的垃圾箱恢复定位记录和任何事件 schema 明确声明的 FORMAT-021 历史任务邻居字段若引用目标任务,必须把整个引用对象替换为精确的 `UnavailableTaskRef`,从该字段移除目标任务标识、标题及其他内容。不得把范围写死为当前已锁定的移动事件字段,也不得在本条擅自决定尚未锁定的事件是否具有邻居字段。不得按 UUID 或标题全文搜索并改写用户任务标题、备注、自定义分类名称或其他自由文本;文本偶然相同不构成引用。

去身份化不得删除引用所在的无关任务、无关历史事件或独立分类主体事件,不得改变其他任务内容、分类、状态或顺序,不得把未知位置伪造成顶部、末尾或另一任务。`UnavailableTaskRef` 只表达原引用已不可用,恢复时必须先尝试另一有效锚点,再使用 RESTORE-002 的既定末尾回退;它不得用于查找目标、阻止删除前备份导入或充当跨导入墓碑。

永久清理及其去身份化属于同一个维护事务,不得追加历史、占用 `operationSequence`、修改 `data.meta.nextOperationSequence` 或推进任何保留任务的 `updatedAt`。自动清理物理事务失败时,PURGE-005 的逻辑工作状态和所有新备份必须应用完全相同的去身份化投影,直到物理重试原子成功。

## 验收 Gate

- 分别创建任务主体和分类主体事件,验证每条只有 FORMAT-016 七个顶层字段,`subject` 严格匹配 `subjectType`,发生时标题或名称逐字保留;缺失、额外、`null`、交叉主体字段或顶层平铺主体字段均被拒绝。
- 对 14 个事件类型逐一验证 `details` 只由外层 `eventType` 判别并符合 FORMAT-018 的事件专属最小严格结构;其中 `task.content_changed` 精确符合 FORMAT-019,`task.completed` 与 `task.reopened` 精确符合 FORMAT-020,`task.created` 精确符合 FORMAT-022,`task.priority_changed` 精确符合 FORMAT-023,`task.reordered` 精确符合 FORMAT-024,`task.category_changed` 精确符合 FORMAT-025,`task.moved_to_inbox_by_category_deletion` 精确符合 FORMAT-026,`task.trashed` 精确符合 FORMAT-027,`task.restored` 精确符合 FORMAT-028,`category.created` 精确符合 FORMAT-029,`category.renamed` 精确符合 FORMAT-030,`category.reordered` 精确符合 FORMAT-031,`category.deleted` 精确符合 FORMAT-032。加入根级 `kind`、重复外壳或主体、完整实体快照、通用整实体 `before` / `after` 包、任意层级 `null`、未知或额外字段时拒绝。不存在的一侧由事件形状表达,嵌套严格联合只在对应字段定义允许时使用自身判别。
- 对使用任务位置的事件分别生成 FORMAT-021 前侧开头/任务分支和后侧任务/末尾分支,验证任务分支精确为 `{ kind, taskId, title }` 且冻结发生时邻居标题;前侧 `end`、后侧 `start`、裸 ID、自引用、悬空 ID、缺标题、边界带标题、`null`、额外字段或正常生产的 `unavailable` 均拒绝。
- 在空分类、已有未完成任务和混合完成状态分类中分别创建任务,验证 FORMAT-022 根部精确为 `{ categorySnapshot, position }`,`position` 精确为 `{ previousTask, nextTask }`,只取插入完成后的未完成序列邻居;连续创建 A/B/C 后 B 前邻居为 A、C 前邻居为 B,先前事件不回写。
- 通过任务行菜单和编辑器分别修改优先级,验证都生成同一 `task.priority_changed` 类型与精确 FORMAT-023 `{ categorySnapshot, beforePriority, afterPriority }`;旧新值合法且不同,不保存控件来源或位置,任务顺序不变。
- 连续执行 `P3 → P1 → P5` 后移动任务或改名、删除发生时分类,验证两条优先级历史分别保留原值对与发生时分类,并继续按该分类筛选;重复选择当前值不产生事件、时间或操作顺序变化。
- 在同分类 `[A, B, C, D]` 的未完成序列把 `B` 移到 `C` 后,验证 FORMAT-024 只保存一份发生时分类与 `open`,原位置为 `A / C`,新位置为 `C / D`;同一邻居跨位置重复合法,每个位置内双任务邻居仍不同且非主体。对 `completed` 序列重复验证。
- 把任务放回原位,验证不改变顺序、`updatedAt`、历史、操作顺序或待保存数量;不含 `unavailable` 且前后位置相同的 FORMAT-024 记录必须拒绝。永久清理足以区分两个位置的邻居后,对应分支变为 `unavailable`,两个位置即使收敛也可合法保留和往返。
- 分别通过跨分类拖拽与两种选择器产生 FORMAT-025,验证状态只保存一次,来源与目标分类身份不同,两侧位置分别对应移出前和插入后同状态邻居;拖拽保存精确落点,选择器目标前侧为 `start`,所有正常邻居 ID 跨两侧互异且非主体。
- 来源只含主体、目标同状态区为空时,验证 FORMAT-025 两侧位置同为 `start / end` 仍合法;选择当前分类不生成事件。永久清理邻居使多个分支变为 `unavailable` 后保留事件,但正常生产相同任务 ID 跨来源与目标、相同分类身份或直接不可用必须拒绝。
- 按来源分类与目标分类分别筛选同一 FORMAT-025 事件,验证只在目标结果中出现,展开仍显示完整来源;后来改名、删除或再次移动不改变筛选身份和快照。
- 删除来源总顺序为 `A(open), B(completed), C(open)` 的分类,验证 FORMAT-026 任务事件按 A/B/C 而不是 A/C/B 排列;每条来源位置取整批前同状态邻居,最终位置取整批后 Inbox 同状态邻居,并允许引用更大 `eventOrder` 的批次任务。
- 对批次中间任务验证 FORMAT-026 同一邻居在 `source.position` 与 `targetPosition` 同方向重复合法且必要,每个位置内部仍身份不同并非主体;可识别 `taskId` 跨方向重复、来源 Inbox、来源快照与分类删除主体不一致、孤立迁移事件、逐项中间目标位置或正常生产 `unavailable` 必须拒绝。
- 永久清理一个在 FORMAT-026 两侧重复出现的邻居,验证所有出现位置在同一事务变为 `unavailable`;再清理若干迁移主体,验证分类删除事件保留原数量、任务事件与 `eventOrder` 可留洞甚至全部消失,导入不要求数量相等或重编号。
- 分别按被删来源分类与收件箱筛选 FORMAT-026,验证任务迁移事件只出现在收件箱结果,紧凑摘要和展开仍使用来源发生时名称与整批前后位置且不查询当前状态。
- 创建事件后移动任务、改名或删除初始分类并改变周围任务,验证创建分类筛选、位置与发生时邻居标题保持;平铺邻居、缺一侧、两侧引用同一任务、正常 `unavailable`、重复标题/时间/默认值、入口/草稿/提交元数据、内部顺序、`before` 或额外字段均拒绝。
- 验证 `(operationSequence, eventOrder)` 对全部保留事件唯一且无需独立事件 ID;注入重复键、负数、非安全整数、小数、字符串、`id`、`eventId`、动作组或本地化摘要时拒绝。
- 永久清理一次多事件操作中的一个任务主体后,验证剩余事件保留原 `eventOrder` 缺口且没有重编号;调换底层记录迭代或备份数组排列后,稳定全序不变。

- 删除未满 30 天的任务不会被自动清理;达到 30 天后会在规定触发点清理。
- 应用关闭期间到期的任务会在下次启动首次展示数据前或回到前台恢复交互前消失。
- 对同一份数据连续执行两次清理,第二次执行前后的持久化状态完全一致。
- 恢复一个任务不会改变任何无关任务的内容或状态。
- 删除任务时验证 `categorySnapshotAtDeletion`、公共 `status` 与严格 `previousTaskAnchor` / `nextTaskAnchor` 同软删除及删除历史原子保存,生命周期没有 `statusAtDeletion` 或裸锚点 ID;删除后移动、编辑、切换或删除锚点任务不受该快照限制。
- 删除任务时验证活动生命周期被完整替换、权威活动顺序不再含该 ID、公共状态和内容没有重复副本,`updatedAt === deletedAt ===` 删除操作 `occurredAt`,previous / next 分别只接受规定任务、边界或不可用分支。
- 在自定义分类中删除任务后重命名或删除原分类,验证垃圾箱仍显示删除时用户原文名称;完整备份往返后该名称快照保持一致。另在固定收件箱中删除任务并切换语言,验证删除时分类按当前语言显示且持久化快照未改写。
- 构造不同 `deletedAt` 的多个垃圾箱任务,验证仅未到期任务按最近删除优先排列,每行显示标题、优先级、删除时分类、删除时间和由 `expiresAt` 实时计算的剩余天数。
- 从垃圾箱直接恢复任务,验证不出现确认弹窗且任务离开垃圾箱;尝试点击任务行、修改字段或拖拽,验证均不会编辑或重排垃圾箱任务。
- 恢复事务成功后验证仍停留在垃圾箱,任务行消失并显示含实际分类名称和“查看任务”的非阻断反馈;不选择该操作时不得自动切换页面。
- 分别恢复到已改名原分类和因原分类删除而回退到收件箱的任务,验证反馈显示恢复后的实际分类名称而非删除时名称快照。
- 注入恢复写入失败,验证不得显示“已恢复”成功文案,并按既定规则持续显示待保存状态。
- 从垃圾箱任务菜单选择永久删除,验证只打开不可恢复确认;取消不改变任务或历史,明确确认后才按 PURGE-002 和 ERASE-001 销毁。
- 分别发起单任务永久删除和清空垃圾箱,验证确认框显示任务标题或冻结集合准确数量、不可恢复后果及明确破坏性按钮,且不要求输入确认短语或再开一层确认。
