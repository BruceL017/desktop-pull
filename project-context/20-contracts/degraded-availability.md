# 写入故障可用性契约(Degraded Availability Contract)

## 定义

- 已持久化状态:已由 `IndexedDB` 成功提交的核心状态和历史。
- 待保存队列:当前运行会话内、尚未成功持久化的有序、契约允许入队的正式业务变更及其对应历史意图;每项保留操作被接受时冻结的 `eventType`、FORMAT-018 事件专属最小 `details`、`occurredAt`、`operationSequence` 和全部事件 `eventOrder`;内容变化还冻结 FORMAT-019 要求的保存后 `subject.title`、发生时 `categorySnapshot` 与精确详情形状和值,完成与重新打开冻结 FORMAT-020 的发生时分类快照和精确形状,主动跨分类变化冻结 FORMAT-025 的根状态、来源与目标分类及两侧位置,分类删除派生迁移冻结 FORMAT-026 的根状态、来源整批前分类与位置、整批后最终 Inbox 位置及来源总顺序,分类删除主体同时冻结 FORMAT-032 精确 `{ affectedTaskCount }`,软删除冻结 FORMAT-027 的删除时分类、状态、移出前位置、最新有效主体标题及同一意图 FORMAT-014 生命周期,恢复冻结 FORMAT-028 的实际目标分类、未改变状态、插入后位置及同一意图完成后的活动生命周期,分类创建冻结公共主体中的创建时 ID / 名称和 FORMAT-029 精确 `{}`,分类改名冻结公共主体中的同一分类 ID / 改名后用户原文名称和 FORMAT-030 精确 `{ beforeName }`,其中 `beforeName` 是改名前存储的用户原文且必须与新名称不同,任何事件 schema 已声明的历史任务邻居字段还冻结 FORMAT-021 的方向分支、另一任务身份与发生时标题。
- 分类排序待保存项还必须冻结被移动 Custom 分类公共 `subject` 与 FORMAT-031 精确 `{ beforePosition, afterPosition }`;每个位置精确只含 `previousCategory` / `nextCategory`,邻居是发生时 Custom 分类 UUID / 用户原文名称或自定义分类序列 `start` / `end` 边界。Inbox、`unavailable`、索引/rank/排序键、`categoryOrder` 副本和 UI/设备/语言元数据都不得进入队列。
- 待保存草稿快照:按 FORMAT-015 保存的最新未持久化四字段草稿记录;它不是任务操作且没有历史意图。
- 工作状态:已持久化状态依次应用全部待保存变更后的界面状态。
- 清理待完成态:核心数据库已经完整读取,但启动、回到前台或运行期自动清理的到期任务、其任务主体历史及保留记录中的目标结构化引用尚未完成物理清理或去身份化;产品已经逻辑排除目标内容、把保留引用投影为不可用并继续提供日常功能。

## 强制规则

### AVAIL-001 · 写事务失败进入降级态

核心数据已成功加载后,任一正式任务、分类或历史业务变更的 `IndexedDB` 事务失败时,持久化数据必须保持操作前状态,该变更进入待保存队列,产品进入全局可写降级态。仅草稿事务失败时遵守 AVAIL-013,不触发本条。自动清理、迁移工件清理等维护事务不得仅据此进入用户待保存队列。

启动、回到前台或运行期自动到期清理事务失败不是正式任务、分类或历史业务变更,必须遵守 AVAIL-016,不得仅因该失败建立待保存队列或增加待保存数量。

### AVAIL-002 · 契约允许的日常操作继续可用

可写降级态必须继续允许任务创建、编辑、状态与优先级修改、分类操作、组内及跨组拖拽、软删除和未到期垃圾箱任务恢复。这些操作依次作用于工作状态并进入待保存队列。恢复是否未到期只在 `history-retention.md` 的 RESTORE-004 接受正式操作时判定一次。

编辑器中尚未保存的有效内容之后发起软删除时,内容编辑与软删除必须作为两个独立操作按先后顺序进入队列。取消删除只能移除尚未入队的删除意图,不得移除或回退前序编辑。

### AVAIL-003 · 持续暴露未保存事实

存在正式待保存变更时,所有主视图必须持续、明确显示当前处于全局降级态、待保存变更数量以及关闭或重载可能丢失这些变更。不得显示或宣布保存成功。界面必须提供立即重试和应急完整备份操作。只有待保存草稿快照时使用 AVAIL-013 的入口级提示。

若失败操作来自当前打开的任务编辑器,编辑器顶部的保存状态区域还必须持续显示“待保存”,并指向同一全局自动重试状态和应急完整备份入口,不得另建第二套恢复流程。

### AVAIL-004 · 正式操作有序且不合并

待保存变更必须保留用户操作顺序、每次操作对应的历史意图和 `history-retention.md` 定义的全部稳定排序元数据。每条历史意图必须在入队时冻结 FORMAT-017 的精确 `eventType` 和 FORMAT-018 的事件专属最小 `details`,并足以原样物化为 FORMAT-016 七字段外壳和 `(operationSequence, eventOrder)` 稳定逻辑键;`task.created` 必须冻结 FORMAT-022 精确 `{ categorySnapshot, position }`,其中位置是创建完成后的未完成序列嵌套双邻居;`task.content_changed` 还必须冻结保存后的 `subject.title` 与 FORMAT-019 三个带发生时 `categorySnapshot` 的分支之一,不得另存或后来补算 `afterTitle`;`task.completed` 与 `task.reopened` 必须冻结 FORMAT-020 `{ categorySnapshot }`;`task.priority_changed` 必须冻结 FORMAT-023 `{ categorySnapshot, beforePriority, afterPriority }`,旧新值必须不同且不得携带位置或控件来源;`task.reordered` 必须冻结 FORMAT-024 `{ categorySnapshot, status, beforePosition, afterPosition }`,正常生产的前后位置必须真实不同且不得携带 UI、绝对索引或内部排序字段;`task.category_changed` 必须冻结 FORMAT-025 `{ status, source, target }`,两侧精确为 `{ categorySnapshot, position }` 且分类引用不同,来源位置取移除前、目标位置取插入后,根状态保持不变。FORMAT-025 正常生产的四个可识别邻居 ID 必须全局两两不同且非主体,不得直接使用 `unavailable`;来源唯一任务移入目标空状态区时两侧 `start / end` 合法。`task.moved_to_inbox_by_category_deletion` 必须冻结 FORMAT-026 `{ status, source, targetPosition }`,来源 Custom 快照与分类事件主体一致,`source.position` 取整批前来源同状态邻居,`targetPosition` 取整批后最终 Inbox 同状态邻居,固定目标不另存快照;任务事件按来源权威总顺序冻结且最终位置可引用更大 `eventOrder`。每个位置内身份不同且非主体,同一批次邻居可在来源和目标同方向重复,正常生产不得使用 `unavailable`。`task.trashed` 必须冻结 FORMAT-027 `{ categorySnapshot, status, position }`,取主体移出前同一工作状态的分类、未改变状态与直接邻居;正常双任务邻居不同且非主体,主体标题取 TRASH-004 前序编辑后的最新有效值。FORMAT-027 与同一意图 FORMAT-014 生命周期的分类、状态、位置与时间关系必须在入队时一致,但带标题历史位置和无标题恢复锚点保持分型。`task.restored` 必须冻结 FORMAT-028 `{ categorySnapshot, status, position }`,取恢复操作接受时当前工作状态中的 FORMAT-014 生命周期完成定位后形成的实际目标分类、未改变状态与插入后同状态直接邻居;原 Custom 分类仍存在时使用同一 ID 与恢复时当前名称,已经删除时使用 Inbox。详情不得包含删除上下文、生命周期、锚点、锚点命中或回退原因、30 天字段、UI/设备来源、绝对索引、内部排序值或当前顺序;FORMAT-028 只供审计,不得在后来补写、排序或恢复中作为输入。`category.created` 必须冻结 FORMAT-029 精确 `{}`,分类 ID 与创建时用户原文名称只由公共 `subject` 表达;缺失、`null`、非对象或任何非空详情都不得入队,也不得冻结位置、入口、关联任务、计数、默认值或当前顺序。`category.renamed` 必须冻结 FORMAT-030 精确 `{ beforeName }` 以及公共 `subject` 中同一分类 ID 与改名后用户原文名称;`beforeName` 必须是改名前存储的用户原文并与 `subject.name` 不同。缺失、`null`、数组、字符串、空对象、`afterName`、未知或额外字段都不得入队,也不得冻结身份副本、位置、顺序、任务、入口、UI 或完整分类记录。任何事件 schema 已声明的历史任务邻居字段必须在入队时冻结 FORMAT-021:前侧无邻居用 `start`,后侧无邻居用 `end`,存在邻居时用精确 `{ kind, taskId, title }` 并逐字保存发生时标题;正常业务历史意图不得直接生成 `unavailable`。邻居后来改标题、移动、换分类、完成或软删除不得改写冻结分支。不得在重试或应急导出时根据当前界面入口、手势、语言、后来状态、分类、顺序或标题重新推断类型、补详情或生成快照,也不得生成事件 ID。后续正式操作继续取得更大的 `operationSequence`;重试不得合并、重排、遗漏、重复或重新计时这些变更。选择当前分类、提交同一有效当前分类名称及其他未产生实际工作状态变化的操作不得进入队列。分类改名必须作为一项待保存操作冻结唯一 `category.renamed(eventOrder = 0)`,只更新工作状态中的当前分类名称并推进一次操作顺序;分类 ID、`categoryOrder`、`taskOrderByCategory`、任务与任务历史保持不变。主清单创建分类必须作为一项待保存操作只冻结 `category.created(eventOrder = 0, details = {})`。选择器内新建分类并移动任务必须作为同一待保存操作冻结 `category.created(eventOrder = 0, details = {})` 与 `task.category_changed(eventOrder = 1)`,不得拆分补写。分类删除同样必须把 `category.deleted(eventOrder = 0, details = { affectedTaskCount: N })`、按来源总顺序排列的完整 FORMAT-026 集合、连续批次状态和全部主体原操作时间冻结为一项待保存操作。`N` 是删除受理时工作状态中被删 Custom 分类活动总顺序实际迁移到 Inbox 的任务数,同时计入未完成与已完成任务,不计垃圾箱任务、逻辑到期物理残留、历史引用或未提交草稿;必须是 JSON 非负安全整数,`0` 合法。正常生产恰有 `N` 条任务迁移事件且 `eventOrder = 1..N`;不得按状态拆批、保存逐项中间位置或在重试时按后来状态重算计数。FORMAT-022 已锁定创建分支,FORMAT-023 已锁定优先级分支,FORMAT-024 已锁定组内排序分支,FORMAT-025 已锁定主动跨分类分支,FORMAT-026 已锁定分类删除派生迁移分支,FORMAT-027 已锁定软删除分支,FORMAT-028 已锁定实际恢复结果分支,FORMAT-029 已锁定 `category.created` 精确空详情,FORMAT-030 已锁定 `category.renamed` 精确 `{ beforeName }`,FORMAT-031 已锁定 `category.reordered` 精确 `{ beforePosition, afterPosition }`,FORMAT-032 已锁定 `category.deleted` 精确 `{ affectedTaskCount }`,且 FORMAT-021 只锁定可复用联合;14 个事件类型的精确详情分支均已锁定。

分类排序必须作为一项待保存操作冻结唯一 `category.reordered(eventOrder = 0)`、移动主体、FORMAT-031 两组位置、操作时间与顺序。每个位置内可识别邻居 ID 必须不同且均非主体,正常前后位置必须不同;原位放下不得入队。工作状态只能改变 `categoryOrder`;分类记录、`taskOrderByCategory`、任务归属/顺序/内容/状态/优先级/生命周期/时间和任务历史必须保持不变。重试与应急物化不得查询后来分类名称/顺序、重放历史或生成任务事件补算该意图。

分类删除待保存项必须在操作首次进入工作状态时冻结 FORMAT-032 的 `affectedTaskCount`、同一批次的 FORMAT-026 事件集合和稳定事件顺序。计数包含此前已经依次应用到工作状态并仍在被删分类中的待保存活动任务变化,但不包含随本次确认被消费的分类入口草稿。后来创建、移动、完成、恢复、清理、重试或应急导出都不得回写该值;任务主体历史随后因永久清理而减少时,分类删除事件与原计数仍保留。

每项待保存任务操作必须同时冻结由该操作 `occurredAt` 得到的任务 `updatedAt`;创建操作还建立同值 `createdAt`。后续工作状态、补写与应急备份只能把这些值应用于直接受影响任务,不得按重试、导出或提交时刻重新计算,也不得改写只因相邻插入而被动位移的任务。

选择器内新建分类并移动任务的待保存操作还必须冻结两条事件的同一 `occurredAt` / `operationSequence`、固定 `eventOrder = 0 / 1`、FORMAT-029 精确 `{}` 及关联身份;FORMAT-025 的 `target.categorySnapshot` 自定义分类 ID / 名称必须与 `category.created` 主体逐字一致。补写和应急物化不得拆分两条事件、向分类详情补字段、改写目标快照或从后来当前分类补算关联。

工作状态中的当前分类集合、名称和顺序必须由已持久化状态叠加待保存分类状态变更得到,不得重放 `category.created`、`category.renamed`、`category.reordered` 或 `category.deleted` 历史建立。分类后来再次重命名、排序或删除时,队列内已经冻结的创建主体与 FORMAT-029 `{}`,改名后主体与 FORMAT-030 `{ beforeName }`,排序主体与 FORMAT-031 两组发生时位置,以及删除主体与 FORMAT-032 `affectedTaskCount` 都不得回写;任务永久清理也不得移除或改写无任务引用的独立分类历史意图。

### AVAIL-005 · 顺序原子补写

应用必须自动按队列顺序重试。每条待保存变更只能在当前状态更新与对应历史事件通过同一个 `IndexedDB` 事务提交后移出队列;补写必须使用入队时冻结的 `occurredAt`、`operationSequence`、`eventOrder` 和由该 `occurredAt` 得到的任务 `updatedAt`,不得使用本次提交时间替换。失败时停止本轮补写并保留该变更及其后续队列。

### AVAIL-006 · 应急完整备份

降级态导出必须生成符合 `backup-format.md` 的完整备份,其数据等于导出瞬间的工作状态、全部对应历史及包含待保存草稿快照的全部非空快速创建草稿。每份内存草稿快照必须原样物化其语义入口、当前 `generation`、标题原文和 UTF-16 `cursorOffset`,不得按导出时刻生成新代次。物化待保存历史时必须生成精确 FORMAT-016 七字段记录,原样保留入队时的 FORMAT-017 `eventType`、FORMAT-018 `details`、`occurredAt`、`operationSequence`、`eventOrder`、严格主体快照和稳定逻辑键;创建事件必须物化已冻结的 FORMAT-022 初始分类与嵌套位置,内容变化事件必须逐字物化已冻结的保存后 `subject.title` 与 FORMAT-019 精确分支,完成与重新打开必须物化已冻结的 FORMAT-020 精确分支,优先级变化必须物化已冻结的 FORMAT-023 发生时分类与旧新值,组内排序必须物化已冻结的 FORMAT-024 发生时分类、状态与移动前后位置,主动跨分类变化必须物化已冻结的 FORMAT-025 根状态、来源与目标分类及两侧位置,分类删除派生迁移必须物化已冻结的 FORMAT-026 根状态、整批前来源与整批后最终 Inbox 位置及来源总顺序,软删除必须物化已冻结的 FORMAT-027 删除时分类、状态、移出前位置与最新有效主体标题,并维持同一删除意图 FORMAT-014 生命周期关系,恢复必须物化已冻结的 FORMAT-028 实际目标分类、状态与插入后位置及活动任务结果,分类创建必须逐值物化已冻结的公共主体与 FORMAT-029 精确 `{}`,并保持主清单单事件或尚未清理选择器 `(eventOrder = 0 / 1)` 事务边界;若选择器关联任务在物化工作状态中已逻辑到期,必须排除该任务及其任务主体历史而独立保留 `category.created(0, {})`,不得补建任务事件或输出反向孤立的 `task.category_changed(1)`;所有已声明历史任务邻居字段必须物化已冻结的 FORMAT-021 分支及发生时标题。不得使用导出时间替代、按后来分类重新分类、从当前分类记录或顺序为 FORMAT-029 补字段、根据后来状态、顺序或标题补详情或补建事件 ID;任务状态同时保留原任务 `createdAt` / `updatedAt`。工作状态中已经到期但因队列存在而尚未物理清理的目标及其任务主体历史必须排除,保留事件中所有 schema 已声明且指向目标的 FORMAT-021 `task` 分支必须整体物化为精确 `{ "kind": "unavailable" }`,同时按 FORMAT-014 独立处理对应恢复锚点;历史替换必须移除目标 `taskId` 与发生时 `title`。若投影使 FORMAT-024 的两个位置、FORMAT-025 的来源与目标位置或 FORMAT-026 的来源与最终位置、FORMAT-027 的删除前位置或 FORMAT-028 的恢复后位置收敛,仍必须原样物化对应合法保留事件。FORMAT-026 同一邻居跨两侧重复时必须投影全部出现槽位;部分迁移主体已经逻辑清理时允许任务事件少于分类事件原受影响数量并保留 `eventOrder` 缺口,不得补建或重编号。导出不得修改 `IndexedDB`、清空待保存队列、移除草稿快照或把产品标记为健康态。

分类改名必须逐值物化入队时冻结的改名后公共 `subject` 与 FORMAT-030 精确 `{ beforeName }`;不得从导出时工作状态中的后来分类名称、顺序、删除状态、后来事件、首次出现或历史重放补算或改写任一名称,也不得增加 `afterName` 或其他字段。同一有效当前名称不入队,因此不得由应急物化补建改名事件或消耗顺序。

分类排序必须逐值物化入队时冻结的移动主体与 FORMAT-031 精确 `{ beforePosition, afterPosition }`;两个位置、Custom 邻居 UUID / 发生时用户原文名称及 `start` / `end` 边界都不得从导出时工作状态、当前分类记录或顺序、后来事件或历史重放补算。应急备份不得增加 Inbox/`unavailable` 邻居、索引/rank/排序键、`categoryOrder`、UI/设备/语言或其他字段;原位放下不入队,不得由物化补建事件或消耗顺序。

分类删除必须逐值物化入队时冻结的公共分类主体与 FORMAT-032 精确 `{ affectedTaskCount }`,并保留同一操作中尚未被逻辑清理的 FORMAT-026 迁移事件和原 `eventOrder`。应急物化不得按剩余任务事件数、当前 Inbox、当前分类、垃圾箱、草稿或物理残留重新计算计数;即使迁移任务主体已经逻辑到期而被排除,原计数也不得减少。

### AVAIL-007 · 暂停永久清理与覆盖导入

存在正式待保存变更时,必须暂停单任务永久清理、清空垃圾箱、自动永久清理和完整备份导入。完整备份导出保持可用,且必须按 AVAIL-006 自动包含全部待保存变更。仅存在待保存草稿快照时不得仅据此暂停这些操作;清理待完成、迁移或其他独立状态已经施加的限制继续有效。

仅存在 AVAIL-016 的清理待完成态时,必须暂停新的单任务永久清理、清空垃圾箱和完整备份导入,但继续自动重试或允许手动重试当前到期清理。完整备份导出继续可用且必须排除全部逻辑到期任务及其任务主体历史,把保留事件中所有 schema 已声明且指向目标的 FORMAT-021 `task` 分支整体物化为精确 `{ "kind": "unavailable" }`,并按 FORMAT-014 独立处理对应恢复锚点。清理待完成态与正式待保存队列同时存在时,先暂停到期清理并按本契约补写队列。

### AVAIL-008 · 恢复健康态

只有全部待保存变更按队列顺序成功提交,并随后基于补写后的当前状态在同一幂等原子事务完成仍为软删除到期任务、其任务主体历史、保留事件中所有 schema 已声明的目标 FORMAT-021 `task` 分支整体去身份化及对应 FORMAT-014 恢复锚点去身份化,产品才能清除降级提示并重新开放单任务永久清理、清空垃圾箱、自动永久清理和完整备份导入。历史分支必须精确替换为 `{ "kind": "unavailable" }` 并移除目标 ID 与发生时标题。到期前已接受的恢复必须先按入队时冻结的活动状态和 FORMAT-028 实际恢复结果提交,不得在补写前被清理重新判定为失效,也不得跨期重算分类、位置或邻居。

没有正式待保存变更但仍处于清理待完成态时,必须在一次重试事务成功后重新扫描;只有不存在任何仍为软删除的到期任务时才能清除清理提示并恢复受限入口。不得仅凭某次请求返回成功而跳过重新扫描。

### AVAIL-009 · 不引入第二持久化事实源

待保存队列和待保存草稿快照只保存在当前运行会话的内存中,不得持久化到 `localStorage`、`sessionStorage`、OPFS、Service Worker Cache 或远程服务。应用必须明确告知用户:补写前结束会话会丢弃这些内存状态;若未完成应急导出,待保存变更与最新草稿可能不可恢复。

### AVAIL-010 · 到期只阻止新的恢复

降级期间,工作状态中仍在垃圾箱且尚未接受恢复的任务达到 `expiresAt` 时,必须立即从全部逻辑视图排除,并拒绝此后发起的恢复。保留事件中所有 schema 已声明且语义上指向这些目标的 FORMAT-021 `task` 分支必须立即整体逻辑投影为精确 `{ "kind": "unavailable" }`,同时按 FORMAT-014 独立投影对应恢复锚点;历史邻居不再保留目标 `taskId` 或发生时 `title`,且不得只处理移动事件。历史界面、恢复解析和应急完整备份不得读取物理残留的目标标识或标题。物理删除任务及其任务主体历史与引用去身份化写入延后到持久化恢复后执行;应急完整备份必须排除目标任务及其任务主体历史并物化引用投影,但不得因此排除独立分类主体事件或无关历史。

任务在 `expiresAt` 前已经按 RESTORE-004 接受恢复并进入待保存队列时,工作状态必须继续把它视为已恢复;跨过到期时间不得撤销操作、移回垃圾箱、重算已冻结 FORMAT-028 或从应急完整备份排除。补写和到期清理的先后必须遵守 AVAIL-008。

### AVAIL-011 · 草稿快照按入口覆盖

草稿持久化失败不得阻塞输入或弹出对话框。相关入口必须显示未保存状态并自动重试。每个 FORMAT-015 语义入口只能保留一份最新待保存四字段草稿快照;同一非空代次的后续标题或光标修改必须覆盖该入口的此前快照并保留 `generation`,不得进入 AVAIL-004 的正式操作队列或生成历史意图。输入变为空时移除该快照,之后重新进入非空输入才生成新代次。任务等正式操作仍不得合并。

### AVAIL-012 · 提交消费旧代次后再保存新代次

提交待保存草稿时,必须把提交幂等键、该草稿的 FORMAT-015 语义入口、`generation`、标题、由入口推导的目标分类、初始顺序位置、从同一工作状态生成的 FORMAT-022 创建详情、正式操作的 `occurredAt` 和 `operationSequence` 冻结进任务创建操作,并从待保存草稿快照中条件消费同一入口与代次且使其独立草稿重试失效。入口、代次与提交键不得写入创建详情。输入框清空后产生的文字属于新代次草稿。恢复补写必须先提交较早的任务创建操作,再持久化同入口的新代次草稿;旧代次消费不得按入口无条件删除新代次。

### AVAIL-013 · 草稿失败保持入口级状态

只有草稿持久化失败且正式任务、分类与历史业务事务尚未失败时,产品不得仅因草稿失败进入全局可写降级态、显示全局待保存横幅或新增对永久清理、清空垃圾箱和完整备份导入的暂停。只有相关快速入口显示“草稿未保存”、自动重试、关闭或刷新风险和应急完整备份入口;其他独立状态已经施加的提示和限制不得因此解除。

后续任一正式任务、分类或历史业务事务失败时,必须立即按 AVAIL-001 升级为全局可写降级态;原有待保存草稿快照继续保留并进入应急备份,但不转化为任务历史操作。

### AVAIL-014 · 未完成初始读取不得进入可写降级

可写降级态必须以核心数据已经完整加载为前提。应用启动时因非迁移故障无法初始化或完整读取 `IndexedDB` 时,不得建立空白工作状态或内存待保存队列,必须按 `indexeddb-storage.md` 的 STORAGE-009 进入启动数据保护态。只有完整读取成功后发生的正式任务、分类或历史业务事务失败才能适用 AVAIL-001。

完整读取成功而启动到期清理事务失败时已经具有可信基线,不得退回数据保护态;必须按 AVAIL-016 继续启动。

### AVAIL-015 · 待保存状态属于活动窗口

正式待保存队列和待保存草稿快照只属于持有 `single-active-window.md` 排他控制权的当前活动窗口。任一种待保存状态存在时都不得移交窗口控制权;第一版不得把队列或草稿快照传输、合并或持久化给另一窗口。

活动窗口关闭或崩溃后,其他窗口只能从已持久化状态接管。原窗口未应急导出的内存状态可能丢失;即使已经完成应急导出,控制权移交仍须等待实际待保存状态落盘,不得把文件生成误当成数据库恢复。

### AVAIL-016 · 自动清理失败先逻辑排除再继续

活动窗口已经确认唯一活跃数据库代次并完整读取全部核心数据后,若启动、回到前台或运行期自动到期清理事务失败且完整回滚,必须进入清理待完成态。启动触发必须在任何产品数据可见前完成逻辑排除;回到前台触发必须在恢复产品交互前完成;运行期触发必须在任务达到 `expiresAt` 时立即使目标退出逻辑产品状态,不得等待物理事务成功。所有仍为软删除且触发时刻达到或超过 `expiresAt`、又没有到期前已接受恢复的任务,连同其任务内容和全部任务主体历史,必须从逻辑工作状态排除;所有保留事件中语义上指向这些目标且由 schema 明确声明的 FORMAT-021 历史任务邻居 `task` 分支必须按 ERASE-003 整体逻辑投影为精确 `{ "kind": "unavailable" }`,同时按 FORMAT-014 独立投影对应恢复锚点。独立分类主体事件继续保留。

逻辑排除与引用去身份化投影必须覆盖任务、垃圾箱、历史、搜索、筛选选项、计数、直接标识访问、可执行命令和所有新生成的完整备份。被排除任务不得恢复或重新进入界面;保留记录不得显示或导出目标任务标识、标题或其他引用内容。该维护投影不得推进任何保留任务的 `updatedAt`。物理残留不得被解释为仍在 30 天保留期内,`UnavailableTaskRef` 恢复时按无效锚点处理。

清理待完成态必须继续允许任务创建、编辑、状态与优先级修改、分类操作、组内及跨组拖拽、软删除和未到期恢复。后续正式任务、分类或历史业务写入成功时正常持久化;这类业务写入失败时才按 AVAIL-001 叠加可写降级态。清理失败本身不得追加历史、占用 `operationSequence`、进入待保存队列或增加待保存数量。

所有主视图必须持续显示非阻断状态,明确说明部分到期内容尚未从当前设备物理清除、产品已经隐藏并正在自动重试,同时提供手动重试。该提示不得使用“待保存”描述清理失败,也不得声称已经彻底清除。

不存在正式待保存队列时,应用必须自动幂等重试物理清理与引用去身份化。重试前及清理待完成期间有其他任务新达到 `expiresAt` 时,必须立即加入逻辑排除与去身份化投影范围;重试事务按当时工作状态重新计算全部到期目标、保留事件中所有 schema 已声明且指向目标的 FORMAT-021 `task` 分支及对应 FORMAT-014 恢复锚点。出现正式待保存队列时,按 AVAIL-007 暂停物理清理,先提交到期前接受的恢复及其他前序操作,再重新计算目标。

清理待完成状态只由完整读取的数据库内容、工作状态和当前时间推导,不得持久化为第二事实源或进入备份。会话重启后必须重新完整读取并执行同一逻辑排除和重试,不得短暂展示物理残留内容;后台期间跨过到期时刻的任务在回到前台时也不得短暂恢复可见或可操作。手动永久删除和迁移工件清理失败不因本条自动取得相同处置。

### AVAIL-017 · 分类删除消费已确认草稿代次

用户按 CATEGORY-012 接受“删除分类并丢弃草稿”时,工作状态必须立即移除该分类标题入口的已确认 FORMAT-015 `entry`、`generation`,并使对应内存快照、自动重试与延迟回调失效。即使该草稿只存在于内存、从未成功持久化,也不得要求先保存、迁移或创建任务。

若分类删除的正式业务事务失败,分类删除必须连同 FORMAT-032 精确 `affectedTaskCount`、连续任务批次、每个迁移主体原操作时间、精确 FORMAT-026 历史意图、操作顺序进度和草稿条件消费作为一项冻结的正式操作进入待保存队列;不得另建草稿丢弃操作。计数取该操作首次进入工作状态时被删分类活动总顺序中的实际迁移数量,同时计入未完成与已完成任务并排除垃圾箱、逻辑到期物理残留、历史引用和本次消费的草稿;空分类保存 `0`。FORMAT-026 的来源位置取整批前状态,最终位置取整批完成后的工作状态,任务事件按来源权威总顺序冻结;不得在补写时按状态拆批、逐项生成中间位置、查询当前 Inbox 尾部或重算计数。工作状态和 AVAIL-006 应急完整备份都必须物化分类已删除、任务已迁入收件箱、既定历史已产生且该草稿不存在的同一逻辑结果。补写时以一个原子事务提交全部正式结果,并以冻结 `entry`、`generation` 为逻辑授权清除匹配持久草稿或被该已确认内存代次明确覆盖的同入口旧持久记录;旧重试或回调不得在已删除分类下重建草稿。草稿丢弃不生成历史、不增加独立待保存项,也不额外消耗 `operationSequence`;同一次确认的重复派发不得增加第二项队列记录。

## 验收 Gate

- 数据加载完成后注入一次任务写事务失败,验证数据库不变、界面应用该变更、待保存数量增加且普通操作仍可继续。
- 在降级态依次执行编辑、拖拽、软删除和恢复,验证工作状态与队列顺序正确,没有操作被合并或重复。
- 在自动保存失败后从编辑器发起并确认删除,验证内容编辑排在软删除之前且两者不合并;取消删除时前序编辑仍在队列中。
- 让软删除进入待保存,验证同一队列项冻结 FORMAT-027 `{ categorySnapshot, status, position }`、最新有效主体标题及 FORMAT-014 垃圾箱生命周期;历史带标题邻居与无标题恢复锚点表达同一删除现场,时间、分类或位置关系不因重试、应急导出或后来操作重算。
- 在待保存工作状态中恢复、修改、移动并再次删除同一任务,验证旧 FORMAT-027 不回写,新删除冻结独立现场;恢复只读取工作状态中的当前 FORMAT-014 生命周期,不得从队列历史位置移动其他任务。
- 分别让收件箱、仍存在且已改名的原 Custom 分类、已经删除的原分类以及各锚点命中/回退路径的恢复进入待保存,验证同一队列项只冻结 FORMAT-028 `{ categorySnapshot, status, position }`:实际目标分类使用恢复时当前名称或 Inbox,状态不变,位置取插入后同状态邻居;现有其他任务不移动或覆盖。
- 恢复进入待保存后继续移动、改状态、改标题、改名或删除目标分类,并跨过原 `expiresAt`,验证补写与应急备份仍逐值使用入队时 FORMAT-028,不从后来工作状态、FORMAT-027、FORMAT-014 或当前顺序重算,后续操作仍排在恢复之后。
- 向待保存恢复意图加入删除上下文、生命周期、锚点、命中/回退原因、30 天数据、UI/设备来源、绝对索引、内部排序值或当前顺序,验证不能入队或物化为应急备份;缺失、错向、自引用或同位置双侧同任务的邻居同样拒绝。
- 在清理投影命中 FORMAT-028 `position` 邻居时,验证应急备份把整个任务分支改为精确 `unavailable` 并移除目标 ID 与发生时标题,恢复事件本身保留且不查询当前邻接补值。
- 执行不改变工作状态的操作,验证待保存数量和历史意图均不增加。
- 验证桌面与移动端所有主视图持续显示未保存事实、会话风险、重试和应急备份入口。
- 从打开的任务编辑器触发正式保存失败,验证编辑器顶部持续显示“待保存”并连接同一全局重试与应急备份,且没有第二套恢复状态。
- 模拟存储恢复,验证待保存变更依次提交,且每条状态与历史要么同时存在、要么同时不存在。
- 在队列中间注入再次失败,验证已提交前缀只提交一次,失败项及后续项仍按原顺序待保存。
- 为连续待保存操作设置相同时间值并延迟补写,验证每项保留原 `occurredAt`、递增 `operationSequence` 和操作内 `eventOrder`;补写完成时间不改变历史排序。
- 在降级态依次创建、编辑、移动、软删除和恢复任务,验证工作状态、应急备份与最终补写中的 `createdAt` / `updatedAt` 都使用各操作原 `occurredAt`;重试、导出及周围任务被动位移不改写时间。
- 导出应急备份并在空数据库导入,验证恢复结果等于导出时工作状态且包含待保存操作的历史。
- 导出含待保存软删除的应急备份,验证 FORMAT-027 不包含删除/到期时间、生命周期、恢复锚点、内容、优先级、原因、确认/UI/设备或排序实现字段;对应任务记录仍独立包含严格 FORMAT-014 生命周期。
- 导出包含任务与分类待保存操作的应急备份,验证物化历史逐条符合 FORMAT-016 七字段外壳,FORMAT-017 精确类型与稳定逻辑键均和入队时一致且没有事件 ID;跨重试切换语言或从不同界面重试不改变类型,永久清理形成的合法 `eventOrder` 缺口保持不变。
- 让待保存队列覆盖 FORMAT-017 全部 14 个类型,验证补写和应急物化逐值保持且不接受未知类型;直接归类与分类删除派生迁移在重试后仍保持不同类型和各自操作约束。
- 验证降级态不能执行手动或自动永久清理、清空垃圾箱和完整备份导入,但完整导出可用且包含全部待保存变更。
- 检查所有持久化实现,验证待保存队列未写入第二种本地或远程存储。
- 在 `expiresAt` 前接受恢复并让写入失败,跨期后验证任务仍在工作状态、待保存队列和应急备份中;恢复持久化时先提交恢复及历史,随后清理不会删除它。
- 让另一项未接受恢复的垃圾箱任务在降级期间达到 `expiresAt`,并预先让它成为保留垃圾箱任务的恢复锚点与保留历史中所有 schema 已声明的邻居字段目标,验证目标立即不可见、无法再发起恢复且不进入应急备份,全部对应引用在历史界面、恢复解析和备份中立即整体投影为 `{ "kind": "unavailable" }`,历史邻居不再含目标 ID 或发生时标题;恢复持久化后才在同一事务物理删除目标与任务主体历史并写入引用去身份化,独立分类主体事件和无关历史不受影响。
- 在上述到期引用投影及物理补写前后比较所有保留任务,验证其 `createdAt` / `updatedAt` 不因维护清理或锚点去身份化变化。
- 分别在指针按下早于到期但正式接受晚于到期、正式接受恰好等于到期两种场景恢复,验证都以接受时刻为准拒绝,不改变工作状态、不入队、不写历史或占用操作顺序。
- 到期前接受恢复后继续编辑或移动该任务并跨期,验证队列保持恢复在前、后续操作在后,到期清理不打断队列或删除任务。
