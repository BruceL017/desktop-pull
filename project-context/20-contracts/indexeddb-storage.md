# IndexedDB 存储与迁移契约

## 强制规则

### STORAGE-001 · 唯一核心数据库

任务、分类、持久顺序、垃圾箱记录、历史事件和快速创建草稿必须统一存储在 `IndexedDB`。`localStorage`、`sessionStorage`、Service Worker Cache 或内存状态不得成为任何核心数据或跨重启草稿的持久化事实源。

Schema 升级可以按 `migration-rollback.md` 短暂创建不可写的隔离候选数据库代次,但持久化激活标记在任一时刻只能选择一个可写核心事实源。候选工件不得承接用户操作、进入备份或在新代次开放写入后继续保留。

### STORAGE-002 · 共享事务边界

当前状态更新、匹配真实任务或分类主体的历史事件追加及已使用 `operationSequence` 的持久进度必须在同一个 `IndexedDB` 事务内完成。同一操作的全部事件必须原子保存共同的 `occurredAt`、`operationSequence` 和各自 `eventOrder`。按 CATEGORY-012 删除分类时,该事务还必须断言逻辑入口仍为复核冻结的无草稿状态或已确认 `entry`、`generation`,并清除同入口匹配记录或被该已确认内存代次明确覆盖的旧持久记录;发现未经确认的新逻辑代次或无法证明陈旧的不同代次必须中止整个事务,不得把条件删除零行当作成功。确认草稿只在内存且数据库没有该入口记录时允许零行,但最终复核至提交必须由同一入口变更栅栏排除新代次,提交后不得留下 custom 悬空记录。永久清理任务、删除其任务主体历史及把保留事件中所有 schema 已声明且指向目标的 FORMAT-021 `task` 分支整体替换为精确 `{ "kind": "unavailable" }`,以及按 FORMAT-014 独立去身份化对应恢复锚点,必须使用同一个事务;历史替换必须同时移除目标 `taskId` 与发生时 `title`,不得只扫描移动事件。清空垃圾箱时,全部仍符合条件的冻结目标、其任务主体历史及所有必要的保留引用替换必须共享一个批量事务,且不得删除独立分类主体事件或无关历史。该维护事务不得追加事件或消耗操作顺序。

选择器内新建分类并移动任务时,新分类、主体当前归属与权威顺序、主体 `updatedAt`、操作顺序进度及两条历史必须在同一事务提交:`category.created` 固定 `eventOrder = 0` 且 FORMAT-029 `details` 必须为精确 `{}`,精确符合 FORMAT-025 的 `task.category_changed` 固定 `eventOrder = 1`,分类 ID / 创建时名称只由该事件公共 `subject` 保存;其目标分类 ID / 名称必须与分类事件主体逐字一致。任一写入失败必须整笔回滚,不得留下空分类、单边历史或已消耗顺序。

主清单内联创建分类时,新 FORMAT-012 分类记录、追加到 `categoryOrder` 末尾、操作顺序进度与唯一的 `category.created(eventOrder = 0, details = {})` 必须在同一事务提交。分类公共主体必须与新记录 ID / 名称逐字一致;任一写入失败时不得留下分类、顺序、历史或已消耗操作顺序的局部结果。

分类改名时,分类记录的当前 `name`、操作顺序进度与唯一的 `category.renamed(eventOrder = 0)` 必须在同一事务提交。该事件公共 `subject` 精确保存同一分类 ID 与改名后用户原文名称,FORMAT-030 `details` 必填且精确只含改名前存储的用户原文 `beforeName`,两者必须不同。事务不得改变分类 ID、`categoryOrder`、`taskOrderByCategory`、任何任务记录、任务归属、任务顺序、任务时间或任务历史;任一写入失败时全部回滚且不得消耗操作顺序。同一有效当前名称是无变化操作,不得建立事务历史事实或推进顺序。

分类排序时,新的 `categoryOrder`、操作顺序进度与唯一的 `category.reordered(eventOrder = 0)` 必须在同一事务提交。该事件公共 `subject` 是被移动 Custom 分类,FORMAT-031 `details` 必填且精确只含 `beforePosition` / `afterPosition`;每个位置只含有方向的 `previousCategory` / `nextCategory`,并在操作接受时冻结 Custom 邻居的规范小写 UUID v4 与用户原文名称或自定义分类序列 `start` / `end` 边界。Inbox 不得作为邻居,每个位置内可识别邻居 ID 必须不同且均非主体,正常前后位置必须不同。事务只能改变 `categoryOrder` 并推进一次操作顺序;不得改变分类记录、`taskOrderByCategory`、任务归属/顺序/内容/状态/优先级/生命周期/时间或写入任务事件。任一写入失败时全部回滚且不得消耗顺序;原位放下是完整 no-op,不得建立事务或历史事实。

删除分类时,同一事务必须把来源权威总顺序作为一个连续批次追加到 Inbox、更新每个迁移主体 `updatedAt`、写入 `category.deleted(eventOrder = 0, details = { affectedTaskCount: N })` 与按来源总顺序排列的完整 FORMAT-026 任务事件集合,并推进一次操作顺序。`N` 是受理时该分类活动总顺序中实际迁移的任务数,同时计入未完成与已完成任务,不计垃圾箱任务、逻辑到期物理残留、历史引用或未提交草稿;空分类的 `N = 0` 合法。正常事务恰写 `N` 条任务事件并占据 `eventOrder = 1..N`。每条 `source.position` 从整批前状态冻结,`targetPosition` 从整批完成后的最终状态冻结且可以引用更大 `eventOrder` 的批次任务;不得按状态拆批、逐条提交、保存中间 Inbox 位置或随后按剩余任务重算计数。任一 store 或事件写入失败必须整笔回滚。

### STORAGE-003 · 显式 schema 版本

数据库 schema 必须包含单调递增的显式版本。任何对象存储、索引或记录结构变化都必须通过对应版本迁移完成,不得在运行时隐式猜测数据版本。

### STORAGE-004 · 迁移保留用户数据

从任一受支持旧版本升级到当前版本时,迁移必须保留任务内容、语言无关状态、优先级、分类、顺序、软删除状态、恢复定位与删除时分类语义快照、全部保留中的任务主体和分类主体历史及其系统语义、用户原文、操作时间与稳定全序,以及非空快速创建草稿的语义入口、当前代次、标题原文与 UTF-16 光标偏移。旧事件 schema 已声明的正常历史任务邻居必须按 `backup-compatibility.md` 无歧义迁移为 FORMAT-021 的方向边界或精确 `{ kind, taskId, title }` 发生时快照,不得从升级时当前顺序、分类、状态或标题补算;邻居后来移动、换分类、完成、软删除或改标题不得触发改写。旧 `task.created` 还必须由旧记录自身无歧义迁移为 FORMAT-022 的初始分类与创建后嵌套双邻居,无法确定时拒绝候选迁移而不得猜测默认边界。旧 `task.priority_changed` 必须由旧记录自身无歧义迁移为 FORMAT-023 的发生时分类与不同旧新优先级,不得从最终任务值、默认 `P3`、当前分类或相邻事件补算。旧 `task.reordered` 必须由旧记录自身无歧义证明同分类同状态真实换位并迁移为 FORMAT-024 的发生时分类、状态及移动前后位置,不得从最终或当前顺序、分类、状态、标题、绝对索引、排序键或相邻事件补算。旧 schema 合法保留的、指向已永久清理任务的结构化邻居或恢复锚点才可按 COMPAT-011 迁移为 `UnavailableTaskRef`,不得继续保存目标身份或把损坏引用伪装成不可用;合法去身份化使 FORMAT-024 两个位置收敛时仍须保留。FORMAT-014 恢复锚点仍使用无标题 `task` 分支,不得与 FORMAT-021 串型。

旧 `task.category_changed` 只有在旧文件自身能无歧义证明来源与目标分类引用不同、同一 `open | completed` 状态、来源移除前位置、目标插入后位置及全部发生时邻居标题时,才能迁移为 FORMAT-025 精确 `{ status, source, target }`。迁移不得从最终或升级时当前归属、顺序、状态、标题、绝对索引、排序键、界面入口或相邻事件猜测缺失事实;合法旧清理投影可迁移嵌套 `unavailable` 并允许位置收敛,普通损坏不得借此通过。任一必需事实不确定时必须拒绝候选迁移。

旧 `task.moved_to_inbox_by_category_deletion` 只有在旧文件自身能无歧义证明匹配的分类删除、来源 Custom 快照、不变状态、来源权威总顺序、整批前来源位置、整批后最终 Inbox 位置及全部发生时邻居标题时,才能迁移为 FORMAT-026 精确 `{ status, source, targetPosition }`。同方向批次邻居跨来源与目标重复合法,最终位置可引用更大 `eventOrder`;不得从当前或最终状态、当前 Inbox 尾部、绝对索引、事件顺序、D-009、HIST-006 或相邻分类事件猜测缺失事实。合法旧清理结果可保留 `unavailable`、任务事件缺口及原顺序号,但孤立迁移、来源错配、可识别 `taskId` 跨方向重复或半侧去身份化必须拒绝。

旧 `task.trashed` 只有在旧记录自身能无歧义证明删除时分类、`open | completed` 状态、移出前同分类同状态直接邻居及全部发生时邻居标题时,才能迁移为 FORMAT-027 精确 `{ categorySnapshot, status, position }`。不得从升级时当前任务、当前顺序、默认边界、相邻事件或 FORMAT-014 无标题恢复锚点补算缺失事实;后来恢复、修改、移动或再次删除造成的当前状态差异不得改写或判废旧删除事件。任一必需事实不确定时必须拒绝候选迁移。

旧 `task.restored` 只有在旧记录自身能无歧义证明恢复完成后的实际分类语义(Custom 的 ID 与恢复时名称,或 Inbox)、`open | completed` 状态、插入后同分类同状态直接邻居及全部发生时邻居标题时,才能迁移为 FORMAT-028 精确 `{ categorySnapshot, status, position }`。原 Custom 分类仍存在时必须证明同一 ID 与恢复时当前名称,已经删除时必须证明实际落点为 Inbox;不得从 FORMAT-027 删除事件、FORMAT-014 无标题锚点、升级时当前状态、默认回退、相邻事件或历史重放补算。任一必需事实不确定时必须拒绝候选迁移。

旧 `category.created` 必须先按候选记录声明的、明确受支持的旧 schema 验证。只有旧事件类型及合法分类主体、时间和稳定顺序已无歧义证明创建时,才能规范化公共主体并把旧版本正式允许且已验证的重复身份/名称、位置、界面入口、关联、计数或默认值确定性投影为 FORMAT-029 精确 `{}`。未知字段、冲突值、旧 schema 不允许的字段或含混主体/类型必须使候选迁移失败;不得从升级时当前分类、当前顺序、首次看见、后来事件或配对任务事件推断。当前 schema 中缺失、`null`、非对象或非空的 `category.created.details` 是损坏记录,不得复用旧版本迁移路径修复。

旧 `category.renamed` 必须先按候选记录声明的、明确受支持的旧 schema 验证。旧版本正式同时保存改名前后名称时,必须先验证两端名称合法且不同,再要求旧后值与规范化后的公共 `subject.name` 逐字一致;只有这样才能丢弃冗余后值并把旧前值确定性投影为 FORMAT-030 精确 `{ beforeName }`。未知字段、冲突或含混名称、旧 schema 不允许的字段或无法判别的主体/类型必须使候选迁移失败;不得从升级时当前分类名称、当前顺序、后来事件、首次出现或历史重放推断。当前 schema 中缺失、`null`、数组、字符串、空对象、含 `afterName`、未知或额外字段,或 `beforeName` 与 `subject.name` 相同的改名详情是损坏记录,不得复用旧版本迁移路径修复。

旧 `category.reordered` 必须先按候选记录声明的、明确受支持的旧 schema 验证。只有旧记录自身无歧义证明被移动 Custom 主体、移动前后两组有方向的自定义分类序列边界,以及每个存在邻居的分类 ID 与发生时用户原文名称,才能确定性迁移为 FORMAT-031 精确 `{ beforePosition, afterPosition }`。不得从升级时当前 `categoryOrder`、后来事件、历史重放、Inbox、绝对索引/rank/排序键或 `unavailable` 猜测缺失事实。未知字段、冲突或含混方向/主体/邻居、旧 schema 不允许的字段必须使候选迁移失败;当前 schema 中缺失/额外字段、错误联合、Inbox 或不可用邻居、主体自引、位置内重复邻居和相同前后位置不得复用旧版本迁移路径修复。

旧 `category.deleted` 必须先按候选记录声明的、明确受支持的旧 schema 验证。只有旧记录自身保存删除受理时原受影响活动任务数,或候选能够证明保留清理前完整无缺口的同操作 FORMAT-026 集合,才能确定性迁移为 FORMAT-032 精确 `{ affectedTaskCount }`。不得从升级时当前任务归属、当前 Inbox、剩余迁移事件数、最大 `eventOrder`、后来历史或默认 `0` 猜测;部分任务事件已经缺失且没有原计数时必须使候选迁移失败。当前 schema 中缺失、`null`、非 JSON 非负安全整数、任务列表或额外字段不得复用旧版本迁移路径修复。

### STORAGE-005 · 迁移失败回退

迁移失败时,候选新版本必须停止写入并按 `migration-rollback.md` 自动回退到 last-known-good 应用版本。不得通过删除数据库、重建空库或丢弃无法识别记录继续候选版本;回退旧版本可以继续对保留的旧 schema 正常读写。

### STORAGE-006 · 不降级到 localStorage

`IndexedDB` 初始化、事务或迁移失败时,应用不得把核心数据降级写入 `localStorage` 或其他非事务存储。

### STORAGE-007 · 内存待保存队列不是持久化后备

数据已加载后的正式任务、分类或历史业务事务失败可以按 `degraded-availability.md` 使用当前会话内存队列维持工作状态。自动清理、迁移工件清理等维护事务失败不得仅据此进入用户待保存队列。该队列不得被视为已持久化,不得在关闭或重载后承诺恢复,也不得扩展成第二个持久化事实源。

### STORAGE-008 · 草稿使用独立记录语义

快速创建草稿必须作为符合 `backup-format.md` FORMAT-015 逻辑语义的非任务记录保存在同一版本化数据库中。无论 object store、主键或索引如何设计,逻辑读取结果都必须且只能得到 `entry`、`generation`、`title` 与 `cursorOffset`,且每个语义入口最多一条当前非空记录;不得另存可与入口推导结果冲突的目标分类事实。草稿更新和明确清空不得追加任务历史;成功提交草稿时,任务创建、FORMAT-022 创建历史追加和入口与代次均匹配的草稿条件删除必须共享一个原子事务。创建详情只保存初始分类与创建后嵌套位置,不得复制草稿入口、代次或提交键。CATEGORY-012 的分类删除确认也只能在分类删除、任务迁移与既定历史的同一事务中条件删除冻结入口与代次匹配的草稿。两种路径都不得只按入口标识无条件删除草稿。

草稿写入失败后的最新内存快照必须遵守 `degraded-availability.md`;不得为草稿建立第二持久化后备,也不得把每次按键转换为正式任务操作。

主清单或任务分类选择器中的未提交分类名称不是快速创建草稿,只允许存在于当前输入状态,不得写入 `IndexedDB` 或待保存队列。只有 `task-categories.md` 定义的明确提交才能发起分类创建事务并追加历史。

### STORAGE-009 · 完整读取是开放写入的前置屏障

应用必须先成功初始化 `IndexedDB`,再完整读取当前 schema 要求的任务、分类、顺序、垃圾箱、历史、已使用操作顺序进度和快速创建草稿,之后才能建立可操作的已持久化状态。成功读取合法空库可以进入正常任务清单;初始化或任一必要读取失败不得被解释为空库。

首次安装时激活标记缺失只有在启动器能够确认不存在任何 Desktop Pull 数据库代次、候选工件或其他既有业务记录时才表示合法空白状态。此时可以创建首个数据库代次与对应激活标记,但仍须成功初始化并完整读取后才能开放产品。首次引导中断产生的工件必须可明确识别并幂等续建或清理;任何无法证明为空的记录都必须进入数据保护态。

完整读取之前发生非迁移故障时,应用必须按 ADR-008 进入启动数据保护态:不得显示可写空清单,不得接受任何核心修改、自动清理、完整备份导入或生成不完整备份。界面必须说明本地数据尚未加载且未被改写,自动重试并提供手动重试。

数据保护态不得创建内存临时工作区、写入其他存储、自动删除或重建数据库。只有同一核心数据库随后被完整读取后才能开放产品;此后的正式任务、分类或历史业务事务失败才可进入 `degraded-availability.md` 的可写降级态。

启动阶段完整读取已经成功、但随后到期清理事务失败时,可信读取屏障已经通过,不得把该失败解释为空库、读取失败或代次歧义。应用必须按 `degraded-availability.md` 的 AVAIL-016 从逻辑状态排除到期任务及其任务主体历史、把保留事件中所有 schema 已声明且指向目标的 FORMAT-021 `task` 分支整体投影为精确 `{ "kind": "unavailable" }`,并按 FORMAT-014 独立投影对应恢复锚点后继续启动;清理事务自身必须完整回滚,不得留下半删除或半替换。

同一活动窗口在回到前台或运行期执行自动到期清理时已经沿用该可信读取基线;清理事务失败必须同样完整回滚并按 AVAIL-016 逻辑隔离和去身份化引用投影,不得转入启动数据保护态或用户待保存队列。手动永久删除与迁移工件清理仍遵守各自契约。

Schema 迁移切换后还必须先确认持久化激活标记唯一选择兼容的数据库与应用版本,并按 `migration-rollback.md` 清理其他数据库代次,才能建立可信已持久化基线。无法确认时复用数据保护态。

### STORAGE-010 · 激活标记只选择数据库代次

Schema 升级的持久化激活标记只能保存活跃数据库代次标识、schema 版本、兼容应用版本和迁移状态,不得保存任务、分类、历史、草稿或其他业务记录。标记更新必须原子且可恢复:提交前中断继续选择旧代次,提交后中断确定性选择候选代次。

候选代次完成完整读取和应用启动验证前不得更新激活标记。标记选择候选后,旧代次与其他候选必须在任何核心写入前幂等清理;无法确定唯一代次或完成清理时按 STORAGE-009 停止写入。

首次安装建立首个激活标记是唯一没有旧代次可选的例外,且必须满足 STORAGE-009 的可证明空白前提。若标记缺失但存在任何无法确认为首次引导工件的数据库代次,不得新建空库或选择其中任一代次。

### STORAGE-011 · 窗口所有权不形成业务事实源

单活动窗口的排他所有权只能协调哪个运行实例可以加载和修改当前活跃数据库,不得保存任务、历史、草稿或待保存队列,也不得成为数据库内容的替代读取源。失去所有权必须使窗口停止全部核心访问并清除已加载工作状态。

候选迁移、永久清理和覆盖导入必须由活动窗口独占完成;普通网页标签页、窗口和已安装 PWA 共享同一存储作用域时不得分别写入数据库。

### STORAGE-012 · 不保存跨导入永久删除墓碑

核心数据库、激活标记、窗口协调状态、Service Worker Cache、OPFS、`localStorage`、`sessionStorage` 或其他本地与远程存储均不得保存已永久清理任务的墓碑、删除黑名单、内容指纹或外部备份索引。FORMAT-013 的通用 `UnavailableTaskRef` 不含任务身份、指纹或映射,不是任务特定墓碑且不得用于查找目标或阻止恢复。覆盖导入只以所选备份和 IMPORT-006 的当前到期过滤为输入,不得依赖第二事实源阻止删除前备份中的任务恢复。

### STORAGE-013 · 核心记录不持久化本地化系统文案

核心数据库中的固定系统分类、任务状态、`P0` 至 `P5` 任务优先级、精确事件类型、位置边界和 `UnavailableTaskRef` 必须保存稳定、语言无关的语义。`eventType` 必须且只能是 FORMAT-017 的 14 个精确值之一并匹配主体类型;动作组由精确事件类型唯一映射,不得保存本地化动作组文案。任务标题、备注、自定义分类名称及其历史快照必须保存用户原文。不得持久化由当前语言预渲染的系统显示名称、不可用文案、动作摘要或完整历史句子,也不得在语言切换时迁移或重写核心记录。

### STORAGE-015 · 核心任务语义符合精确生命周期

核心数据库中的逻辑任务必须完整表达 `backup-format.md` FORMAT-014 的七个公共字段和一个判别式生命周期,合计八个顶层字段;object store 拆分、物理键与索引仍由 D-092 的技术评审决定。任何物理布局都不得形成第二套活动分类或顺序事实源:活动任务的唯一当前归属与顺序只能由 `taskOrderByCategory` 对应的核心顺序状态表达,垃圾箱任务不得占活动顺序位置。

创建、实际内容编辑、状态、优先级、分类或顺序移动、软删除和恢复的原子事务必须用各自操作首次被工作状态接受时冻结的 `occurredAt` 更新直接受影响任务的 `updatedAt`;创建同时建立不可变 `createdAt`。重试、数据库提交、导入、导出、无变化操作和维护清理不得重新计时,相邻任务的被动位移不得改写其记录。软删除必须原子移除活动顺序并建立完整 `trashed` 生命周期;恢复必须只读取操作接受时当前 FORMAT-014 生命周期,原子删除全部垃圾箱专用字段、建立精确 `active` 生命周期、把原 ID 恰好一次放回活动顺序,并在同一事务追加 FORMAT-028 实际目标分类、未改变状态与插入后位置;不得改动或覆盖其他现存任务。

## 验收 Gate

- 检查持久化实现,确认全部核心记录只存在于 `IndexedDB`。
- 对一次任务变更注入事务失败,验证 `IndexedDB` 当前状态与历史都未写入,且待保存变更只存在于 `degraded-availability.md` 定义的当前会话队列。
- 对一次产生多条历史的操作分别注入事件或操作顺序进度写入失败,验证当前状态、全部事件和顺序进度要么全部提交,要么全部不提交。
- 从每个受支持旧 schema fixture 迁移到当前版本,验证任务、分类、顺序、垃圾箱和历史语义保持一致。
- 迁移含同时间与多事件操作的 schema fixture,验证 `occurredAt`、`operationSequence`、`eventOrder` 及下一操作顺序均保持稳定。
- 迁移包含垃圾箱任务及其删除历史的旧 schema fixture,验证当前垃圾箱生命周期的删除时分类进入 `categorySnapshotAtDeletion`,可恢复完成状态只读任务公共 `status`,前后位置转换为 FORMAT-014 严格锚点对象且生命周期没有状态副本或裸 ID;可无歧义迁移的 FORMAT-027 独立保留删除时分类、状态与带标题位置且不参与恢复。自定义分类用户原文不变,固定收件箱按当前语言显示且仍只按生命周期恢复。
- 持久化非空草稿后刷新或重启应用,验证 FORMAT-015 的语义入口、代次、标题原文及 UTF-16 光标偏移完整恢复;升级 schema 后验证这些值保持一致。
- 注入草稿提交事务失败,验证数据库中不会同时留下已创建任务和提交前草稿的半成功组合。
- 在旧代次草稿提交待保存期间写入同入口新代次草稿,验证旧提交事务不会删除新代次记录。
- 删除一个存在已确认草稿的分类,分别注入分类、任务迁移、历史、操作顺序进度或草稿删除写入失败,验证单个 `IndexedDB` 事务全部回滚;事务成功时只删除冻结入口与代次匹配的草稿,不产生草稿历史或额外顺序。
- 在分类删除确认打开后持久化同入口新代次草稿,验证旧确认不能删除新记录;分类删除已进入工作状态后重放旧草稿写入,验证活动窗口与代次约束拒绝复活已删除分类的入口记录。
- 分别让已确认入口在事务中变为另一代次、让无草稿入口在事务中出现草稿,验证前置条件失败会回滚所有 stores 与操作顺序进度并要求重新确认;只有已确认草稿仅在内存且入口没有换代时,匹配删除零行才可随分类删除成功。
- 构造数据库旧代次 `A` 与明确覆盖它的最新内存代次 `B`,确认 `B` 后验证分类删除事务清除同入口物理 `A`,不会保留悬空记录;全局、Inbox 与其他分类入口记录逐字不变,重复派发同一确认不产生第二次提交。
- 检查草稿 object store、索引和逻辑读取结果,验证每个语义入口最多一条非空草稿,目标分类只从入口推导,没有空记录、`null`、目标分类副本或按响应式形态拆分的第二记录。
- 在两处新建分类输入中键入但不提交后刷新或重开应用,验证名称未写入 `IndexedDB`、未进入待保存队列且不会恢复;明确提交后才出现分类及对应历史。
- 注入迁移失败,验证原数据库未被删除或重置,失败候选不写入,且 last-known-good 版本自动启动后可继续正常读写。
- 用含既有任务和历史的数据库注入初始化失败及分段读取失败,验证应用进入明确的数据保护态,不显示空清单、不开放任何核心修改、清理、导入或不完整导出,并说明本地数据未被改写。
- 在数据保护态检查全部存储写入,验证数据库未被删除或重建,且没有内存临时工作区、`localStorage` 或其他第二事实源;自动重试与手动重试均可触发重新完整读取。
- 恢复同一数据库访问后重试,验证原任务、顺序、垃圾箱、历史和草稿精确加载且没有额外状态或历史;随后注入正式任务业务事务失败,验证进入可写降级态而非返回启动数据保护态。
- 首次使用时成功初始化并完整读取合法空数据库,验证可以正常显示空任务清单;对照读取失败场景,确认实现没有仅凭“未读到记录”推断空库。
- 分别模拟全新存储、首次引导中断、激活标记丢失但既有代次仍在三种场景,验证只有可证明没有既有数据的前两种安全路径可以建立或续建空库,第三种进入数据保护且不创建竞争空库。
- 检查迁移代次与激活标记,验证标记不含任何业务记录、同一时刻只选择一个活跃代次,候选验证前不切换且切换中断后不会混合两个代次。
