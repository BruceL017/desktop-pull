# 系统架构边界(System Architecture Boundary)

## 第一版交付形态

- Desktop Pull 第一版是响应式 Progressive Web App(PWA)。
- 用户既可以把它作为普通网页打开,也可以安装到桌面或手机主屏幕。
- 完成一次成功加载后,核心任务路径在离线状态下仍可使用。
- 普通网页模式与已安装模式使用同一套任务数据语义和核心能力。
- 普通网页模式是基础入口,安装形态是增强能力;安装不可用或失败不改变同一浏览器网页模式的可用性。

## 正式支持范围

- Windows 11 正式覆盖 Chrome、Microsoft Edge、Firefox 网页模式及 Chrome、Microsoft Edge 安装模式。
- macOS 当前及上一受支持大版本正式覆盖 Safari、Chrome、Firefox 网页模式及 Chrome 安装模式。
- iOS 与 iPadOS 当前及上一受支持大版本正式覆盖 Safari 网页及主屏幕 Web App。
- Android 当前及上一大版本正式覆盖 Chrome、Firefox 网页模式及 Chrome 安装模式。
- Chrome 与 Firefox 使用当前及上一个 Stable 的滚动窗口,Microsoft Edge 使用当前及前两个 Stable,Safari 随 Apple 当前支持组合;每次发布候选记录实际验收版本。
- 其他官方安装形态可以兼容但不阻断 M1 发布;矩阵外环境不因 User-Agent 被硬拦截,也不获得正式可用性承诺。

## 系统边界

- 第一版的任务、分类、顺序和历史只保存在当前设备。
- 核心任务操作不依赖登录、服务端 API、云端数据库或持续网络连接。
- 原生移动 App、账号和跨设备同步不属于第一版架构。

## 客户端实现基线

- M1 使用 React 构建响应式界面,应用源码逻辑使用 TypeScript,Vite 负责开发与生产构建,既定顶层页面导航由 React Router 承担。
- React Router 只负责页面与导航状态,不得成为任务、分类、顺序、历史、草稿或设备偏好的事实源,路由与当前顶层页面也不进入 `IndexedDB` 或完整备份。M1 按 D-119 使用 Hash 历史;以 `/` 结尾的应用部署目录 URL 记为 `APP_BASE`,五个规范地址分别是 `APP_BASE + "#/"`、`APP_BASE + "#/history"`、`APP_BASE + "#/trash"`、`APP_BASE + "#/settings"` 与 `APP_BASE + "#/backup"`。
- 同一应用会话内的顶层页面切换写入浏览器历史,后退与前进按访问顺序切换页面。完整刷新、完全关闭后重开普通网页或 PWA,以及直接打开缺失、非任务或未知 Hash,都在呈现顶层页面前以 `replace` 回到任务路由并从清单顶部开始;M1 不恢复冷启动深链目标,运行期缺失或未知 Hash 同样归一化且不得形成返回循环。
- Manifest 启动地址解析到应用部署基址下的任务 Hash 路由。HTTP 请求始终命中同一静态应用文档,Hash 后路由由客户端解释,静态托管不需要子路径重写或业务服务端;子路径部署不得丢失应用基址。
- M1 是纯客户端 SPA。生产核心路径只依赖静态应用资源、浏览器能力与既定 Service Worker,不要求业务服务端、服务端渲染、远程 API、云数据库或联网许可检查。开发服务器和静态资源托管不属于业务服务端。
- React、React Router、中英文资源及其他核心运行时依赖必须作为离线应用资源交付,不得在运行时从 CDN 或其他网络地址加载后才能完成核心路径。
- M1 不安装 Capacitor,不创建 iOS / Android 原生工程,也不预建原生桥接、设备权限或持久化适配层。未来移动 App 可以优先评估把同一 Web 应用接入 Capacitor,但浏览器 `IndexedDB` 不因此被假定为可直接复用或搬迁;原生容器、存储、生命周期、窗口所有权、备份与权限必须届时重新决策。
- D-118 不指定依赖版本、包管理器、测试框架、状态库、样式方案、IndexedDB 封装或拖拽库;这些实现选择必须遵守任务包与技术评审边界,不得改变既定产品和数据契约。

## 状态与历史模型

- 任务、分类和顺序记录保存产品的当前真实状态,主界面直接读取当前状态。
- 逻辑任务以七个公共字段和一个判别式活动/垃圾箱生命周期表达,合计八个顶层字段。活动任务自身不保存分类或顺序副本,当前唯一归属与顺序只由权威分类任务顺序表达;物理 object store 或索引设计不得制造第二事实源。
- 每次成功变更在更新当前状态的同时,按每个实际主体事实追加对应审计事件;一项原子操作可以产生 FORMAT-017 规定的多事件集合。事件按任务或分类的真实主体形成七字段可判别逻辑结构并使用 14 值精确类型闭集;外层事件类型唯一选择事件专属最小严格详情,不得复制完整实体、通用整实体新旧包或第二根判别,分类管理不得伪造任务字段。`(operationSequence, eventOrder)` 是事件唯一稳定业务键,不另建事件 ID;私有 IndexedDB 物理键只属于实现,不得进入逻辑记录或备份。
- 当前状态更新与历史追加是同一个原子操作;任一部分失败时都不得留下半成品。
- 每次实际任务变化还在同一事务中以操作冻结的 `occurredAt` 更新直接受影响任务的 `updatedAt`;`createdAt` 只在创建时建立。补写、备份、无变化操作、维护事务和周围任务被动位移不重新计时。
- 数据已加载后的正式任务、分类或历史业务事务失败时,持久化状态保持不变;界面可以按 `availability-model.md` 叠加仅属于当前会话的有序待保存变更。维护事务失败遵守各自故障规则,不得伪装成用户待保存操作。
- 历史用于查看、筛选和解释变化,不用于重放并重建整份当前任务清单。
- 垃圾箱恢复读取软删除任务的当前记录;永久清理原子删除当前活跃数据库中的任务记录及其全部任务主体历史,并去身份化其他保留记录中的目标结构化邻居与恢复锚点,不连带删除无关历史或独立分类主体事件。后续新备份反映相同逻辑结果,但用户主动覆盖导入删除前备份可以恢复整个旧快照。
- 核心数据库完整读取后,启动、回到前台或运行期自动到期清理失败都不改变可信数据源角色:产品从逻辑工作状态立即排除到期任务及其任务主体历史,把保留记录中的目标结构化引用投影为不可用并继续提供日常功能,后台对同一活跃数据库幂等重试原子物理清理与去身份化。
- 第一版不采用事件溯源(Event Sourcing)。

## 本地持久化

- 任务、分类、顺序、垃圾箱、历史和跨重启快速创建草稿统一保存在浏览器 `IndexedDB` 中。草稿的可移植逻辑记录只含语义入口、不透明当前代次、标题原文与 UTF-16 光标偏移;目标分类从入口推导,不得形成第二事实源。
- 核心数据不得写入 `localStorage` 或 `sessionStorage`。
- 当前状态和历史使用同一个 `IndexedDB` 事务边界兑现原子一致性。
- 快速创建草稿不是任务且不产生历史;提交时以同一个事务创建任务、追加创建历史并按语义入口与代次条件删除草稿。删除自定义分类时,同一分类删除确认明确接受的草稿也在分类删除、任务迁移与既定历史的原子事务中按入口与代次消费,且旧内存重试不得复活。全局入口跨响应式形态保持同一身份,但不得与收件箱分类标题入口合并。
- 数据 schema 必须有显式版本;每次结构变化通过版本化迁移升级既有数据。
- 迁移失败时不得清空、重建或静默丢弃用户数据库。
- Schema 升级不得直接改写活跃数据库代次;候选版本先迁移一个不可承接用户业务写入的隔离副本并完成完整读取与启动验证,成功后才原子选择为新活跃代次。
- 任一时刻只有一个数据库代次可接受核心写入;候选失败时先清理副本再回到旧代次,候选成功时先清理旧代次再开放写入。
- 第一版提供完整的手动备份导出与导入,作为本地数据库的数据安全和迁移出口。
- 不同浏览器、用户配置文件及平台隔离的安装容器可能形成彼此独立的本地数据库。只有实际共享同一源站 `IndexedDB` 的实例才共享任务和设备偏好;独立作用域之间不自动复制、同步或合并,只能由用户通过完整备份迁移。
- 完整导入只执行经过校验和二次确认的原子覆盖;导入前先生成当前数据库的完整安全备份,不做数据合并。
- 第一版不为永久清理建立跨覆盖导入墓碑、删除黑名单或第二持久化事实源;产品也不查找或改写用户已经下载的备份文件。

## 写入故障可用性

- 正式任务、分类或历史业务事务失败不会立即把整个产品切成只读;契约明确允许入队的正式业务操作进入有序且明确标记的当前会话待保存队列,包括已确认但事务失败的分类删除。
- 启动、回到前台或运行期自动到期清理事务失败使用同一个独立的清理待完成状态,不伪造用户待保存操作;所有新备份基于已经排除到期内容并去身份化目标结构化引用的逻辑状态生成。
- 待保存队列不构成第二持久化数据库,不得写入 `localStorage` 或其他后备存储。
- 存储恢复后按原顺序提交待保存变更,再原子物理清理到期内容、目标主体历史和保留记录中的目标结构化引用;新的手动永久清理和覆盖导入仅在队列与清理待完成状态都清空后恢复。

## 同一存储作用域多窗口

- 共享同一源站存储的普通标签页、窗口和已安装 PWA 任一时刻只有一个活动窗口加载并操作核心数据。
- 非活动窗口不展示任务数据或维护只读镜像,只允许请求“在此窗口继续”。
- 正常移交必须先冻结原窗口、持久化最新有效编辑与草稿并完成进行中事务;新窗口取得排他控制权后重新完整读取数据库。
- 待保存状态存在时不得移交或跨窗口传递内存队列。原窗口关闭或崩溃后,新窗口只从持久化状态接管。
- 永久清理、覆盖导入和隔离候选迁移独占活动窗口,执行期间暂停移交。
- 失去所有权或进入非活动状态的窗口必须关闭核心数据库连接;BFCache 恢复先重新验证所有权,挂起但仍持有所有权的窗口不会被超时抢占。
- Service Worker 只管理应用资源、离线启动和不含业务记录的版本选择元数据,不得打开或操作核心业务数据库。

## 应用版本与 schema 迁移

- PWA 必须保留一个与当前数据库 schema 兼容、已经成功启动的 last-known-good 应用版本。
- 候选新版本从活跃数据库一致复制隔离代次,只在副本内迁移;完成新 schema 完整读取和无错误启动前,不得切换数据库或删除 last-known-good 应用资源。
- 迁移或候选启动失败会清理候选代次并自动启动 last-known-good 版本;旧活跃数据库维持原 schema 并继续完整读写。
- 验证成功后通过持久化原子标记同时选择候选数据库与兼容应用版本;旧代次必须在开放写入前清理,避免永久删除后仍残留旧副本。
- 修复版本后续从回退期间持续更新的最新活跃代次重新复制,不得复用失败候选或迁移首次失败时的旧业务快照。
