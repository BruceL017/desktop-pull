# 历史与恢复语义(History and Recovery)

## 历史时间线

- 历史事件明确区分任务主体与分类主体:任务变化以任务为主体,分类创建、重命名、排序和删除以分类为主体,分类事件不伪造任务字段。
- 每条可移植历史记录只使用 `subjectType`、`subject`、`eventType`、`occurredAt`、`operationSequence`、`eventOrder` 与 `details` 七字段公共外壳;任务和分类 `subject` 各自严格保存发生时身份与用户原文。外层 `eventType` 唯一判别一个事件专属最小严格 `details`,根部不重复 `kind`,也不复制完整任务/分类记录或通用整实体新旧快照;嵌套严格联合只在语义需要时使用自身判别。`(operationSequence, eventOrder)` 是唯一稳定逻辑键,不再建立事件 ID、动作组或本地化摘要字段。
- `category.created` 的公共分类 `subject` 已完整拥有不可变分类 ID 与创建时用户原文名称,因此 D-114 / FORMAT-029 的 `details` 必须存在且精确为 `{}`;缺失、`null`、数组、字符串或含任一字段都不是合法创建事件。位置、相邻分类、任务数量或标识、分类记录副本、界面入口、提交方式、设备和语言都不得重复写入。
- `category.renamed` 的公共分类 `subject.name` 保存改名后经统一名称规则处理的用户原文,D-115 / FORMAT-030 `details` 必须存在且精确为 `{ beforeName }`,其中 `beforeName` 是改名前保存的用户原文且必须与 `subject.name` 不同。不得重复 `afterName`、分类身份或记录、位置、相邻分类、顺序、任务、数量、入口、提交方式、设备和语言。
- `category.reordered` 的公共分类主体保存被移动 Custom 分类发生时 ID 与用户原文名称,D-116 / FORMAT-031 `details` 必须存在且精确为 `{ beforePosition, afterPosition }`;每个位置精确含 `{ previousCategory, nextCategory }`,前邻居只能是 `{ kind: "start" }` 或发生时 `{ kind: "category", categoryId, name }`,后邻居只能是 `{ kind: "end" }` 或同一严格分类分支。分类分支只能引用发生时 Custom 分类且不得引用 Inbox;`start` / `end` 只界定 Custom 序列。每个位置内可识别邻居 ID 必须互异且都不是主体,正常生产的前后位置必须不同;不存在 `unavailable` 分支,也不保存绝对索引、排序键、当前顺序、拖拽来源或完整分类记录。
- 每次已提交的新增、修改、移动、删除和恢复都按每个实际主体事实追加对应历史事件;一项原子操作可以形成既定多事件集合,例如选择器内创建分类后归入任务,或删除分类后派生逐任务迁移。
- 主清单独立创建只追加 `category.created(eventOrder = 0, details = {})`;选择器内创建并归入任务则在同一原子操作中先追加该分类事件,再追加 FORMAT-025 `task.category_changed(eventOrder = 1)`,且任务目标分类 ID / 名称与分类主体逐字一致。待保存队列、活动存储、普通或应急备份都只原样保留该 `{}`,不得在重试或物化时补入界面和当前状态。
- 自定义分类真实改名在同一原子操作中更新当前分类名称、推进一次操作顺序并只追加 `category.renamed(eventOrder = 0, details = { beforeName })`;分类 ID、分类顺序、任务顺序及所有任务事实保持不变且不追加任务事件。提交与当前名称相同的有效处理结果是完全无操作,不更新状态、不消费操作顺序也不形成历史。
- 自定义分类真实换位在同一原子操作中只更新 `categoryOrder`、推进一次操作顺序并只追加 `category.reordered(eventOrder = 0, details = { beforePosition, afterPosition })`;分类名称和 ID、全部任务顺序与任务归属 / 状态 / 内容 / 优先级 / 生命周期 / 时间保持不变且不追加任务事件。放回原位置是完全无操作,不更新状态、不消费操作顺序也不形成历史。
- 任务事件保存发生时任务标题及相关分类快照;分类事件保存发生时自定义分类名称。已锁定的创建、内容变化、完成、重新打开、优先级变化、组内排序与软删除事件都在事件专属详情中保存发生时 `CategorySnapshot`,任务后来移动、分类改名或删除都不会改变原分类筛选结果。`task.created` 还以 FORMAT-022 的嵌套 `position` 冻结创建完成后在初始分类未完成序列中的直接前后任务邻居;它不重复标题、时间、固定默认值或快速入口。`task.priority_changed` 还以 FORMAT-023 冻结不同的旧新优先级,但不保存位置、排序或控件来源。`task.reordered` 以 FORMAT-024 冻结一次语言无关状态及移动前后位置,分类和状态都不保存新旧对,也不保存拖拽来源、绝对序号或内部排序键。`task.category_changed` 以 FORMAT-025 冻结根部一次语言无关状态,并在 `source` / `target` 中分别保存发生时分类快照及移出前 / 插入后位置;两个分类身份必须不同,选择当前分类属于无变化且不产生事件。`task.trashed` 以 FORMAT-027 冻结删除时分类、未改变状态与移出前同状态直接位置,不复制标题、时间、内容、优先级或恢复锚点。用户输入的标题、备注与自定义分类名称按原文保存,后续修改或语言切换都不会回写旧事实;固定收件箱只保存稳定系统身份,不保存某一种语言的名称快照。`task.moved_to_inbox_by_category_deletion` 以 FORMAT-026 冻结一次状态、来源被删 Custom 分类与整批前位置、以及整批后最终 Inbox 位置;目标固定且不另存分类快照。
- `task.restored` 以 D-113 / FORMAT-028 精确冻结 `{ categorySnapshot, status, position }`:分类是任务实际插入后的目标,状态是未改变的公共 `open | completed`,`position` 是插入完成后同分类同状态序列的直接邻居。原 Custom 分类仍存在但已改名时保存同一标识及恢复时当前名称;原分类已删除时保存固定 Inbox 快照。该详情不复制删除上下文、生命周期、恢复锚点、锚点命中或回退原因、到期信息、界面来源、绝对位置或内部排序值。
- M1 精确事件类型是 14 值闭集:任务为 `task.created`、`task.content_changed`、`task.completed`、`task.reopened`、`task.priority_changed`、`task.reordered`、`task.category_changed`、`task.moved_to_inbox_by_category_deletion`、`task.trashed`、`task.restored`;分类为 `category.created`、`category.renamed`、`category.reordered`、`category.deleted`。未知、大小写变体和本地化值均无效。
- 十个任务事件与四个分类事件共 14 个事件详情分支已经全部锁定;14 值事件闭集和八个动作组不变。`category.deleted` 由 D-117 / FORMAT-032 精确锁定为 `{ affectedTaskCount }`:计数是删除接受时该分类活动权威顺序的任务总数,空活动分类为 `0`,垃圾箱任务、到期残留、历史旧归属与草稿不计入。
- 正常 N 项分类删除先保存 FORMAT-032 分类事件,再按来源总顺序保存 N 条 FORMAT-026 迁移事件;待保存重试冻结同一计数和批次。以后永久清理部分或全部迁移任务不会减少分类事件计数,现存任务事件可少于 N 甚至全部消失,但保留事件仍使用 `1...N` 内原操作顺序。计数只供发生时审计与双语呈现,不得重建当前任务、分类、顺序或迁移事件。
- 精确事件类型、完成状态、系统分类和位置边界使用语言无关语义码;14 个类型唯一映射到创建、内容编辑、完成状态、优先级、移动与归类、删除、恢复、分类管理八个动作组。分类创建只属于分类管理;内容编辑不按标题、备注或两者的组合拆类型。三个内容分支都保存发生时分类快照;只改标题时另存旧标题,新标题由保存后的任务主体标题表达;只改备注时另存备注新旧值;两者同时变化时合并这些变化字段,由字段存在性生成当前语言下的具体动作。完成与重新打开只另存发生时分类快照,状态方向由两个精确事件类型表达,不重复保存状态新旧值。优先级变化只保存发生时分类及不同的旧新值,修改不重排;重复选择当前值不产生历史。组内排序只保存一份发生时分类、一份状态及移动前后位置;原位、取消和无效放下不产生历史。跨分类变化只保存一份状态及来源、目标两侧的分类和位置;选择当前分类不产生历史。
- 分类筛选按结果归属解释:`category.renamed` 与 `category.reordered` 都只按公共 `subject.categoryId` 匹配;重命名搜索可同时命中 `details.beforeName` 与 `subject.name`,排序搜索可命中该事件公共主体及前后位置中的发生时 Custom 邻居名称。两者都不得查询当前分类、当前 `categoryOrder`、后来事件或重放历史推导名称或位置。FORMAT-025 `task.category_changed` 只按 `target.categorySnapshot` 归入目标分类,不得按 `source.categorySnapshot` 同时匹配来源分类,但仍完整保存并展示来源快照与位置;分类删除主体事件归入被删除分类,由此产生的 FORMAT-026 逐任务迁移事件只归入固定收件箱,其来源快照只供解释;FORMAT-027 软删除只按删除时 `categorySnapshot` 匹配,不按垃圾箱或恢复后的当前分类重算。筛选不读取任务后来当前归属、状态或顺序。
- FORMAT-028 恢复事件只按其中实际恢复目标 `categorySnapshot` 归入分类筛选;不得按 FORMAT-027 删除时分类、FORMAT-014 删除快照、垃圾箱或任务后来归属匹配。
- 直接跨分类拖拽与各种归类选择器都形成精确符合 FORMAT-025 的 `task.category_changed`,不保存界面来源;选择器按目标状态区顶部生成 `target.position`,拖拽按最终精确落点生成该位置,两者都以移出前来源位置和插入后目标位置记录同一业务事实。只有分类删除派生迁移使用独立 `task.moved_to_inbox_by_category_deletion`,并按 FORMAT-026 与对应分类删除共享操作、按来源总顺序排列且固定进入收件箱;来源位置取整批前状态,目标位置取整批完成后的最终状态,不得按状态拆批或记录逐项中间态。草稿输入、自动保存、明确清空及随分类删除确认丢弃草稿等行为不进入历史;折叠、筛选、导航、导入和备份导出等界面行为同样不进入历史。创建、删除和恢复也不因附带位置变化重复生成移动事件,永久清理不留新历史痕迹。
- 需要任务位置上下文的历史事件按 FORMAT-021 保存方向严格的任务邻居快照:前邻居只能是 `start`、`task` 或 `unavailable`,后邻居只能是 `end`、`task` 或 `unavailable`;`task` 分支精确为 `{ kind, taskId, title }`,其中标题是事件发生时用户原文。FORMAT-022 创建详情把两侧收束在精确 `{ previousTask, nextTask }` 位置对象中,只描述插入完成后的同分类未完成序列;连续创建后一条可以引用前一条,但不得回写先前事件。FORMAT-024 组内排序分别以同样的严格对象保存移出前与插入后位置,每个位置内双任务邻居不同且非主体,跨位置允许同一邻居重复。FORMAT-025 在 `source.position` 与 `target.position` 中各复用该严格对象;正常生产时四个槽位中仍为 `task` 的可识别 ID 必须跨侧两两不同且非主体,但来源与目标位置可以同为 `start / end`,因为不同分类已经证明真实变化。任务后来改标题、移动、改变完成状态或软删除都不回写该快照;只有永久清理、导入到期过滤、清理待完成逻辑投影或有效旧备份中已经清理的引用迁移才可产生不含身份的 `unavailable`,正常业务事件不得直接写入它。FORMAT-026 在整批前 `source.position` 与整批后 `targetPosition` 中复用同一严格对象;每个位置内部身份不同且非主体,但同一批次邻居可在来源与目标同方向重复,最终位置可引用更大 `eventOrder`。FORMAT-027 在软删除移出前单一 `position` 中复用同一对象,正常双任务邻居不同且非主体;它与 FORMAT-014 无标题恢复锚点只在删除事务发生时表达同一现场,但始终分型。多个区分邻居被去身份化使 FORMAT-024 两个位置、FORMAT-025 两侧多个槽位、FORMAT-026 来源与最终位置或 FORMAT-027 删除前位置收敛时仍是合法保留历史;同一批次邻居被清理时全部出现槽位一起去身份化。历史邻居只用于审计发生时位置,不得驱动当前顺序或垃圾箱恢复。界面按当前语言为 FORMAT-025 先显示“从来源分类移到目标分类”,只按 `target.position` 补充顶部、末尾或相邻对象;目标位置不可用时降级为中性跨分类移动文案,展开仍显示两侧完整位置,不展示内部排序值、容易失真的绝对序号或后来当前状态。
- FORMAT-028 在插入后的单一 `position` 中复用 FORMAT-021;正常双任务邻居不同且非主体。后来改名、移动、改变状态、软删除或再次恢复都不回写该位置;永久清理、到期过滤或清理投影对其中命中的每个嵌套 `task` 分支整体去身份化。FORMAT-028 只审计本次恢复实际结果,不得驱动当前顺序或任何之后的恢复。
- 正式操作进入工作状态时冻结操作时间与递增顺序;延迟补写保留原值,不会因数据库稍后恢复而伪装成刚发生的操作。
- 时间线按自然日与操作时间倒序浏览,同一时间用操作顺序稳定裁决;一次分类操作产生多条事件时先显示分类事实,再按操作前任务相对顺序显示关联任务事实。内部顺序号不向用户展示。
- 永久清理删除部分任务主体事件后可以留下操作内顺序缺口;历史、迁移和备份保留原逻辑键,不压缩或重编号。
- 在任务仍可恢复期间,历史只追加;执行恢复不会删除、改写或截断恢复操作之前或之后的记录。
- 恢复操作本身也会在状态恢复、实际落点插入和 `updatedAt` 更新的同一原子事务中追加一条精确 FORMAT-028 历史记录;失败不得留下活动任务或孤立恢复事件。
- 只要任务尚未永久清理,其任务主体历史就在当前设备无限期保留;分类主体历史在分类删除后也继续保留,两者都不按时间或记录数量自动截断。
- 用户不能单独删除某一条历史记录。
- 永久删除是唯一例外:任务内容及以该任务为主体的全部历史痕迹一并清除,其他保留记录中指向目标的结构化任务邻居和恢复锚点同步去身份化;无关任务、无关历史及不含任务身份的独立分类主体事件不被连带删除。

## 垃圾箱

- 删除任务是软删除:任务进入独立的垃圾箱,不立即销毁。
- 软删除把活动生命周期整体替换为带 `deletedAt`、`expiresAt`、删除时分类快照和双锚点的垃圾箱生命周期,并从活动顺序移除;任务公共标题、备注、状态与优先级继续保留且不在生命周期重复保存。同一事务追加 FORMAT-027 删除历史审计快照,但它不属于当前垃圾箱或恢复状态来源。
- 任务进入垃圾箱前必须经过阻断式确认弹窗;取消或关闭不会产生软删除、顺序变化或删除历史,但不会撤销确认前已经触发保存的有效编辑。
- 用户按任务逐个恢复,而不是把整个任务清单回滚到某个历史时刻。
- 任务从删除时刻起保留 30 天;到期后进入永久清理范围。
- 垃圾箱按最近删除优先展示删除时上下文,只提供直接恢复与经确认永久清理;任务内容和整理属性必须恢复后再修改。

## 恢复语义

- 恢复只把被删除的任务重新加入当前清单。
- 被恢复任务保留删除时的标题、备注、优先级、完成状态和原始创建时间。
- 恢复把垃圾箱生命周期整体替换为精确活动生命周期,移除全部删除专用元数据,复用原任务标识并只在权威活动顺序中加入一次;`updatedAt` 取恢复操作原始时间而 `createdAt` 不变。
- 当前垃圾箱展示与恢复所读的删除时分类保存为 FORMAT-014 `CategorySnapshot`,当前完成状态只读任务公共 `status`,前后位置使用方向明确的恢复锚点对象;其 `task` 分支只含 `{ kind, taskId }`,不复制标题,生命周期也不另存状态副本或裸任务 ID。FORMAT-027 另保存同值分类和状态及带发生时标题的 FORMAT-021 位置,只用于历史审计。两种位置分型且不得互换,恢复只能读取生命周期锚点;锚点或历史邻居任务后来永久清理时,对应分支分别变为不含身份的 `unavailable`。
- 恢复算法只读取操作被接受时的当前 FORMAT-014 生命周期与任务公共状态,不得读取 FORMAT-027 或 FORMAT-028、重放历史或从当前其他事实反推删除现场。算法算出实际目标与落点后,同一原子操作追加 FORMAT-028;该历史详情是结果审计,不是定位输入。
- 原分类仍存在时,任务按双锚点、前锚点、后锚点、同状态序列末尾的顺序,合并到最接近原位置的有效位置;不可用锚点按无效处理,先尝试另一锚点再回退。分类后来改名仍视为同一分类。
- 原分类已删除时,任务恢复到收件箱对应完成状态序列末尾,不会重新创建已删除分类。
- 原分类仍存在但已改名时,恢复继续使用同一分类标识,FORMAT-028 的 Custom 快照保存恢复时当前名称;原分类已删除时,FORMAT-028 保存固定 Inbox 快照。两条路径都记录插入后的实际同状态邻居,而不是删除前位置或回退原因。
- 恢复不会覆盖恢复点之后新增或修改的其他任务;被恢复任务与当前任务状态共存。
- 恢复只插入原任务,不移动当前任何其他任务,也不创建副本。
- 恢复后的后来任务修改、移动、状态变化、分类改名或删除都不得回写既有 FORMAT-028;该事件与后来事实共存。
- 创建、内容、状态、优先级、分类或顺序、软删除与恢复都只用各自原始操作时间更新直接受影响任务;重试和周围任务被动位移不得改写时间。
- 恢复成功不强制离开垃圾箱;用户可以继续恢复其他任务,也可以从非阻断反馈主动查看并定位刚恢复的任务。
- 恢复资格以操作被工作状态接受的时刻为准:到期前接受的恢复即使待保存期间跨过 30 天也继续有效,先于到期清理提交;到期时或之后才发起则不形成操作。未补写且未应急导出便终止会话时,仍承担待保存恢复丢失的既定风险。
- 到期前接受但待保存的恢复必须冻结其已计算的实际 FORMAT-028 `{ categorySnapshot, status, position }`;重试、跨过到期点或应急备份物化不得重读锚点、重算落点或改写邻居标题。

## 永久清理

- 应用运行期间自动清理已删除满 30 天且没有在到期前接受恢复的任务。
- 应用关闭期间到期的任务,在下次启动或回到前台时、展示或恢复任务交互之前尝试物理清理;运行期间任务达到 `expiresAt` 时自动清理。可信数据库基线下任一自动清理事务失败,都必须立即从全部产品视图和新备份逻辑排除目标任务及其任务主体历史,并把保留记录中的目标结构化引用投影为“不可用”后继续使用。
- 自动清理失败期间产品持续提示尚有本地物理残留并自动、手动重试,契约允许的日常操作继续可用;新的手动永久清理、清空垃圾箱和覆盖导入暂停。
- 自动清理必须幂等:重复执行不会产生额外变化、重复记录或错误。
- 用户可在 30 天内手动永久删除单个任务或清空垃圾箱;两种操作都必须二次确认。
- 清空垃圾箱确认时冻结目标集合;后来进入垃圾箱或确认前已恢复的任务不会被连带销毁,其余目标任务、各自全部任务主体历史及集合外保留记录中对目标的结构化引用整批原子清理或去身份化。
- 自动或手动永久清理都会从当前活跃数据库销毁任务内容及其全部任务主体历史痕迹,把其他垃圾箱恢复锚点中的 FORMAT-014 `task` 分支和包括 FORMAT-028 恢复后位置在内的历史 FORMAT-021 `task` 分支分别整体、原子替换为精确 `{ "kind": "unavailable" }`,同步移除目标 ID 及历史邻居标题,后续新备份反映相同结果;分类管理事件只保留发生时分类名称和汇总事实,不保留或泄露已清理任务身份,尤其不得删除或改写不含任务引用的独立 `category.created(details = {})` 与 `category.renamed(details = { beforeName })`。不得全文擦除偶然含有同一 UUID 或标题的用户自由文本,也不得为该动作新增历史或消耗操作顺序。
- 用户此前保存到产品外的删除前备份不受当前永久清理修改。用户主动覆盖导入有效删除前备份时,其中任务与当时历史可以随完整快照重新进入当前数据库;第一版不保留跨导入墓碑或删除黑名单。
- 永久清理确认必须区分“当前数据库与新备份中不可恢复”和“删除前备份仍可能保留并重新带回内容”,不得作出销毁所有副本的承诺。

## 第一版不提供

- 不提供整份任务清单的历史快照回滚。
- 不允许一次恢复覆盖恢复点之后的有效任务或修改。
