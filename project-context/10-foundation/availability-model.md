# 可用性与待保存状态(Availability Model)

## 术语

- 健康态:当前没有待保存变更或待完成到期清理,核心写入能够由 `IndexedDB` 原子提交。
- 已持久化状态:已经写入 `IndexedDB` 的当前状态和对应历史,是跨会话事实源。
- 待保存变更:用户已在当前会话完成、界面已经应用,但尚未成功写入 `IndexedDB` 的契约允许入队的正式业务操作及其历史意图。
- 待保存草稿快照:某一快速入口尚未成功写入 `IndexedDB` 的最新草稿;后续输入可覆盖此前快照,且没有历史意图。
- 可写降级态:数据已成功加载后,因正式任务、分类或历史业务事务失败而显示“已持久化状态 + 有序待保存变更”的当前会话工作状态。
- 草稿局部待保存:只有草稿持久化失败、正式任务、分类与历史业务事务尚未失败时的入口级状态;它不等于全局可写降级态。
- 启动数据保护态:应用尚未成功初始化并完整读取核心数据库,因而没有可信已持久化基线时的只恢复、不写入状态。
- 清理待完成态:核心数据库已经完整读取,但到期任务、其任务主体历史及保留记录中的目标结构化引用尚未完成物理清理或去身份化;目标内容已从产品逻辑状态排除,保留引用已投影为“不可用”,日常操作继续可用。

## 适用边界

- 第一版可写降级只处理数据已经成功加载后的正式任务、分类或历史业务事务失败;自动清理、迁移工件清理等维护事务遵守各自 ADR 或开放项,不得仅据此进入用户待保存队列。
- 核心数据库完整读取后,启动、回到前台或运行期自动到期清理失败都按 ADR-014 进入清理待完成态,不因清理失败本身建立用户待保存队列。只有启动触发需要额外裁决其不属于启动数据保护态。
- 应用更新引起的 schema 迁移失败通过最近一次已验证应用版本回退处理。
- `IndexedDB` 因迁移之外的原因无法初始化或完整读取时,按 ADR-008 进入启动数据保护态,不得误用可写降级态。

## 启动数据保护

- 只有成功初始化并完整读取当前 schema 所需核心数据后,应用才能建立已持久化状态并开放任务、历史、垃圾箱和备份操作。首次安装须先证明不存在任何既有数据库代次或候选工件,才能建立合法空数据库;读取失败或标记缺失本身不得被解释为空库。
- 数据保护态不得显示可写空清单,不得接受创建、编辑、状态、优先级、分类、拖拽、删除、恢复、永久清理或自动清理,也不得执行完整备份导入。
- 因核心数据尚未完整读取,数据保护态不得生成声称完整的备份导出。应用必须保留恢复界面,明确说明本地数据尚未加载且未被改写,持续自动重试并提供手动重试。
- 数据保护态不建立内存待保存队列、临时任务清单或第二持久化事实源,也不得自动删除、重建或覆盖现有数据库。
- 完整读取成功后才能离开数据保护态。随后启动到期清理成功时进入健康态;启动到期清理失败时按 ADR-014 建立逻辑排除后的清理待完成态;回到前台或运行期触发同类失败时复用该状态;日常业务写事务之后失败时才进入既定可写降级态。

## 自动到期清理写入失败

- 应用必须从可信工作状态与触发时刻推导仍为软删除的到期任务。启动时在任何产品数据可见前、回到前台时在恢复交互前、运行期在任务达到 `expiresAt` 时,把这些任务、任务内容及其任务主体历史排除出逻辑工作状态,并把保留记录中指向目标的结构化任务邻居与恢复锚点投影为不含身份的“不可用”。到期前已接受的恢复不属于目标,独立分类主体事件不因此排除。
- 物理清理事务失败不阻断创建、编辑、状态、优先级、分类、拖拽、软删除和未到期恢复。后续业务写入成功时正常落盘;失败时才按可写降级规则进入有序待保存队列。
- 所有主视图持续显示非阻断的清理待完成状态,说明到期内容尚未从当前设备物理清除、已经在产品中隐藏并正在自动重试,同时提供手动重试。
- 清理待完成态不产生任务历史、操作顺序或待保存数量。它可以与可写降级态重叠,但两种状态必须分别表达物理残留风险与用户操作丢失风险。
- 清理待完成期间暂停新的单任务永久清理、清空垃圾箱和完整备份覆盖导入。完整备份导出继续可用,但必须从逻辑状态生成,排除到期任务及其任务主体历史并物化同一引用去身份化投影。
- 没有正式待保存队列时持续幂等重试物理清理;一旦出现正式待保存队列,必须先停止清理并按原顺序补写用户操作,再基于补写后的状态重新计算并清理到期目标。

## 更新迁移回退

- 新版本尝试 schema 迁移前,最近一次已成功读取并使用旧 schema 的应用版本必须作为 last-known-good 版本保留在设备上。
- 迁移只能作用于从活跃数据库一致复制的不可写候选代次;活跃代次在候选完成完整读取和启动验证前保持不变。
- 迁移、候选完整读取或候选启动失败时,失败版本停止所有核心写入并退出启动流程;候选工件清理后,应用自动启动 last-known-good 版本并继续使用原数据库代次。
- 回退版本继续提供完整功能并正常写入旧 schema,不把用户限制在只读或恢复页面。
- 同一失败版本不得在每次启动时重复触发迁移;只有修复后的不同应用版本再次尝试。
- 修复版本迁移时必须包含用户在回退期间产生的最新任务与历史。
- 候选验证成功后才能原子切换数据库代次;旧代次与其他候选必须在开放任何写入前清理。激活或清理状态不确定时进入启动数据保护态。

## 活动窗口边界

- 同一存储作用域只有一个窗口可以加载核心数据并持有正式待保存队列或草稿待保存快照;其他窗口不维护持久化状态、工作状态或只读镜像。
- 正常移交前,活动窗口立即处理最新有效编辑和草稿。只有全部内容成功持久化、队列为空且敏感事务结束后才能释放控制权。
- 任一待保存状态都会暂停移交,且不得跨窗口传输或合并。活动窗口关闭或崩溃时,新窗口只从持久化状态接管,原窗口未导出的内存变更继续承担既定丢失风险。

## 降级行为

- 创建、编辑、状态与优先级修改、分类操作、拖拽、软删除和恢复继续作用于当前会话工作状态。
- 每次待保存变更在进入工作状态时冻结自己的历史意图、操作时间与稳定顺序,不得因重试而重新计时、合并、重排或重复。
- 草稿写入失败不阻断输入;每个语义入口只保留一个包含入口、当前代次、标题原文和 UTF-16 光标偏移的最新待保存草稿快照并自动重试,不把每次按键放入正式操作队列。
- 草稿提交会按语义入口与代次把当前快照消费为正式任务创建操作;输入框清空后的文字属于新代次。恢复时先提交旧任务创建,再保存新草稿,且旧代次消费不能删除新代次。
- 删除自定义分类时,用户在同一分类删除确认中明确接受丢弃的草稿代次随分类删除操作从工作状态消费;分类删除事务失败则整体进入一项待保存操作,并在首次进入工作状态时冻结 FORMAT-032 `affectedTaskCount`、同批 FORMAT-026 事件集合及稳定顺序。计数包含受理时实际迁移的未完成与已完成活动任务,不含垃圾箱、逻辑到期物理残留、历史引用或被消费草稿;空分类为 `0`。应急备份物化分类已删、任务已迁移、原计数与顺序保持且草稿不存在。对应内存快照、重试和旧回调立即失效,不得迁移、建任务、生成草稿历史、重算计数或在已删除分类下复活。
- 只有草稿写入失败时仅在对应入口显示未保存、重试、风险和应急导出;不因草稿本身显示全局降级状态或新增对永久清理、清空垃圾箱和覆盖导入的限制,也不解除清理待完成、迁移等独立状态已有的提示和限制。正式业务事务随后失败时才升级为全局可写降级态。
- 未产生实际工作状态变化的操作不进入待保存队列。
- 存在正式待保存变更时,全局界面持续显示未安全保存状态并后台自动重试;产品不得把待保存变更描述为已经保存。
- 用户可以导出由已持久化状态、全部待保存变更和最新待保存草稿快照组成的应急完整备份;到期前已经接受的待保存恢复按工作状态物化为活动任务。
- 单任务永久清理、清空垃圾箱、自动永久清理和完整备份导入在降级期间暂停。
- 垃圾箱任务是否可恢复只在恢复操作进入工作状态时检查。到期前已经接受的待保存恢复继续有效并进入应急备份;没有及时恢复的任务达到 `expiresAt` 后立即失去发起新恢复的资格并从可恢复视图隐藏,仅物理销毁延后到存储恢复。

## 恢复与会话边界

- 存储恢复后,待保存变更按原顺序逐条提交;每条状态变化与对应历史仍使用同一个原子事务,历史继续使用操作最初进入工作状态时的时间与顺序而非补写时间。到期前接受的恢复必须在到期清理之前提交。
- 只有全部待保存变更成功提交、再基于补写后的当前状态完成到期永久清理后,产品才回到健康态并重新开放单任务永久清理、清空垃圾箱、自动永久清理和完整备份导入。没有待保存队列但仍处于清理待完成态时,同样必须等待物理清理成功。
- 第一版不为待保存队列引入 `localStorage`、OPFS、Service Worker Cache 或远程服务等第二持久化后备。
- 若应用在补写前关闭、崩溃或重载,内存队列和最新草稿快照会丢失;已完成应急导出时可通过该文件恢复,否则待保存变更或最新草稿可能不可恢复。这项风险必须在对应未保存状态中持续可见。
