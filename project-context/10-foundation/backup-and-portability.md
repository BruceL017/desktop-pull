# 备份与可移植性(Backup and Portability)

## 第一版能力

- 用户可以手动导出当前设备上的完整 Desktop Pull 备份。
- 用户可以把完整备份导入 Desktop Pull,用于恢复本地数据或迁移到另一设备环境。
- 不同浏览器、浏览器用户配置文件和被平台隔离的安装容器可能拥有独立 `IndexedDB`;完整备份也是这些本地存储作用域之间唯一的第一版迁移路径,产品不自动复制、同步或合并数据。
- 完整备份包含仍在保留范围内的任务、分类、持久顺序、带删除时分类与恢复位置快照的垃圾箱状态、全部保留中的任务主体与分类主体历史及其用户原文快照、语言无关系统语义、各事件实际存在的精确字段事实、操作时间与稳定全序,以及非空快速创建草稿;每条草稿精确保留语义入口、当前代次、标题原文与 UTF-16 光标偏移,目标分类只从入口推导,导入后仍不属于任务或历史。仍为软删除且已经到期的任务及其任务主体历史不得进入新备份,保留记录中对这些目标的结构化任务引用必须成为不含身份的“不可用”,即使物理清理暂时失败。
- `data` 使用独立于 IndexedDB 物理布局的七个逻辑字段:`meta`、`categories`、`tasks`、`categoryOrder`、`taskOrderByCategory`、`drafts` 和 `history`。固定收件箱不伪装成自定义分类;分类顺序和活动任务唯一归属及总顺序分别由两套明确顺序数组表达,完成状态只投影该总顺序,垃圾箱任务不占活动位置。
- 任务与自定义分类使用跨备份不变的规范小写 UUID v4,但产品顺序和时间不得从 UUID 推导。当前分类引用以 `inbox` / `custom + categoryId` 判别,不使用名称或特殊标识冒充收件箱;历史及删除上下文的分类语义快照与当前引用分型。备份中所有时间统一为 UTC 固定毫秒精度并原样往返。
- 当前自定义分类记录只保存 ID 与名称,分类顺序由完整 ID 数组单独表达。收件箱和每个自定义分类都具有一个显式活动任务总顺序分组,空分组不省略。历史与垃圾箱的 Custom 分类快照可以指向已改名或删除分类并保留发生时名称;Inbox 快照不保存名称。
- 每条备份任务精确保存七个公共字段和一个判别式生命周期,合计八个顶层字段。活动任务不重复保存分类或顺序;垃圾箱任务只在生命周期保存删除时间、到期时间、删除时分类快照与双锚点,公共内容、状态和优先级不建立副本。无备注精确为 `""`,状态精确为 `open` / `completed`;FORMAT-014 恢复锚点使用严格对象联合,其中任务分支只含 `kind` 与 `taskId`,另有方向边界或永久清理后的通用不可用分支。
- 每条备份草稿精确保存 `entry`、`generation`、`title` 与 `cursorOffset` 四个字段。全局入口和收件箱分类入口保持独立,同一语义入口最多一条记录;代次采用不透明小写 UUID v4,纯空白标题仍原样保留,光标偏移统一按 UTF-16 code unit 解释。分类删除确认按入口与代次消费的草稿不再进入健康态或待保存应急备份,且不得留下悬空自定义分类入口。
- 每条备份历史精确保存 `subjectType`、`subject`、`eventType`、`occurredAt`、`operationSequence`、`eventOrder` 与 `details` 七个顶层字段。`subject` 按任务或分类严格保存发生时 ID 与用户原文,`eventType` 只能使用 FORMAT-017 的 14 值闭集并唯一判别 FORMAT-018 的事件专属最小严格 `details`,`eventOrder` 是同一操作内唯一的 JSON 非负安全整数;`(operationSequence, eventOrder)` 是唯一稳定逻辑键,不另存事件 ID、动作组、本地化摘要、界面来源、根级详情判别、完整实体快照或通用整实体新旧包。`task.content_changed` 由 FORMAT-019 锁定三个带发生时 `categorySnapshot` 的精确分支,标题新值只存于保存后 `subject.title`;`task.completed` 与 `task.reopened` 由 FORMAT-020 锁定只含发生时 `categorySnapshot` 的详情,状态方向只由类型表达。FORMAT-021 锁定历史任务前邻居为 `start | task | unavailable`、后邻居为 `end | task | unavailable`,其中 `task` 精确保存 `kind`、`taskId` 与发生时 `title`。`task.created` 由 FORMAT-022 锁定只含初始 `categorySnapshot` 与嵌套 `position` 的详情,位置以创建完成后未完成序列中的前后 FORMAT-021 邻居表达。`task.priority_changed` 由 FORMAT-023 锁定只含发生时 `categorySnapshot` 及不同的 `beforePriority` / `afterPriority`,不保存位置、排序键或控件来源。`task.reordered` 由 FORMAT-024 锁定一份发生时 `categorySnapshot`、一份 `open | completed` 状态及严格 `beforePosition` / `afterPosition`,不保存拖拽来源、绝对索引、内部排序键或当前顺序。`task.category_changed` 由 FORMAT-025 锁定根部精确 `{ status, source, target }`,状态只保存一次,来源与目标分类引用必须不同,两侧各以 `{ categorySnapshot, position }` 冻结发生时分类和同状态直接邻居;来源位置取主体移出前,目标位置取插入后。正常四槽可识别任务 ID 跨槽两两不同且非主体,正常生产不得使用 `unavailable`;来源与目标位置结构相同仍可合法。不得保存拖拽、任务行、编辑器或新建分类入口,也不得保存绝对索引、内部排序键或当前顺序。`task.moved_to_inbox_by_category_deletion` 由 FORMAT-026 锁定根部精确 `{ status, source, targetPosition }`,来源只含被删 Custom 快照与整批前位置,目标只含整批后最终 Inbox 位置且不重复固定目标快照;任务事件按来源权威总顺序,批次邻居可在来源与目标同方向重复,最终位置可引用更大 `eventOrder`。`task.trashed` 由 FORMAT-027 锁定根部精确 `{ categorySnapshot, status, position }`,只冻结删除时分类、未改变状态和移出前同状态直接邻居;删除时间、主体标题、内容、优先级与无标题恢复锚点仍由既有字段唯一承担,历史位置不得参与恢复。`task.restored` 由 FORMAT-028 锁定根部精确 `{ categorySnapshot, status, position }`,逐值冻结恢复事务完成后的实际目标分类、未改变状态和插入后同状态直接邻居;原 Custom 分类仍存在时使用同一 ID 与恢复时当前名称,已删除时使用固定 Inbox 快照。该详情不重复删除上下文、生命周期、锚点、锚点命中或回退原因、30 天字段、UI/设备来源、绝对索引或内部排序值,且只供审计,不得参与之后的恢复或当前顺序。`category.created` 由 FORMAT-029 锁定必填精确空对象 `{}`;分类不可变 ID 与创建时用户原文名称只在公共 `subject`,不得在详情重复身份、名称、位置、入口、任务关联或默认值。主清单创建只产生该事件 `(eventOrder = 0)`;选择器创建并移动任务时同一原子操作先写该事件 `(eventOrder = 0)`,再写 FORMAT-025 任务事件 `(eventOrder = 1)`,目标分类身份逐字一致。关联任务后来永久清理或逻辑到期时,其任务主体历史消失而独立分类创建事件继续以原顺序保留;不得补建任务事件,反向孤立的 `task.category_changed(eventOrder = 1)` 非法。`category.renamed` 由 FORMAT-030 锁定必填精确 `{ beforeName }`;公共 `subject` 保存同一分类 ID 与改名后用户原文名称,`beforeName` 保存改名前存储的用户原文且必须与 `subject.name` 不同。两端名称都按 CATEGORY-011 规则校验,详情不得重复新名称、分类身份、位置、任务、入口或其他字段;同一有效当前名称不形成事件或消耗操作顺序。成功改名只原子更新当前分类名称、推进一次操作顺序并写入唯一 `category.renamed(eventOrder = 0)`,不改变分类 ID、`categoryOrder`、`taskOrderByCategory`、任务或任务历史。永久清理留下的操作内缺口不重编号;多个邻居去身份化使 FORMAT-024 前后位置、FORMAT-025 两侧位置、FORMAT-026 来源与最终位置、FORMAT-027 删除前位置或 FORMAT-028 恢复后位置收敛时仍保留合法事件;FORMAT-026 同一邻居跨侧重复时全部出现槽位一起投影,迁移主体清理后任务事件数量可以少于分类事件原受影响数量并保留顺序缺口。`category.deleted` 由 FORMAT-032 锁定精确 `{ affectedTaskCount }`,保存删除受理时实际从被删分类迁入 Inbox 的活动任务总数;14 个事件类型的精确详情分支均已锁定。
- `category.reordered` 由 FORMAT-031 锁定必填精确 `{ beforePosition, afterPosition }`,每个位置精确只含 `previousCategory` 与 `nextCategory`。前邻居只能为 `{ kind: "start" }` 或发生时 Custom 分类快照 `{ kind: "category", categoryId, name }`,后邻居只能为 `{ kind: "end" }` 或同一快照分支;分类 ID 使用规范小写 UUID v4,名称保留发生时用户原文。`start` / `end` 只表示自定义分类序列边界,固定 Inbox 永不成为邻居;公共 `subject` 已保存被移动 Custom 分类,详情不得重复主体。在每个位置内,可识别邻居 ID 必须不同且均非主体;正常生产的前后位置必须不同,原位放下是完整 no-op。成功排序只原子改变 `categoryOrder`、推进一次操作顺序并写入唯一 `category.reordered(eventOrder = 0)`,不得改变任何分类名称、任务归属/顺序/内容/状态/优先级/生命周期/时间或生成任务事件。详情不允许 `unavailable`、绝对索引、rank、排序键、`categoryOrder` 副本、拖拽/UI/设备/语言元数据或通用实体 `before` / `after`;后续改名、排序或删除主体及邻居不回写快照,历史筛选与搜索只读事件公共主体和已存邻居名称,不得查询当前分类或重放历史。
- `category.deleted` 由 FORMAT-032 锁定必填精确 `{ affectedTaskCount }`。`affectedTaskCount` 是删除受理时被删 Custom 分类活动总顺序中实际迁入 Inbox 的任务数,同时计入未完成和已完成任务,不计垃圾箱任务、逻辑到期物理残留、历史引用或随确认消费的未提交草稿;必须是 JSON 非负安全整数,且 `0` 合法。正常生产中同一操作先写分类事件 `eventOrder = 0`,再按来源权威总顺序写恰好该数量的 FORMAT-026 任务事件 `eventOrder = 1..N`。任务主体后来永久清理或导入时到期过滤可以使剩余任务事件少于该值并留下顺序缺口,但分类事件与原计数保持不变;详情不得保存任务清单、任务身份/标题、状态拆分、分类身份/名称、目标 Inbox、位置、确认/草稿/UI/设备或原因。
- FORMAT-021 历史任务邻居与 FORMAT-014 垃圾箱恢复锚点不得互换:前者的任务分支保留发生时标题并只解释历史位置,后者不复制标题并只参与恢复落点。FORMAT-031 分类邻居同样是独立严格联合,不得与前两者串型。FORMAT-028 的 `position` 是恢复完成后的审计结果,恢复算法仍只读取操作接受时当前 FORMAT-014 生命周期。任务后来改标题、移动、改变完成状态或软删除不回写历史邻居;历史邻居也不得驱动当前顺序或恢复。
- 任务 `createdAt` 永远保留创建操作时间;`updatedAt` 保留最近一次实际任务变化的原始操作时间。导出、导入、待保存重试和数据库提交不得重新计时,维护清理与周围任务被动位移也不得推进该值。
- 备份中的系统分类、任务状态、精确事件类型、事件类型到动作组的映射和位置边界不得依赖导出时界面语言。固定收件箱保存稳定系统身份;任务标题、备注、自定义分类名称及其历史快照保留用户原文。相同备份在简体中文或英文界面导入后恢复同一业务事实,只由当前界面语言决定系统文案呈现。
- 当前设备的语言偏好、分类与“已完成”折叠状态等界面偏好不进入完整备份,也不属于跨设备恢复承诺。
- 完整覆盖导入成功后清除导入前折叠偏好,导入分类默认展开且“已完成”默认折叠,但继续使用当前设备语言;未成功导入时偏好不变。
- 备份导入与导出不依赖账号、服务端或云存储。

## 导入语义

- 第一版只支持用完整备份覆盖当前本地数据库,不支持把备份与现有数据合并。
- 覆盖前必须完整校验备份格式、版本和记录关联,并向用户展示待导入数据摘要。
- 覆盖前必须先为当前数据库生成一份完整安全备份,再要求用户二次确认。
- 覆盖操作必须在同一事务中替换全部核心数据,排除导入时已经到期的垃圾箱任务及其任务主体历史,并把保留记录中对这些目标的结构化引用去身份化;FORMAT-021 中指向这些目标的整个 `task` 分支原子替换为精确 `unavailable`,不得残留 ID 或标题。独立分类主体历史和无关记录不因某个任务到期而排除。校验、备份生成、到期过滤、引用替换或写入任一步失败时,当前数据库保持不变。
- 导入校验必须先要求 FORMAT-021 的 `taskId` 解析到原文件 `tasks` 中另一条任务,包括随后会因导入执行时已经到期而被过滤的垃圾箱任务;该任务已经移动、改标题、改变完成状态或处于垃圾箱仍可合法解析,发生时 `title` 也无需等于当前标题。只有原文件完整校验通过后才能执行到期过滤及原子投影,不得用 `unavailable` 掩盖未知引用、自引用、方向错误或其他损坏。
- 导入保留备份中的任务标识、时间、分类、顺序、垃圾箱删除上下文与恢复位置,以及任务主体和分类主体历史的七字段外壳、语言无关系统语义、用户原文快照、事件专属且实际存在的完整精确字段事实、稳定逻辑键与全序;FORMAT-022 创建分类与位置、FORMAT-025 主动跨分类来源/目标/状态/位置、FORMAT-026 分类删除派生迁移的来源整批前和最终 Inbox 位置、FORMAT-027 软删除的删除时分类/状态/移出前位置、FORMAT-028 恢复后的实际分类/状态/插入后位置、FORMAT-029 分类创建精确 `{}` 与公共分类主体,以及 FORMAT-030 分类改名前 `details.beforeName` 和改名后公共 `subject.name` 都不得按导入后当前状态重算;FORMAT-026 也不得按事件顺序重放或用当前 Inbox 尾部重建,FORMAT-027 不得与任务当前生命周期对质或从 FORMAT-014 无标题锚点补造,FORMAT-028 不得作为恢复或当前排序输入,也不得与导入后的当前归属、状态或位置交叉校验。导入先校验原文件中全部正常 FORMAT-021 任务引用,再执行到期目标投影;当前分类记录和 `categoryOrder` 只取导入文件当前状态,不得重放分类创建、改名或排序历史补建、改名或重排分类;不得重放任务历史、拿当前归属或顺序对质发生时快照、生成事件 ID、整实体新旧快照或压缩操作内缺口。后续分类改名、排序或删除不得回写旧 FORMAT-030 或 FORMAT-031,任务永久清理也不得删除或改写这些无任务引用的独立分类事件。导入后新操作从备份保留且严格大于全部文件历史的 `nextOperationSequence` 继续,不得按永久清理后的剩余历史最大值回退。当前 v1 的 `category.created.details` 缺失、为 `null`、非对象或含任意字段都必须拒绝;`category.renamed.details` 缺失、为 `null`、数组、字符串、含 `afterName`、未知或额外字段,或 `beforeName` 与 `subject.name` 相同也必须拒绝,均不得自动修复。
- 当前 v1 的 `category.reordered.details` 必须严格符合 FORMAT-031,并直接保存两组发生时 Custom 分类邻居或方向边界;缺字段、额外字段、Inbox 邻居、`unavailable`、主体自引、位置内重复邻居或相同前后位置均须拒绝,不得按当前 `categoryOrder`、当前名称或历史重放补算。导入后的当前分类顺序仍只取文件中的 `categoryOrder`,历史只供筛选、搜索和审计。
- 当前 v1 的 `category.deleted.details` 必须严格符合 FORMAT-032,只含一个 JSON 非负安全整数 `affectedTaskCount`;缺失、`null`、非对象、负数、小数、超出安全整数、字符串、额外字段或任务列表必须拒绝。未发生任务主体清理的正常记录必须具有同操作 `eventOrder = 1..N` 的恰好 `N` 条 FORMAT-026 事件;已经合法清理或导入过滤时允许剩余数量少于 `N`,但每个剩余事件顺序必须仍落在 `1..N`,不得按当前任务、当前 Inbox、剩余事件数量或历史重放改写计数。
- 删除前备份是某项永久清理发生前由用户保存到产品外的完整备份,不等同于旧格式备份。Desktop Pull 不修改或销毁该文件;用户主动覆盖导入有效删除前备份时,其中后来被当前数据库永久清理的任务及当时历史可以按完整快照重新出现,仍须执行导入时到期过滤。
- 第一版不保留跨覆盖导入的永久删除墓碑、任务黑名单或其他产品外删除记忆,也不因当前数据库后来的永久清理拒绝有效删除前备份。
- 覆盖成功后应用失效导入前的自动保存、草稿重试和延迟写入,清空旧工作状态并重新完整读取导入数据库;取消或失败时不清除仍有效的原状态。

## 文件隐私

- 第一版完整备份不加密,不提供备份密码或加密导出模式。
- 导出前必须明确提示:备份包含任务、备注、未提交草稿、垃圾箱和历史,任何取得该文件的人都可以读取这些内容。
- Desktop Pull 只在用户设备上生成和下载备份,不得把备份内容上传到应用服务或第三方服务。
- 用户下载后的备份由用户自行保管;后续永久清理不会扫描、修改或销毁这些产品外文件。永久清理确认和覆盖导入确认都必须披露删除前备份可能重新带回内容。

## 文件格式

- 第一版完整备份是单个、未压缩的 UTF-8 JSON 文件。
- 根对象记录 Desktop Pull 备份标识、备份格式版本、数据库 schema 版本、应用版本、导出时间和完整数据载荷。
- 第一版不使用 ZIP、多文件目录或依赖外部文件的备份结构。

## 版本兼容

- 后续 Desktop Pull 版本必须继续导入所有正式发布版本生成的有效旧备份。
- 旧备份先在当前数据库之外迁移并完整校验,通过后才进入既定原子覆盖流程;旧 `category.created` 必须先按其明确受支持的原版本 schema 验证;只有外层旧类型与合法分类主体、时间和顺序已无歧义证明创建时,才可把当时正式允许且已验证的重复身份/名称、位置、界面入口、关联、计数或默认值确定性投影掉并生成 FORMAT-029 `{}`。未知、冲突、原 schema 不允许或主体/类型含混时拒绝,不得从当前分类、当前顺序、首次看见、后来事件或配对任务事件推断;当前 v1 损坏详情不得冒充旧版本迁移。旧 `category.renamed` 同样必须先按明确受支持的旧 schema 验证;旧记录正式同时保存改名前后名称时,只有改名后名称与规范化公共 `subject.name` 逐字一致,才能丢弃该冗余后值并把旧前值确定性投影为 FORMAT-030 `{ beforeName }`。未知、冲突或含混旧记录必须拒绝,不得从当前分类名称、当前顺序、后来事件、首次出现或历史重放推断任一名称;当前 v1 损坏详情不得改走旧迁移。旧 `task.created` 只有在旧文件自身能无歧义证明发生时初始分类、创建完成后的嵌套双邻居和任务邻居发生时标题时才可迁移为 FORMAT-022,不得从当前顺序、当前标题、默认边界或 `unavailable` 猜测。旧 `task.priority_changed` 只有在旧文件自身能无歧义证明发生时分类与不同的旧新优先级时才可迁移为 FORMAT-023,不得从最终优先级、默认 `P3`、当前分类或相邻事件猜测。旧 `task.reordered` 只有在旧文件自身能无歧义证明同分类同状态真实换位、发生时分类与状态及移动前后直接邻居时才可迁移为 FORMAT-024,不得从最终或当前顺序、分类、状态、标题、绝对索引、排序键或相邻事件猜测。旧 `task.category_changed` 只有在旧文件自身能无歧义证明直接跨分类变化、唯一状态、身份不同的来源与目标分类快照、来源移出前位置、目标插入后同状态位置及邻居发生时标题时才可迁移为 FORMAT-025,不得从最终或当前归属、顺序、状态、标题、相邻事件或界面入口猜测;两侧位置结构相同仍可合法,但正常可识别任务 ID 必须跨四槽两两不同且非主体。只有能证明是既往合法永久清理结果的任务邻居引用才可迁移为 FORMAT-021 `unavailable`,不得把无法解析、重复身份或无法补足发生时标题的损坏引用伪装成已清理引用;合法清理使 FORMAT-024 两个位置收敛或 FORMAT-025 两侧位置相同仍可迁移。旧 `task.moved_to_inbox_by_category_deletion` 只有在旧文件自身无歧义证明匹配分类删除、来源 Custom 快照、不变状态、来源总顺序、整批前来源位置、整批后最终 Inbox 位置和发生时标题时才可迁移为 FORMAT-026;不得从当前或最终状态、当前 Inbox 尾部、绝对索引、事件顺序、D-009、HIST-006 或相邻事件猜测。合法清理可留下任务事件缺口与 `unavailable`,但同一重复邻居必须全部槽位去身份化,不得半侧迁移。旧 `task.trashed` 只有在旧文件自身无歧义证明删除时分类、不变状态、移出前同状态邻居及发生时标题时才可迁移为 FORMAT-027;不得从当前任务、当前顺序、默认边界、FORMAT-014 无标题锚点或相邻事件猜测。旧 `task.restored` 只有在旧记录自身无歧义证明恢复完成后的实际分类语义(Custom 的 ID 与恢复时名称,或 Inbox)、未改变状态、插入后同状态直接邻居及其发生时标题时才可迁移为 FORMAT-028;不得从 FORMAT-027 删除事件、FORMAT-014 锚点、当前状态、默认回退、相邻事件或历史重放推断。
- 旧 `category.reordered` 只有在候选记录先通过其明确受支持的旧 schema 校验,并由记录自身无歧义证明被移动 Custom 主体、移动前后两组有方向的自定义分类序列边界或邻居 ID 与发生时用户原文名称时,才能确定性迁移为 FORMAT-031。不得从导入时当前顺序、后来历史、Inbox、绝对索引、内部排序值或 `unavailable` 猜测缺失事实;未知、冲突或含混记录必须拒绝,当前 v1 损坏详情不得转走旧迁移路径。
- 旧 `category.deleted` 只有在候选记录先通过其明确受支持的旧 schema 校验,且旧记录自身保存原受影响任务数,或文件可证明保留了清理前完整且无缺口的同操作 FORMAT-026 集合时,才能确定性迁移为 FORMAT-032。不得从导入时当前任务归属、当前 Inbox、剩余迁移事件数量、`eventOrder` 最大值、历史重放或默认 `0` 猜测;未知、冲突或已经缺失任务事件而没有原计数的旧记录必须拒绝,当前 v1 损坏详情不得转走旧迁移路径。
- 当前应用遇到无法理解的更高格式或 schema 版本时,必须保持当前数据库不变并提示用户升级应用。

## 写入故障应急导出

- 数据已加载后进入可写降级态时,任何完整导出都自动包含当前会话的全部待保存变更及其历史意图,并保留操作入队时冻结的时间与顺序而非导出时间。
- 应急导出仍使用标准、自包含的备份格式,不暴露或依赖内部待保存队列。
- 应急导出先物化工作状态:到期前已接受的待保存恢复以活动任务和入队时冻结的 FORMAT-028 实际恢复结果进入备份;只有跨期后仍为软删除的任务及其任务主体历史被排除,保留记录中的目标结构化引用同步物化为“不可用”。待保存分类创建必须以入队时公共主体与 FORMAT-029 精确 `{}` 进入备份;主清单单事件及尚未清理的选择器 `category.created(0)` 后 FORMAT-025 任务事件 `(1)` 的操作边界不得拆分或重算;关联任务逻辑到期时只排除任务主体事件,独立分类创建事件仍保留且不补建配对。待保存分类改名必须以入队时冻结的改名后公共 `subject` 与 FORMAT-030 精确 `{ beforeName }` 进入备份,不得从后来分类记录、排序、删除状态或历史重放补算或改写前后名称。独立分类主体事件继续按正常保留规则进入备份。
- 待保存分类排序必须以入队时冻结的移动分类公共 `subject` 与 FORMAT-031 精确前后位置进入应急备份;邻居快照、边界和稳定键不得从后来工作状态、当前分类名称/顺序或历史重放补算。原位放下不入队,后续改名、排序或删除不回写已冻结值。
- 待保存分类删除必须以入队时冻结的公共 `subject`、FORMAT-032 精确 `affectedTaskCount` 与同批 FORMAT-026 事件进入应急备份。计数取操作首次进入工作状态时的实际迁移集合,包含此前已经应用于工作状态的待保存活动任务变化,不含被本次确认消费的草稿;重试、后来任务操作、逻辑清理、物理残留或应急物化不得重算。任务主体事件因逻辑到期被排除时保留分类事件原计数和事件顺序缺口。
- 应急导出不会清空待保存队列或把未持久化变更标记为已保存。
- 清理待完成但没有待保存用户操作时,标准完整导出仍可使用;它必须从一个一致数据库快照和冻结的导出时刻生成单一逻辑保留状态,不得把本地数据库中暂时物理残留的到期任务、任务主体历史或保留记录中的可识别目标引用复制到新文件,也不得与并发业务写入或清理重试前后的状态拼接。与可写降级态重叠时先冻结一个工作状态快照,再应用相同逻辑排除与引用去身份化。

## 目的

- 为浏览器站点数据被清除、PWA 被卸载或设备损坏提供产品外的数据副本。
- 为未来原生移动 App 保留用户可控制的数据迁移出口。
