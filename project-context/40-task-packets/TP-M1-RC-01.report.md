## Findings 与修复

| 严重度 | Finding | 修复与红绿证据 |
|---|---|---|
| P1 | 当前核心数据库已是 schema v2，但新完整/应急备份仍写 `schemaVersion: 1`，违反 FORMAT-002 的“导出时核心数据库 schema 版本”，会让备份兼容判断失真。 | `tests/storage/emergency-backup.test.ts` 先失败显示实际值为 `1`；导出改读 `CORE_DATABASE_VERSION`，envelope 接受旧 v1 与当前 v2，并拒绝 `0.1.0 + schema v2` 的不兼容组合。 |
| P1 | 非活动窗口显示后若原活动窗口已经关闭，“在此窗口继续”只广播请求，没有接收者时会永久停在请求态，违反 WINDOW-005。 | 新测试先因找不到核心界面失败；请求操作现先尝试取得可用 Web Lock，成功后直接从持久化状态接管，等待移交时继续显示“正在请求”。 |
| P2 | 首个窗口正在移交时，后续并发请求被静默忽略，请求窗口永久停在请求态，违反 WINDOW-009 的串行与可重试要求。 | 新测试先因没有任何回复失败；活动窗口现回复 `busy`，请求窗口回到可重试的非活动态。 |

## 其余审计结论

- 永久清理只删除目标任务与任务主体历史，并把保留的恢复锚点和历史任务邻居整体投影为 `{ kind: "unavailable" }`；不推进操作顺序，不改用户自由文本。
- 到期清理先作用于逻辑工作状态；物理提交失败时保持清理待完成并从新备份排除目标，恢复边界在 `expiresAt` 处拒绝。
- 覆盖导入在严格 envelope/data 校验后执行当前完整备份、确认和六 Store 原子替换；待保存、草稿失败或清理待完成时拒绝执行。
- v1 到 v2 迁移使用不可写候选代次，完整读取验证后才更新 activation；激活前失败保留旧代次，激活后中断由下一启动续作清理。
- 指针拖拽只有长按激活后发生实际移动且有效放下才提交；取消、指针取消、未移动长按和组件退出不提交落点。
